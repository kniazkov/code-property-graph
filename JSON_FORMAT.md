# Формат JSON для AST/CPG

Версия: 2  
Дата: 2026-11-25  
Статус: черновик

## 1. Назначение

Документ описывает JSON-представление синтаксического дерева и построенного поверх него code property graph (CPG). Дерево экспортируется как массив узлов, а семантические связи (объявления, вызовы, типы, области видимости, включения) — как отдельный объект `relations`.

Экспорт выполняет класс `com.kniazkov.cpg.utils.JsonExporter`:

```java
JsonObject json = JsonExporter.toJson(graph);
String text = JsonExporter.toJsonString(graph);
```

Перегрузки `toJson(Node)` и `toJsonString(Node)` экспортируют только AST без связей. Связи хранятся в немутабельном классе `com.kniazkov.cpg.graph.Graph`.

## 2. Верхний уровень

Корневой JSON-объект содержит пять полей:

```json
{
  "format": "cpp03-cpg",
  "version": 2,
  "root": 0,
  "nodes": [],
  "relations": {
    "declarations": [],
    "calls": [],
    "types": [],
    "members": [],
    "scopes": [],
    "includes": []
  }
}
```

- `format` — строковый идентификатор формата, всегда `cpp03-cpg`.
- `version` — целое число, версия формата; сейчас `2`.
- `root` — идентификатор корневого узла; всегда `0`.
- `nodes` — массив объектов узлов.
- `relations` — объект со связями, по массиву на каждый тип связи.

## 3. Узел

Каждый элемент массива `nodes` описывает один узел:

```json
{
  "id": 0,
  "type": "TranslationUnit",
  "tags": ["declarations"],
  "fragment": {
    "start": { "offset": 0, "line": 1, "column": 1 },
    "end": { "offset": 120, "line": 5, "column": 1 },
    "code": "..."
  },
  "children": [1]
}
```

Поля:

- `id` — целое число, уникальное в пределах одной генерации JSON.
- `type` — строковое имя типа узла, возвращаемое `Node.name()`. По умолчанию это Java simple name класса узла; для анонимного класса используется полное имя. Узел может переопределить `name()`, чтобы задать стабильное языковое имя.
- `tags` — массив тегов детей. Теги уникальны внутри узла и соответствуют `children` по индексу. У list-узла массив пуст.
- `fragment` — фрагмент исходного текста, покрываемый узлом, либо `null`.
- `children` — массив идентификаторов дочерних узлов AST в порядке исходного текста.

Инварианты:

- у обычного узла `tags.size() == children.size()`;
- у list-узла `tags` пуст, а `children` — элементы списка;
- один и тот же тег не может встречаться в `tags` дважды;
- список однотипных детей представляется одним узлом с тегом, например `arguments`, а не несколькими детьми с одинаковым тегом.

## 4. Фрагмент

```json
{
  "start": { "offset": 0, "line": 1, "column": 1 },
  "end": { "offset": 10, "line": 1, "column": 11 },
  "code": "int main()"
}
```

- `start` — включающая начальная позиция.
- `end` — исключающая конечная позиция.
- `code` — текст из `Source` для полуинтервала `[start.offset, end.offset)`.

Позиция:

```json
{
  "offset": 0,
  "line": 1,
  "column": 1
}
```

- `offset` — абсолютное смещение в символах, начиная с нуля.
- `line` — номер строки, начиная с единицы.
- `column` — номер колонки, начиная с единицы.

## 5. Связи

Объект `relations` содержит по массиву на каждый тип связи. Каждый элемент массива — направленное ребро `from → to`:

```json
"relations": {
  "declarations": [
    { "from": 7, "to": 2 }
  ],
  "calls": [
    { "from": 9, "to": 4 }
  ],
  "types": [],
  "members": [],
  "scopes": [],
  "includes": []
}
```

Поля ребра:

- `from` — идентификатор узла-источника связи;
- `to` — идентификатор узла-цели связи.

Типы связей (ключи объекта `relations`):

- `declarations` — узел, использующий сущность, → узел, объявляющий её;
- `calls` — узел вызова → вызываемая сущность;
- `types` — узел → его тип;
- `members` — узел → содержащая область видимости;
- `scopes` — узел → его лексическая область видимости;
- `includes` — узел → включаемая единица.

Правила:

- каждый массив содержит связи только своего типа;
- связи не хранятся в узлах `nodes`, чтобы дерево оставалось немутабельным;
- у одного источника может быть несколько целей — тогда для каждой цели выводится отдельное ребро;
- пустой тип связи выводится как пустой массив, чтобы схема была стабильной.

## 6. List-узлы

Несколько однотипных детей группируются в один list-узел. Например, аргументы вызова:

```json
{
  "id": 3,
  "type": "ExpressionList",
  "tags": [],
  "fragment": {
    "start": { "offset": 4, "line": 1, "column": 5 },
    "end": { "offset": 9, "line": 1, "column": 10 },
    "code": "x, y"
  },
  "children": [4, 5]
}
```

Родительский узел ссылается на него по тегу:

```json
{
  "id": 0,
  "type": "CallExpression",
  "tags": ["callee", "arguments"],
  "children": [1, 3]
}
```

Правила:

- list-узел является обычным узлом и получает собственный `id`;
- `tags` list-узла всегда пуст;
- элементы списка не тегируются со стороны list-узла;
- пустой список — это list-узел с пустым `children`;
- для пустого списка используется zero-length fragment в позиции вставки;
- конкретные типы: `ExpressionList`, `StatementList`, `ParameterList`.

## 7. Правила идентификаторов

- Корневой узел экспортируемого дерева или поддерева всегда получает `id = 0`.
- Идентификаторы уникальны в пределах одной генерации JSON.
- Идентификаторы монотонно возрастают в порядке обхода.
- Обход детерминирован: сначала дочерние узлы в порядке `children`, затем цели связей в фиксированном порядке типов.
- Идентификатор назначается при первом посещении узла; повторное посещение не меняет идентификатор.
- Для идентификации используется тождество объекта, а не `equals`; два структурно равных, но разных узла получают разные идентификаторы.
- Идентификаторы не переиспользуются и не зависят от предыдущих генераций.

## 8. Замыкание по связям

Экспорт включает не только AST-поддерево, но и все узлы, достижимые по связям. Благодаря этому любое ребро указывает на `id`, который присутствует в `nodes`.

Алгоритм:

1. Начать с корня и поместить его в стек.
2. Пока стек не пуст:
   - извлечь узел;
   - если он уже посещён, пропустить;
   - назначить следующий идентификатор и добавить узел в список;
   - собрать цели всех связей в порядке типов, затем дочерние узлы;
   - поместить собранные узлы в стек в обратном порядке.
3. Построить JSON по списку узлов.
4. Для каждого типа связи вывести рёбра, перебирая источники в порядке их идентификаторов.

## 9. Детерминизм

Для одного и того же графа экспорт должен давать одинаковый JSON:

- порядок узлов соответствует возрастанию `id`;
- порядок `children` сохраняется;
- порядок типов связей фиксирован: `declarations`, `calls`, `types`, `members`, `scopes`, `includes`;
- порядок рёбер внутри типа определяется порядком источников и порядком целей;
- `type` не зависит от времени, платформы или хэш-кода;
- `code` берётся из `Source` без нормализации.

Если узлы или связи созданы в другом порядке, идентификаторы и порядок рёбер могут отличаться; это допустимо, потому что контракт фиксирует порядок обхода, а не порядок создания объектов.

## 10. Пример

```json
{
  "format": "cpp03-cpg",
  "version": 2,
  "root": 0,
  "nodes": [
    {
      "id": 0,
      "type": "TranslationUnit",
      "tags": ["declarations"],
      "fragment": {
        "start": { "offset": 0, "line": 1, "column": 1 },
        "end": { "offset": 10, "line": 1, "column": 11 },
        "code": "int main()"
      },
      "children": [1]
    },
    {
      "id": 1,
      "type": "DeclarationList",
      "tags": [],
      "fragment": {
        "start": { "offset": 0, "line": 1, "column": 1 },
        "end": { "offset": 8, "line": 1, "column": 9 },
        "code": "int main"
      },
      "children": [2]
    },
    {
      "id": 2,
      "type": "Declaration",
      "tags": ["type", "name"],
      "fragment": {
        "start": { "offset": 0, "line": 1, "column": 1 },
        "end": { "offset": 8, "line": 1, "column": 9 },
        "code": "int main"
      },
      "children": [3, 4]
    },
    {
      "id": 3,
      "type": "Name",
      "tags": [],
      "fragment": {
        "start": { "offset": 0, "line": 1, "column": 1 },
        "end": { "offset": 3, "line": 1, "column": 4 },
        "code": "int"
      },
      "children": []
    },
    {
      "id": 4,
      "type": "Name",
      "tags": [],
      "fragment": {
        "start": { "offset": 4, "line": 1, "column": 5 },
        "end": { "offset": 8, "line": 1, "column": 9 },
        "code": "main"
      },
      "children": []
    }
  ],
  "relations": {
    "declarations": [],
    "calls": [],
    "types": [
      { "from": 2, "to": 3 }
    ],
    "members": [],
    "scopes": [],
    "includes": []
  }
}
```

## 11. Ограничения текущей версии

- `type` по умолчанию использует Java-имя класса. Для долговременного формата узлы должны переопределять `name()` стабильным языковым именем.
- `code` дублирует исходный текст для каждого узла. Для больших деревьев это может быть избыточно; в будущем можно добавить режим без `code`.
- Связи выводятся отдельным объектом `relations`; в узлах они не дублируются.
- Формат не описывает диагностику, таблицы символов и типы; это следующие слои CPG.
- `fragment` может быть `null`, если узел синтетический и не имеет исходного текста.

## 12. Версионирование

При несовместимом изменении структуры увеличивается `version`. Совместимые дополнения (новые необязательные поля) версию не меняют. Потребитель должен проверять `format` и `version` перед разбором.
