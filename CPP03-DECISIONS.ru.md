# C++03. Вопросы и решения

[Пошаговый план и критерии приёмки](CPP03-PLAN.ru.md). Здесь вопросы записаны по смыслу с исходной нумерацией. Примеры поясняют, что именно согласовано. Обновляем журнал и чеклист не реже одного раза за каждые три вопроса. Открытые вопросы отделяем от принятых решений.

## Исходная точка

На просьбу восстановить контекст предыдущего чата сверили состояние проекта. Ручной парсер Java/C++ уже строит неизменяемый Project, есть анализ потоков, генерация, сквозные тесты и справочник модели на русском и английском. Для следующего этапа выбрали ISO/IEC 14882:2003. В репозитории лежит рабочий проект N1638 от апреля 2004 года с более поздними поправками; спорные правила сверяем с редакцией 2003 года. Поручение этого чата — подробный русский Markdown-чеклист в корне репозитория, с обсуждением вопросов по одному.

## 1–5. Стандартная библиотека и препроцессор

1. **Насколько глубоко понимать стандартную библиотеку?** Анализу нужна общая модель наблюдаемой операции. Переменная типа `std::vector<int>` может быть представлена как динамический массив целых. Детали перераспределения памяти для такой модели не нужны.
2. **Озеленять ли операции над контейнером?** Да. Для `v.push_back(x)` общая операция добавления в конец читает аргумент и изменяет контейнер.
3. **Нужны ли установленные заголовки STL?** Нет. Описания стандартных типов и операций поставляются с CPG на основании стандарта. Одноимённый метод пользовательского класса сам по себе не основание для озеленения.
4. **Как представить разрешённую библиотечную операцию без зелёного эквивалента?** Оставить C++-вызов со ссылкой на выбранное объявление. Его можно анализировать и генерировать обратно.
5. **Как читать пользовательские заголовки?** Собственным препроцессором C++03 на Java, учитывая пути поиска, макросы и условия конкретной сборки.

## 6–11. Происхождение макросов и варианты сборки

6. **Сохранять ли связь с исходным вызовом макроса и как она выглядит на графе?** Да. В `SQUARE(a)` узел умножения имеет двух детей-чтений; оба происходят из одного аргумента. От операции можно перейти к вызову и к оператору в определении. Для вложенных раскрытий сохраняется вся цепочка. Обычный Visitor идёт по детям, происхождение доступно отдельно, в SVG — отключаемым слоем.
7. **Что генерировать после правки раскрытия?** Неизменённый вызов можно восстановить, если он раскроется так же. Если в одном раскрытии заменить правое чтение на `b`, сгенерировать выражение с `a * b` в этой точке. Сохранить происхождение, определение и остальные вызовы.
8. **Допустимы ли разные параметры для разных .cpp в одном Project?** Да. Один физический config.h с условным typedef может давать разные типы в разных единицах трансляции.
9. **Обязателен ли импорт compile_commands.json?** Да, через CLI и Java API. Учитывать рабочую папку, файлы, пути заголовков и порядок параметров препроцессора. Простой запуск по папке сохраняется.
10. **Что делать с несколькими командами для одного .cpp?** Сохранить отдельные варианты в одном Project и позволить анализу выбрать нужную единицу. Не смешивать их ссылки и потоки.
11. **Как связывать вызовы между несколькими сборками?** Явно задавать состав сборки. При неизвестном составе и нескольких подходящих определениях показывать возможные цели. Дополнительное поручение — объяснить в начале плана зелёные (общие) и красные (языковые) узлы и озеленение как отдельный проход.

## 12–19. Типы и анализ потоков

12. **Откуда брать разрядность типов?** Из параметров или файла профиля, например JSON. По умолчанию int — 32 бита, long — 64. Эффективный профиль определяет конкретные свойства типа.
13. **Сохранять ли исходный тип после озеленения?** Да. Даже при равной ширине int и long различаются в перегрузках. Хранить связь с типом C++ и выбранной функцией, чтобы при генерации сохранить смысл `f(1L)`.
14. **Что делать с неизвестным sizeof?** Выравнивание тоже имеет настройки и значения по умолчанию. Сворачивать выражение только при достаточных данных. Если размещение полей неизвестно, сохранять sizeof с неизвестным значением.
15. **Сохранять ли символическую границу массива?** Да. У `char buf[sizeof(S) + 1]` хранить выражение с операндами. При повторном анализе с полным профилем можно получить численную длину.
16. **Должны ли быть видны неявные деструкторы?** Да. В CFG видны вызовы при выходе из области и при раскрутке стека. Разрушаются успешно созданные объекты в обратном порядке. При генерации автоматическое разрушение остаётся неявным.
17. **Какие пути даёт внешний вызов без тела?** Для `void work();` учитывать возврат и возможное исключение. Для `void work() throw();` исключение от этого вызова не ведёт к обработчику в вызывающей функции.
18. **Что происходит с данными при передаче неконстантной ссылки внешней функции?** После `x = 1; update(x);` у чтения x возможны два источника: инициализация и запись при вызове. Сам факт передачи ссылки не доказывает, что значение перезаписано.
19. **Связывать ли чтение с конкретной записью внутри доступного тела?** Да. Если update безусловно выполняет `x = 7`, после нормального возврата достигает именно эта запись. Дальнейшие технические решения по DFG пользователь делегировал.

## 20–26. Проверки, редакция языка и генерация

20. **Что считать первой вехой?** Большой воспроизводимый пример с двумя .cpp, общим заголовком, compile_commands.json, раскрытием макроса, просмотром происхождения, правкой и запуском результата. Главная цель — большой корпус E2E в CI. Исходники каждого сценария доступны для ручной проверки.
21. **Какие компиляторы обязательны?** GCC и Clang на Linux в строгом режиме C++03. Для исполняемых сценариев проверять исходную и сгенерированную программы обоими компиляторами.
22. **Сколько проверять перевод в Java?** Очень ограниченно. Оставить простые регрессионные примеры прототипа. Приёмка новых конструкций, в том числе vector, опирается на граф и генерацию C++03.
23. **Как обрабатывать расширения компиляторов?** При активной неподдерживаемой конструкции, например GNU packed, выдавать ошибку с координатами. Поддержку диалектов отложить.
24. **Сохранять ли неактивные ветви при генерации?** Да. Правка серверной ветви сохраняет клиентский текст и директивы. Дополнительное решение — указывать редакцию C++ в параметрах парсера и CLI; сейчас поддерживается 03.
25. **Обязателен ли явный выбор редакции при запуске?** Пока нет. Для прежних вызовов API и CLI по умолчанию используется C++03. Явный запрос неподдерживаемой редакции даёт ошибку.
26. **Как учитывать -std из compile_commands.json?** Приоритет: явный выбор API/CLI, затем -std команды конкретной единицы, затем C++03 по умолчанию. Можно намеренно проверить по C++03 исходник, для которого в базе указана более поздняя редакция.

## 27–34. Исходные ветви, внешние данные и шаблоны

27. **Как вывести один заголовок после несовместимых правок разных конфигураций?** Если один физический `return 1;` изменён только для сервера, остановить генерацию до записи и указать строку и обе сборки. Одинаковая правка проходит. Если строки уже разделены через #ifdef, серверную можно менять отдельно. Автоматически угадывать условие для нового #ifdef нельзя.
28. **Как показать неактивную ветвь и что делать, если она синтаксически не складывается?** В API и JSON хранить текст, координаты и явную метку неактивности для данного включения. Не раскрывать её макросы и не строить для неё AST, CFG или DFG. Даже активная ветвь может быть частью выражения: парсер получает весь активный поток единицы. Вложенность директив и наличие закрывающего #endif проверяет препроцессор.
29. **Видно ли неиспользованное определение макроса?** Да. Активный #define из заголовка имеет имя, параметры при наличии, текст замещения, координаты и список раскрытий, в том числе пустой. После #undef и нового определения различать оба определения.
30. **Отличать ли проверку наличия от раскрытия значения?** Да. При -DDEBUG=0 директива #ifdef DEBUG активна: одна проверка, ноль раскрытий. Для отсутствующего имени сохранить проверку и отрицательный результат.
31. **Показывать ли источник внешнего макроса и где разместить его узел?** Да. Макрос из -D принадлежит аргументу конкретной команды, встроенный макрос — профилю. Каждый внешний узел структурно достижим от Project через детей; ссылка происхождения ведёт к этому узлу.
32. **Как хранить стандартную библиотеку?** Полный каталог существует вне графа. В Project один раз материализуются используемые заголовки, объявления, необходимые зависимости и их владельцы. Одно включение vector создаёт ссылку на заголовок, но не переносит все методы в граф.
33. **Храним и шаблон, и его специализации частично?** Для встроенной библиотеки — да: общее объявление и каждую востребованную специализацию с нужными членами. При наличии vector<int> и vector<double> вызов push_back только для int создаёт конкретный метод у первого типа. Явно написанная пользователем специализация сохраняется как часть исходника.
34. **Доступно ли тело пользовательского шаблона без инстанцирования?** Да. В `template<class T> int count(const T& x) { return x.size(); }` доступны возврат и вызов. Цель зависимого вызова остаётся открытой. При инстанцировании для vector<int> связать вызов конкретной специализации с соответствующим size(), сохранив доступ к общему телу.

## 35–36. Причины инстанцирования

35. **Показывать ли места, которым понадобилась специализация?** Да. Связь вызова с целью и связь места с экземпляром шаблона, который там потребовался, имеют разный смысл. От общего экземпляра можно получить все такие места.
36. **Показывать ли вложенные инстанцирования?** Да. В цепочке `main → outer<int> → inner<int>` непосредственным источником запроса на `inner<int>` служит место внутри конкретного `outer<int>`. Обратным обходом видна вся цепочка до исходного запроса.

## 37–39. Диагностика и неявные операции

37. **Как сообщать об ошибке во вложенном инстанцировании?** Сначала показать координаты выражения и причину с подставленными типами, затем места запросов от ближайшего к исходному. Диагностика доступна и при отсутствии графа.
38. **Как различать явное и неявное преобразование?** В обоих случаях представить преобразование узлом с исходным и целевым типами и признаком явности. Для явного приведения сохранить диапазон написанной конструкции.
39. **Как показывать аргумент по умолчанию?** Параметр в объявлении владеет выражением. При пропуске аргумента вызов ссылается на применённое выражение; явно написанный аргумент принадлежит вызову. Генерация сохраняет различие между `log()` и `log(2)`.

## 40–42. Виртуальные методы

40. **Как представить виртуальный вызов с аргументом по умолчанию?** Раздельно связать вызов со статически выбранным объявлением, выражением аргумента по умолчанию и возможной исполняемой реализацией. Для одного объекта Derived вызовы через Base& и Derived могут передавать разные значения в один метод.
41. **Нужна ли связь переопределения без вызовов?** Да. Связать сам переопределяющий метод с базовым объявлением, обеспечить обратный поиск. В месте вызова сохранять его собственные связи. Одноимённый метод с другими параметрами не приобретает связь переопределения по одному имени.
42. **Если метод переопределяет методы двух базовых классов, сохраняем обе связи?** Да. Device::reset переопределяет и Printer::reset, и Scanner::reset. При вызове через Printer& статически выбран Printer::reset, через Scanner& — Scanner::reset.

## 43–45. Цепочки разрешения имён

43. **Сохранять ли цепочку typedef?** Да. Для `OrderId → Counter → unsigned long` доступны все промежуточные объявления и запрос конечного типа. При генерации сохраняется исходное имя.
44. **Как представить using-объявление?** Включить его в единую цепочку от написанного имени к объявлению и далее к типу. По уточнению пользователя API вычисляет конечный тип обходом цепочки; дополнительное прямое ребро не требуется.
45. **Как представить using-директиву?** У `using namespace shop;` один узел со ссылкой на `shop`. Шаг разрешения конкретного использования связывает директиву с найденным для этого имени объявлением.

## 46–48. Неполные типы и комментарии

46. **Как связать предварительное объявление с определением?** От использования имени перейти к объявлению, видимому в этой точке, затем к полному определению, если оно доступно в проекте. Полноту типа проверять в точке использования.
47. **Сохранять ли комментарии?** Да, сохранять их текст и координаты в графе и восстанавливать при генерации. В пакете утилит предусмотреть отдельно тестируемую операцию удаления комментариев, доступную по явному вызову через Java API. Она возвращает новый снимок; автоматический запуск и отдельная команда CLI не предусмотрены.
48. **Очищать ли неактивные ветви?** Да. Утилита удаляет комментарии и из сохранённого текста этих ветвей. Содержимое литералов и разделение токенов сохраняются.

## 49–51. Привязка комментариев и Doxygen

49. **Как связать комментарий с кодом?** Файл владеет единственным узлом комментария. Поясняемая конструкция ссылается на него через `HAS_COMMENT`.
50. **Как выбирается конструкция?** Концевой комментарий относится к последней завершённой конструкции строки; непосредственно предшествующий блок — к следующей конструкции, пока их не разделяет пустая строка. В `f(a, /* в байтах */ size)` поясняется аргумент `size`. Отделённая шапка и неоднозначные комментарии остаются у файла.
51. **Какой объём Doxygen поддерживаем?** Весь исходный текст сохраняется. Структурно разбираем `brief`, `param`, `tparam`, `return` с префиксами `@` и `\`. Документацию связываем с объявлением, записи параметров — с параметрами функции или шаблона. Остальные команды сохраняются текстом.

## 52–54. Имена параметров в документации

52. **Что делать с устаревшим именем в `@param`?** Сохранить запись без ссылки, поставить предупреждение на имя и вернуть полный граф. Совпадение по позиции не используется для угадывания цели тега.
53. **Обновлять ли документацию при переименовании параметра через API?** Обновить имя в связанном теге при генерации. Сохранить свободный текст описания дословно, включая совпадения со старым именем.
54. **Если у объявления и определения разные имена параметров, к чему привязать тег?** К параметру документируемого объявления. Параметры одной функции в разных объявлениях сопоставляются по позиции. От параметра определения можно перейти к документации в заголовке; локальное переименование в определении не меняет тег в заголовке.

## 55–57. Документация функции и однозначность генерации

55. **Как показывать документацию из `.h` и `.cpp`?** Хранить комментарии при своих объявлениях; запрос всей документации возвращает каждый текст с его координатами, включая несколько `@brief`.
56. **Дублировать ли комментарий общего заголовка при нескольких включениях?** Возвращать один раз по физическому месту. Привязки и проверка параметров зависят от контекста включения.
57. **Что делать с неоднозначным именем после правки?** Общее требование — никогда не выдавать код с неоднозначностями. При известной цели сохранять однозначное написание либо подобрать эквивалентную квалификацию. При невозможности сохранить однозначный смысл завершить генерацию с диагностикой до записи файлов.

## 58–60. Переименование и граф с ошибками

58. **Как обновлять использования?** Переименовать выбранную сущность и связанные использования по всему проекту, включая using-объявления. Одноимённые независимые сущности сохраняют имена.
59. **Что делать с переопределениями?** Показать затронутое семейство и переименовать его вместе, включая несколько баз и все связанные вызовы. Заблокированная правка внешнего метода диагностируется до частичного изменения семейства.
60. **Отменять ли правку из-за возникшего конфликта?** Нет. Если после переименования появились два метода с одной сигнатурой, вернуть новый граф с обоими методами, диагностикой конфликта и явной отметкой ошибки в корне Project. Чтение исходника с таким же конфликтом даёт такой же результат. Граф доступен для изучения и исправления. Генерация ошибочного C++ запрещена согласно решению 57.

## 61–63. Восстановление разбора и экспорт

61. **Возвращать ли граф при синтаксической ошибке?** Да. Пометить корень, сохранить диагностику и узел ошибки там, где известно его место. Продолжать только от надёжно установленной границы. Если восстановиться нельзя, сохранить разобранную часть и позицию остановки.
62. **Продолжать ли другие единицы трансляции?** Да. Разбирать каждую со своими параметрами, даже если предыдущую удалось разобрать лишь частично.
63. **Что делает CLI с `--json` при битом графе?** Записывает граф и диагностику, включая успешно разобранные единицы, и возвращает ненулевой код выхода. Генерация C++ остаётся заблокированной.

## 64–66. Просмотр, анализ и исправление битого графа

64. **Экспортировать ли битый граф в SVG?** Да. Показать доступную часть графа, отметить ошибки на корне и обозначить позицию остановки у файла с прерванным разбором.
65. **Какие функции анализировать?** Строить CFG и DFG для полностью разобранных функций, в том числе перед ошибкой в том же файле. У оборванной функции сохранить доступные узлы и явно указать неполноту анализа потоков.
66. **Как снять статус ошибки после исправления через API?** Автоматически перепроверить новый снимок по завершении правки. После устранения последней ошибки разрешить генерацию C++; предупреждения сохраняются и генерации не мешают. Предыдущий снимок сохраняет свой статус.

## 67–69. Диапазоны ошибок и происхождение токенов

67. **Что хранит узел ошибки при восстановлении?** Для пропущенного фрагмента — точный текст и диапазон. Для отсутствующего — пустой текст и точку вставки, например перед `;` в `int x = ;`. Доступно через API и JSON.
68. **Использовать ли цепочку раскрытий в синтаксической диагностике?** Да. Для `ASSIGN(total);`, раскрывшегося в `total = ;`, показать вызов и место происхождения `=` в определении макроса. Узел отсутствующего выражения остаётся перед `;`.
69. **Может ли одна диагностика относиться к нескольким файлам?** Да. Для неудачной склейки `JOIN(+, *)` основная позиция — вызов, а дополнительные подписанные диапазоны — `+`, `*` и `##` в определении. CLI группирует их в одно сообщение, API и JSON дают доступ к каждому диапазону.

## 70. Сводка диагностики и завершение блока

70. **Как показать повторившуюся ошибку общего заголовка?** В сводке одна запись с числом затронутых единиц трансляции. Для каждого срабатывания в API и JSON остаются его конфигурация и цепочка включений. Разные причины на одной строке образуют разные группы.

Дальнейшие решения по обработке ошибок на этой стадии пользователь делегировал. Для реализации приняты детерминированный порядок диагностики, подавление только доказанно производных сообщений и обязательный прогресс либо остановка при восстановлении парсера. Критерии и проверки внесены в чеклист. Обсуждение блока завершено.

## 71–73. Операторные вызовы и копирование контейнера

71. **Как представить перегруженный оператор?** Сохранить исходную операторную запись с операндами и связь с выбранной функцией. Анализ учитывает поведение этой функции. Сам знак `+` не обосновывает озеленение в числовое сложение.
72. **Как учесть копирование элемента при push_back?** У зелёной операции добавления сохранить отдельную связь с вызываемым пользовательским конструктором копирования элемента и учитывать его эффекты.
73. **Как представить копирование vector?** Создать отдельный динамический массив с копиями элементов и связью с их конструктором копирования. Изменение размера копии не затрагивает исходный массив. Совместное владение или использование объектов за указателями определяется поведением типа элемента.

## 74–76. Семейства операций STL

74. **Различать ли создание и присваивание контейнера?** Да. Присваивание заменяет содержимое существующего объекта; ссылка на сам контейнер остаётся связана с ним.
75. **Как моделировать swap?** Одной операцией обмена содержимого. Контейнеры сохраняют идентичность, ссылка на элемент после обмена ведёт к нему в другом контейнере.
76. **Как планировать остальные методы STL?** Пользователь делегировал детализацию по семействам. Для групп операций фиксируем эффекты, связи и E2E; отдельно обсуждаем решения, меняющие общую модель. Чеклист содержит серии для vector и последующих семейств стандартной библиотеки.

## 77–79. Происхождение результатов проходов

77. **Как объяснить зелёный узел, полученный из нескольких исходных?** Сохранить связь с корнем конструкции и связи с участниками по их роли в свойствах результата. У `PrintStatement` видны источник потока, значения и вклад `std::endl` в перевод строки и сброс буфера.
78. **Нужен ли обратный переход?** Да. В контексте выбранного снимка API возвращает все результаты, в создании которых участвовал исходный узел, и роли этого участия. Обратный запрос использует те же рёбра; исходный снимок неизменяем.
79. **Сохранять ли цепочку через несколько проходов?** Да. Каждый проход записывает свой шаг к предыдущему снимку. API позволяет пройти от `5` через свёртку `2 + 3` к исходному выражению и определить, какой проход выполнил преобразование.

## 80–82. Самостоятельный JSON-экспорт

80. **Какую историю включать в файл?** Выбранный снимок и узлы предыдущих стадий, необходимые для прохода по цепочке происхождения до исходника. Остальные узлы предыдущих снимков исключаются.
81. **Нужна ли загрузка JSON обратно в Java API?** Нет. Экспорт односторонний. Внешний инструмент читает файл самостоятельно, без восстановления `Project`.
82. **Версионировать ли формат?** Да. В корне JSON числовое поле `schemaVersion`. До окончания разработки версия фиксирована на `1`. После стабилизации необязательные дополнения совместимы, а переименование или изменение смысла поля требует новой версии.

## 83–85. Идентификаторы и история снимка

83. **Сохранять ли ID между разными версиями исходника?** ID локальны для одного файла JSON. На одинаковом входе с теми же параметрами экспорт детерминирован; при изменении исходника узлы могут получить другие номера.
84. **Указывать ли стадию?** Да. Корень JSON содержит `stage` со значением `parsed`, `resolved`, `green` или `folded`.
85. **Записывать ли проход без изменений или находок?** Да. API и JSON показывают фактически выполненные проходы в порядке запуска, включая прямой вызов через Java API. Это позволяет отличить отсутствие запуска от проверки без предупреждений.

## 86–88. Актуальность и область анализа

86. **Что показывать после правки?** Предыдущий запуск остаётся в истории. Если его результат устарел, API и JSON показывают для нового снимка статус «требуется пересчёт».
87. **Кто обновляет зависимости?** Запрошенный проход автоматически пересчитывает необходимые устаревшие зависимости. История отражает фактический порядок выполнения.
88. **Видна ли область запуска?** Да. При проверке отдельной функции в истории есть ссылка на неё, а результат относится к этой функции. Статусы остальных функций сохраняются. По умолчанию проход проверяет весь проект.

## 89–91. Пользовательские проходы через Java API

89. **Подключать ли пользовательские проходы и какой интерфейс предложен?** Да. Проход объявляет идентификатор и зависимости; runner готовит их для выбранной области и сохраняет историю. Для анализа предложен `AnalysisPass` с `PassContext`; первоначальный `DiagnosticSink` расширен решением 91.
90. **Нужны ли пользовательские преобразования дерева?** Да. Отдельный `TransformationPass` получает контекст и `ProjectEditor`. Runner применяет накопленные правки одним пакетом и возвращает новый снимок.
91. **Может ли анализ публиковать типизированные результаты?** Да. `AnalysisResults` принимает диагностику и значения для отдельных узлов. Последующий проход может получить результат через Java API даже при отсутствии предупреждений. Пример — диапазон значения выражения.
