# Code Property Graph — требования

Статус: сбор требований. Дата начала: 3 ноября 2026 года.

## 1. Контекст и цель

Работа над Astranaut временно приостановлена по распоряжению руководства. Начинается отдельный Java-проект Code Property Graph.

Проект должен предоставлять структуру графа для представления программ на нескольких языках. У представлений разных языков должны быть общие узлы. Конкретный состав узлов, рёбер и правила сохранения языковых различий предстоит согласовать.

В проекте должен быть собственный парсер для поддерживаемых языков, написанный вручную целиком на Java. Генераторы парсеров (например, ANTLR) для его реализации не используются. Допустимость прочих сторонних Java-библиотек пока не определена.

Назначение графа — статический анализ и оптимизация кода. Для первого прототипа согласован общий проход свёртки констант; остальные виды анализа и оптимизаций пока не определены. Изменённое представление программы должно поддерживать генерацию исходного кода; требования к ней приведены ниже.

## 2. Поддерживаемые языки

Конечная цель — поддержка достаточно большого подмножества C, C++, Java, JavaScript и Python. Версии языков, точные границы подмножеств и порядок реализации пока не определены. Полная поддержка всех перечисленных языков не заявлена как требование первого прототипа.

### Первый прототип

Первый прототип должен поддерживать очень маленькие программы на C++ и Java: один класс, один метод main, вычисление чего-нибудь несложного и вывод в консоль. Это начальный объём поддержки, а не ограничение конечного проекта.

Уже на начальном этапе, в первом прототипе, обязательно поддерживается чтение как минимум одной папки с исходниками. Вход не должен ограничиваться одиночным файлом. Результат чтения папки — один граф проекта. В первом прототипе читаются только файлы непосредственно в указанной папке; вложенные папки не обходятся. Рекурсивное чтение пока отложено. Правила отбора файлов пока не согласованы.

Для C++ согласована следующая форма программы:

```cpp
class Program {
public:
    static void main() {
        // Вычисление и вывод.
    }
};

int main() {
    Program::main();
    return 0;
}
```

В Java используется обычный метод `public static void main(String[] args)` внутри класса. Таким образом, C++-пример содержит один класс с методом main и дополнительную свободную функцию main — точку входа.

Для вычислений в первом прототипе достаточно следующего набора:

- локальные переменные типа int и целочисленные литералы;
- объявления с инициализацией и присваивание;
- арифметические операции +, -, *, / и скобки;
- вывод результата в консоль.

Условия и циклы в первый прототип не входят. Пример вычисления:

```java
int a = 2;
int b = 3;
int result = (a + b) * 4;
System.out.println(result);
```

Консольный вывод сначала представляется исходными распознанными конструкциями. Отдельный алгоритм «озеленения» заменяет соответствующие комбинации узлов общим узлом вывода. Критерии готовности прототипа уточняются далее.

В первый прототип входит отдельный общий проход свёртки констант, применимый к графам C++ и Java. Он заменяет арифметические выражения из констант вычисленными литералами: например, `(2 + 3) * 4` превращается в узел `20`. По преобразованному графу можно генерировать исходный код.

Распространение значений переменных и другие оптимизации пока не включены в согласованный объём. В примере с переменными a и b подстановка их значений не требуется; для демонстрации свёртки используется выражение непосредственно из литералов. При делении на ноль или выходе математического результата операции за согласованный диапазон int эта операция остаётся несвёрнутой в графе. Оптимизатор не заменяет её значением, полученным с переполнением. Точный диапазон int и целевая модель C++ должны быть явно определены при реализации прототипа.

В первом прототипе C++ директивы `#include` распознаются и сохраняются для обратной генерации. Чтение содержимого подключаемых заголовков и разбор стандартной библиотеки на этом этапе не выполняются. Например, `#include <iostream>` сохраняется, а ссылки на отсутствующие объявления стандартной библиотеки остаются неразрешёнными. Макросы и другие возможности препроцессора этим решением в объём прототипа не добавляются.

### Генерация исходного кода

- Узлы должны иметь методы для превращения дерева в исходный код.
- Генерация должна поддерживать несколько языков, а не только язык исходной программы.
- Полученный код должен быть человекочитаемым, с отступами.
- Сохранять исходное форматирование не требуется: сгенерированный текст может внешне отличаться от исходного.
- При разборе и обратной генерации на исходном языке без преобразований графа поведение программы должно сохраняться. Например, C++ → неизменённый граф → C++ может изменить оформление, но не поведение программы.
- Конкретный API методов, правила отступов и сохранение комментариев пока не согласованы.

### «Зелёные» и «красные» узлы

Узлы графа делятся на две категории:

- «Зелёные» узлы подходят для всех языков поддерживаемого набора.
- «Красные» узлы подходят только для определённого языка или нескольких языков.

Полностью «зелёное» дерево может быть преобразовано в исходный код на любом поддерживаемом языке. Дерево с «красными» узлами допускает генерацию только на определённом языке или языках, совместимых с этими узлами.

Набор доступных языков генерации дерева равен пересечению наборов языков, поддерживаемых всеми его узлами. «Зелёные» узлы не сужают этот набор. Например, сочетание узла для C и C++ с узлом только для C++ допускает генерацию всего дерева только на C++. Если пересечение пусто, генерация всего дерева невозможна ни на одном языке.

Основное назначение «зелёных» узлов — возможность писать общие алгоритмы для разных языков. При межъязыковой генерации достаточно получить «похожий» код; точная трансформация кода одного языка в семантически эквивалентный код другого языка не требуется. Сам по себе «зелёный» статус не гарантирует одинаковое поведение конструкции на всех языках. Требование компенсировать все семантические различия языков дополнительными конструкциями не принимается.

Способ сообщения о невозможности генерации пока не согласован. Послабление в отношении точной семантики межъязыковой генерации не распространяется на обратную генерацию на исходном языке: без преобразований графа она должна сохранять поведение программы.

## 3. Основное требование: расширение языков

Архитектура должна позволять очень быстро добавлять поддержку надстроек над базовыми языками, используемых компанией заказчика. Добавление таких надстроек — ключевой сценарий проекта, а не второстепенная возможность.

Мотивирующий пример заказчика — AscendC как надстройка над C++. Нужен собственный открытый парсер, позволяющий отказаться от зависимости от проприетарного парсера Huawei в целевом сценарии. Наличие или отсутствие иных реализаций здесь не утверждается: это описание потребности заказчика, а не обзор рынка.

Поддержка языковых надстроек добавляется непосредственным изменением кода в этом репозитории. Результат — монолитная Java-библиотека. Отдельные подключаемые модули для надстроек и расширение без изменения исходников базового парсера не требуются. Внутренняя организация кода пока не определена.

Фраза «практически моментально» пока выражает качественную цель. Измеримые критерии скорости добавления расширений и допустимый объём изменений будут согласованы отдельно.

### Структура графа

Результат чтения папки представляет собой один граф с корневым узлом проекта. Под корнем находятся узлы исходных файлов, внутри которых расположены их синтаксические деревья. Дополнительные ссылки могут связывать узлы разных файлов.

Основой представления программы служит синтаксическое дерево: функции, блоки, выражения и другие конструкции. Граф образуется за счёт дополнительных связей между узлами этого дерева.

Дополнительные связи хранятся в самих узлах как конкретные ссылки (референсы) на другие узлы и доступны для последующего использования алгоритмами. Например, использование переменной связано с её объявлением, а вызов функции — с объявлением функции.

Построение разделяется на этапы: парсер строит синтаксическое дерево, затем отдельный проход разрешает имена и заполняет ссылки на объявления. Это решение касается итоговых ссылок графа и не запрещает использовать вспомогательную информацию об именах во время разбора.

Алгоритмы заполнения ссылок должны быть по возможности общими для разных языков («зелёными»). Чем шире их применимость к поддерживаемым языкам, тем лучше. Это приоритет проектирования; конкретный механизм учёта языковых различий пока не выбран.

Граф с неразрешёнными ссылками допустим. Если целевое объявление найти не удалось, узел и имя сохраняются, а состояние неразрешённой ссылки явно обозначается. Дальнейшие алгоритмы могут работать с доступной информацией. Например, отсутствие объявления функции из внешней библиотеки не требует отбрасывать узел её вызова или весь граф.

Конкретный состав ссылок и представление состояния неразрешённой ссылки в Java API пока не согласованы.

### Целостность возвращаемого результата

Функция чтения возвращает только целый и валидный граф проекта либо не возвращает граф вовсе. Частичный граф, например только для успешно разобранных файлов, не выдаётся как результат. Неподдерживаемый синтаксис нельзя молча пропускать.

Целостность оценивается на выбранной пользователем стадии обработки: остановка после парсинга допустима, как и ранее согласованные неразрешённые ссылки. Эти состояния не равнозначны неполному результату из-за ошибки. При невозможности построить целый валидный граф функция чтения выбрасывает специальное исключение с диагностикой и не возвращает граф. Для ошибки в исходном тексте диагностика содержит имя файла, строку, столбец и понятное описание причины. Сбор нескольких ошибок и точный Java API исключения пока не согласованы.

### Неизменяемость и билдеры

Целевая модель — неизменяемый граф и специальные изменяемые билдеры для его построения. Билдер может находиться в промежуточном невалидном состоянии. Готовый граф невалидным быть не может: создание графа из невалидного состояния билдера не должно выдавать невалидный граф. Конкретный способ сообщения об ошибках построения пока не выбран.

Предусматриваются два отдельных набора классов:

- классы неизменяемого графа со всеми его ссылками;
- классы изменяемого состояния, представляющие тот же граф и предоставляющие специальные методы добавления узлов, изменения ссылок и других изменений структуры.

Из неизменяемого графа можно получить изменяемое состояние, выполнить в нём множество изменений, а затем снова получить неизменяемый граф. Изменяемое состояние — представление всего графа, а не только набор изолированных билдеров узлов. Получать неизменяемый граф после каждой отдельной правки не требуется.

Уже выданный неизменяемый граф и его ссылки остаются нетронутыми. Все разрешённые ссылки результирующего неизменяемого графа должны вести на узлы, входящие в этот же граф. Если объявление заменено, ссылки его использований в результате должны вести на новое объявление. Переиспользование неизменяемых узлов между версиями допускается, если соблюдены эти требования; конкретный механизм копирования не выбран.

Специальный метод замены узла в изменяемом состоянии автоматически перенаправляет все входящие ссылки со старого узла на новый. Алгоритм, выполняющий замену, не обязан вручную обходить использования узла и обновлять их ссылки. Например, при замене объявления переменной её использования начинают ссылаться на новое объявление.

Удаление узла, на который остаются дополнительные входящие ссылки, запрещено. Сначала вызывающий алгоритм должен явно обработать эти ссылки. Автоматически превращать их в неразрешённые при удалении нельзя. Этот запрет относится к дополнительным референсам, а не к самому факту включения узла в синтаксическое дерево. Правила удаления поддерева и обязательных структурных детей пока не определены.

Ранее разрешённые неразрешённые ссылки сами по себе не делают граф невалидным. Остальные инварианты валидности, API изменяемого состояния и билдеров, поведение при несовместимой замене, удалении поддерева и обязательных структурных детей, а также внутренняя реализация перенаправления ссылок предстоит определить.

### Стадии обработки и «озеленение»

Обработка программы состоит из множества стадий/проходов, каждый из которых решает свою задачу. Она не ограничивается только парсингом и заполнением ссылок.

Сначала строятся исходные узлы в соответствии с распознанными конструкциями. Затем отдельный алгоритм «озеленения» обходит результирующее дерево и заменяет некоторые комбинации узлов другими, общими узлами. В частности, исходные конструкции консольного вывода в Java и C++ после такого прохода превращаются в один общий узел вывода.

Это отдельное преобразование дерева, а не обязательная нормализация непосредственно внутри парсера.

Пользователь библиотеки управляет выполнением проходов и получением промежуточного результата через параметры функции, которая читает источник и возвращает граф. Можно получить результат после парсинга, заполнения ссылок или «озеленения», остановившись на нужной стадии. Конкретный формат параметров пока не выбран; произвольная перестановка проходов этим решением не разрешается.

Полный перечень проходов, их зависимости и порядок, а также правила обновления ссылок при замене узлов пока не согласованы.

## 4. Реализация и открытость

- Язык реализации проекта и собственного парсера — Java 21.
- Система сборки — Maven.
- Парсер реализуется вручную; генерация парсера из грамматики сторонним генератором не применяется.
- Лицензия проекта — MIT.
- Результат проекта — монолитная Java-библиотека.
- Maven-координаты: `groupId = com.kniazkov`, `artifactId = cpg` (`com.kniazkov:cpg`).
- Базовый Java-пакет — `com.kniazkov.cpg`.
- Начальная версия пока не определена.
- В начале каждого файла должен быть краткий заголовок.
- JavaDoc пишется на английском, кратко и по делу, без избыточного документирования.
- Допустимые зависимости и детали упаковки пока не определены.
- Повторное использование компонентов Astranaut пока не согласовано; его прежние архитектурные решения автоматически сюда не переносятся.

## 5. Порядок работы

1. Требования ведутся на русском языке в этом репозитории.
2. Вопросы задаются заказчику по одному. Ответы могут быть подробными.
3. Каждый полученный ответ сразу фиксируется в репозитории и учитывается в актуальных требованиях.
4. После согласования достаточного количества вопросов создаётся прототип. Его объём и критерии готовности необходимо определить в ходе обсуждения.
5. Несогласованные предложения не считаются принятыми требованиями.

## 7. Обсуждение

### Вопрос 1. Назначение графа

Какую конкретную практическую задачу должен решать потребитель построенного графа? Нужен пример: какой исходный код он получает и какой результат должен выдать с помощью графа.

Ответ заказчика: «Статический анализ и оптимизация кода».

Принято: граф предназначен для статического анализа и оптимизации кода. Конкретные алгоритмы и необходимость генерации изменённого исходного кода этим ответом не определены.

### Вопрос 2. Результат оптимизации

Нужно ли по изменённому графу получать оптимизированный исходный код на исходном языке, или достаточно графа и рекомендаций, а применение изменений выполняет внешний инструмент?

Ответ заказчика: «Да, должен. Узлы должны иметь методы для превращения дерева в исходный код, причем на нескольких языках. Человеко-читаемый, с отступами. Важно: форматирование кода можно не сохранять, то есть из дерева может получиться новый код, не похожий на старый».

Принято: методы узлов обеспечивают генерацию человекочитаемого исходного кода на нескольких языках; отступы обязательны, сохранение исходного форматирования не требуется.

### Вопрос 3. Границы межъязыковой генерации

Если конструкцию нельзя непосредственно выразить на выбранном целевом языке (например, арифметику указателей C — в Java), допустимо ли явно отказать в генерации с диагностикой, поддерживая межъязыковую генерацию только для согласованного общего подмножества?

Ответ заказчика:

> Узлы графа делятся на две части:
>
> - «зелёные» — которые подходят для всего подмножества языков;
> - «красные» — которые подходят только для определённого языка или языков.
>
> Полностью «зелёное» дерево может давать исходник на любом языке. Дерево с «красными» узлами — только на определённом языке.

Принято: разделение узлов на «зелёные» и «красные» и соответствующие ограничения генерации. Конкретный механизм отказа с диагностикой этим ответом не определён.

### Вопрос 4. Совместимость «красных» узлов

Правильно ли определять доступные языки генерации как пересечение наборов языков, поддерживаемых всеми узлами дерева? Например, если один «красный» узел поддерживает C и C++, а другой — только C++, всё дерево допускает генерацию только на C++. Если пересечение пусто, генерация всего дерева невозможна ни на одном языке.

Ответ заказчика: «Да».

Принято: доступные языки генерации определяются пересечением наборов языков всех узлов дерева. При пустом пересечении генерация всего дерева невозможна ни на одном языке.

### Вопрос 5. Семантика «зелёных» узлов

Должен ли «зелёный» узел иметь единый смысл на всех поддерживаемых языках, а генераторы — сохранять этот смысл, даже если для этого нужны разные выражения или дополнительные конструкции? Например, узел целочисленного деления с округлением к нулю должен давать одинаковый результат на всех целевых языках, включая отрицательные аргументы. Это предложение для уточнения семантики, а не утверждённый состав «зелёных» узлов.

Ответ заказчика: «Достаточно получить "похожий" код. Точной трансформации из кода в код не потребуется. Зеленые узлы прежде всего нужны для того, чтобы писать какие-то общие алгоритмы».

Принято: основная цель «зелёных» узлов — общие алгоритмы. Для межъязыковой генерации достаточно похожего кода без гарантии точной семантической эквивалентности. Предложенное требование единой семантики и её точного сохранения на всех языках не принято. Требования к обратной генерации на исходном языке уточняются отдельно.

### Вопрос 6. Обратная генерация на исходном языке

Если код разобран и затем сгенерирован на том же языке без преобразований графа, требуется ли сохранить его поведение, допуская изменение форматирования? Например, C++ → граф → C++ без оптимизаций.

Ответ заказчика: «Да».

Принято: разбор и обратная генерация на том же языке без преобразований графа сохраняют поведение программы; форматирование может измениться.

### Вопрос 7. Дерево и дополнительные связи графа

Верна ли базовая модель: в основе лежит синтаксическое дерево (функции, блоки, выражения и другие конструкции), а граф получается добавлением связей между его узлами? Например, узел использования переменной связан с узлом её объявления, а узел вызова функции — с узлом её объявления. Конкретный состав дополнительных связей и этапы их построения будут согласованы отдельно.

Ответ заказчика: «Да. В узлы добавляются конкретные референсы, которые потом могут использоваться».

Принято: основа — синтаксическое дерево; дополнительные связи графа представлены конкретными ссылками в узлах, доступными для последующего использования.

### Вопрос 8. Этап заполнения ссылок

Разделяем ли построение на два этапа: парсер строит синтаксическое дерево, затем отдельный проход разрешает имена и заполняет ссылки на объявления? Например, вызов функции можно разобрать раньше её объявления, а ссылку заполнить после разбора. Вопрос касается построения итоговых ссылок; необходимость вспомогательной информации об именах во время самого разбора пока не определяется.

Ответ заказчика: «Да. Причем чем "зеленее" будут эти алгоритмы, то есть чем пригоднее для разных языков, тем лучше».

Принято: ссылки заполняются отдельным проходом после построения дерева парсером. Приоритет — алгоритмы, максимально пригодные для разных языков.

### Вопрос 9. Неразрешённые ссылки

Допустим ли граф с неразрешёнными ссылками, если целевое объявление найти не удалось (например, функция находится во внешней библиотеке, исходников которой нет)? Предложение: сохранять узел и имя, явно отмечать, что ссылка не разрешена, и позволять дальнейшим алгоритмам работать с доступной информацией.

Ответ заказчика: «Да, конечно».

Принято: граф с неразрешёнными ссылками допустим; узел и имя сохраняются, отсутствие разрешённой ссылки явно обозначается, последующие алгоритмы могут работать с доступной информацией.

### Вопрос 10. Способ реализации парсера

Требование «собственный парсер, целиком написанный на Java» означает ручную реализацию разбора на Java или допускает генератор парсеров (например, ANTLR), который по нашей грамматике создаёт Java-код? Выбор влияет на способ добавления языковых надстроек.

Ответ заказчика: «Вручную на Java».

Принято: собственный парсер пишется вручную на Java; вариант с генератором парсеров не принимается. Это решение само по себе не запрещает прочие вспомогательные Java-библиотеки.

### Вопрос 11. Подключение языковой надстройки

Должна ли надстройка подключаться отдельным Java-модулем, который переиспользует базовый парсер и добавляет либо переопределяет отдельные правила разбора без изменения исходников базового парсера? Например, модуль AscendC расширяет парсер C++ своими конструкциями. Конкретный механизм расширения (наследование, регистрация обработчиков и другие варианты) этим вопросом не выбирается.

Ответ заказчика: «Нет, мы будем править код прямо здесь, получая монолитную либу».

Принято: надстройки добавляются изменением кода непосредственно в репозитории; результат — монолитная Java-библиотека. Предложение об отдельных подключаемых модулях без изменения базового парсера отклонено. Конкретная внутренняя организация кода этим решением не задаётся.

### Вопрос 12. Языки первого прототипа

С каких языков начинаем первый прототип? Варианты для обсуждения: небольшие подмножества C и Java, чтобы проверить общие узлы и алгоритмы на двух языках, либо C++ и минимальное расширение AscendC, чтобы сначала проверить основной корпоративный сценарий. Можно выбрать другой набор. Ни один вариант пока не принят.

Ответ заказчика: «Очень маленькие программы на C++ и Java: один класс, один метод main, вычисление чего-нибудь несложного и вывод в консоль».

Принято: первый прототип ориентирован на маленькие программы на C++ и Java с одним классом, методом main, простым вычислением и выводом в консоль. Точная форма точки входа C++ уточняется отдельно, поскольку стандартная точка входа C++ — свободная функция main.

### Вопрос 13. Форма программы на C++

Для выполнения C++-программы нужна свободная функция main; метод класса сам по себе точкой входа не является. Подходит ли для прототипа класс Program со статическим методом main и маленькая свободная функция main, вызывающая Program::main()? В Java при этом используется обычный public static void main(String[] args) внутри класса.

Ответ заказчика: «Да, все подходит».

Принято: в C++ используется класс Program со статическим методом main и свободная функция main, вызывающая Program::main() и возвращающая 0. В Java — обычный public static void main(String[] args) внутри класса.

### Вопрос 14. Минимальный набор вычислений

Достаточно ли для первого прототипа локальных переменных типа int, целочисленных литералов, присваивания, операций +, -, *, /, скобок и вывода результата, пока без условий и циклов? Например: int a = 2; int b = 3; int result = (a + b) * 4; затем вывод result в консоль. Способ представления консольного вывода в графе будет согласован отдельно.

Ответ заказчика: «Да, за глаза хватит».

Принято: первый прототип ограничивается локальными переменными int, целочисленными литералами, объявлениями с инициализацией, присваиванием, операциями +, -, *, /, скобками и выводом результата. Условия и циклы на этом этапе не требуются.

### Вопрос 15. Представление консольного вывода

Нужно ли сводить вывод результата в Java и C++ к общему «зелёному» узлу вывода, либо сохранять исходную структуру языковых выражений? Примеры: System.out.println(result) в Java и std::cout << result << std::endl в C++. Во втором варианте Java-вызов и C++-операторы остаются своими конструкциями, а их аргумент result и вычисляющие его выражения могут использовать общие узлы. Конкретная модель пока не выбрана.

Ответ заказчика:

> Сначала делаем некоторые оригинальные узлы так как они распознались. Потом сделаем отдельный алгоритм "озеленения", который проходит по результирующему дереву и заменяет некоторые комбинации узлов на какой-то другой узел. Так получится один узел вывода.
>
> Из всего этого мы делаем вывод - весь алгоритм будет иметь достаточно много стадий/проходов, каждый из которых реализует что-то свое.

Принято: первоначально сохраняются распознанные конструкции; отдельный проход «озеленения» заменяет комбинации узлов общими узлами, в частности общим узлом консольного вывода. Архитектура обработки предусматривает много проходов с отдельными задачами.

### Вопрос 16. Управление проходами

Должен ли пользователь библиотеки иметь возможность запускать каждый проход отдельно и получать промежуточное дерево/граф, например после парсинга, после заполнения ссылок и после «озеленения», а также остановиться на нужной стадии? Вопрос не предполагает, что любой порядок проходов обязательно допустим.

Ответ заказчика:

> Да. Это передается какими-то параметрами в функцию, которая читает источник и возвращает граф.
>
> Сбоку мне подсказывают: обязятально на первой стадии уметь читать хотя бы одну папку с исходниками, а не один файл.

Принято: управление проходами и стадией возвращаемого графа задаётся параметрами функции чтения источника. Уже в первом прототипе необходимо читать как минимум одну папку с исходниками, а не ограничиваться одиночным файлом.

### Вопрос 17. Структура результата чтения папки

Представляем ли результат чтения папки одним графом с корневым узлом проекта, под которым находятся узлы исходных файлов, а внутри них — их синтаксические деревья? Ссылки между объявлениями и использованиями при этом могут соединять узлы разных файлов.

Ответ заказчика: «Да. В результате должен получиться один граф».

Принято: папка читается в единый граф с корнем проекта и узлами исходных файлов, содержащими синтаксические деревья. Дополнительные ссылки могут соединять узлы разных файлов.

### Вопрос 18. Обход вложенных папок

Нужно ли уже в первом прототипе читать исходники из вложенных папок рекурсивно? Предложение: передаётся одна корневая папка, поддерживаемые исходники ищутся в ней и во всех её подпапках; относительный путь каждого файла сохраняется в его узле. Правила исключения файлов и каталогов будут уточнены отдельно.

Ответ заказчика: «Пока нет».

Принято: в первом прототипе рекурсивного обхода нет; читаются файлы непосредственно в указанной папке. Поддержка вложенных папок отложена, а не запрещена для будущих версий. Предложение о хранении относительных путей этим ответом отдельно не утверждено.

### Вопрос 19. Изменяемость графа

Проходы должны менять существующий граф на месте или создавать новый граф, сохраняя прежний неизменным? Например, при «озеленении» заменяется комбинация узлов вывода: видят ли уже имеющиеся у пользователя ссылки на граф эти изменения, или результат нужно получить как отдельный граф? Решение должно учитывать дополнительные референсы между узлами.

Ответ заказчика: «Очень желательно сделать граф немутабельным и сделать специальные билдеры для его построения. Билдеры, соответственно, мутабельные и могут иметь невалидное состояние. Граф невалидным быть не может».

Принято как целевая модель: неизменяемый граф и изменяемые билдеры. Невалидное промежуточное состояние допускается у билдера, но не у готового графа. Уже возвращённый граф не изменяется последующими проходами. Точные инварианты и механизм построения результата уточняются отдельно.

### Вопрос 20. Согласованность ссылок после преобразования

Должны ли все разрешённые ссылки результирующего графа указывать только на узлы, входящие в этот же результирующий граф? Например, если проход заменил узел объявления переменной новым, использования переменной в новом графе должны ссылаться на новое объявление; прежний граф и его ссылки остаются неизменными. Переиспользование неизменяемого узла допустимо, если он входит и в новый граф. Детали реализации пока не выбираются.

Ответ заказчика:

> Да. Тут надо различать состояния "немутабельный граф" и "мутабельное состояние". Предполагается, что у нас будет некоторый набор классов, которые будут представлять немутабельный граф со всеми ссылками, и некоторый другой набор классов, который будет представлять тот же граф, только там можно делать все, что угодно - добавлять узлы, менять ссылки и т.д, причем будут специальные методы для этого. После того, как многократные изменения будут сделаны, можно бужет снова получить немутабельный граф.

Принято: два отдельных набора классов для неизменяемого графа и изменяемого состояния всего графа. Специальные методы изменяемой модели позволяют многократно менять узлы и ссылки до получения нового неизменяемого графа. Старый граф не изменяется; разрешённые ссылки нового графа ведут на входящие в него узлы.

### Вопрос 21. Замена узла и входящие ссылки

Должен ли специальный метод замены узла в изменяемом состоянии автоматически перенаправлять все входящие ссылки со старого узла на новый? Например, при замене объявления переменной его использования начинают ссылаться на замену без ручного обхода со стороны алгоритма. Альтернатива — алгоритм сам явно обновляет эти ссылки. Поведение при несовместимой замене и удалении узла уточняется отдельно.

Ответ заказчика: «Да».

Принято: метод замены узла в изменяемом состоянии автоматически перенаправляет все входящие ссылки на новый узел; ручное обновление ссылок вызывающим алгоритмом не требуется.

### Вопрос 22. Удаление узла со входящими ссылками

При удалении объявления, на которое ещё есть ссылки, должны ли его использования сохраняться, а ссылки автоматически переходить в неразрешённое состояние с сохранением имени? Например, удалено объявление переменной x, но выражение x + 1 осталось. Альтернатива — не выполнять удаление, пока вызывающий алгоритм явно не обработает входящие ссылки. Правила удаления обязательных структурных детей этим вопросом не определяются.

Ответ заказчика: «Запрещаем удаление».

Принято: удаление узла с дополнительными входящими ссылками запрещено, пока алгоритм явно не обработает эти ссылки. Автоматический перевод входящих ссылок в неразрешённое состояние при удалении не выполняется.

### Вопрос 23. Оптимизация в первом прототипе
