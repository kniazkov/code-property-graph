# Модель графа и анализ программ

[English version](model-guide.en.md) · [README](../README.md)

Этот справочник описывает публичный API и грамматику, реализованные на 5 ноября 2026 года. Примеры рассчитаны на Java 21. При добавлении конструкции обновляй обе версии справочника, таблицу покрытия в конце и соответствующий тест парсера или CLI.

## Получить снимок проекта

```java
import com.kniazkov.cpg.Cpg;
import com.kniazkov.cpg.model.*;
import java.nio.file.Path;
import java.util.*;

// Внутри метода, при запуске из корня репозитория
Project project = Cpg.read(Path.of("examples/unread-write/java"),
        new Cpg.Options(Language.JAVA, Cpg.Stage.RESOLVED));
SourceFile file = project.files().getFirst();
```

Пример читает папку с программой, где первое значение переменной `score` перезаписывается до чтения. Чтение папки нерекурсивное, на запуск выбирается один язык. Файлы обрабатываются в порядке имён. Строгий вход `Cpg.read` при ошибке разбора даёт `parser.ParseException` с именем файла, строкой и столбцом. Успешный строгий вызов возвращает целый неизменяемый проект. Для диагностического снимка повреждённого C++03 предусмотрен отдельный [API с восстановлением](#восстановление-парсера-и-диагностический-экспорт-21).

| Стадия | Какой снимок получишь |
|---|---|
| `PARSED` | Исходное синтаксическое дерево с позициями. `Exit` уже существует. Разрешение имён и анализ ещё не запускались. |
| `RESOLVED` | Разрешённые имена и вызовы, CFG, DFG и диагностика исходных конструкций. Эту стадию удобно выбирать для исследования исходника. |
| `GREEN` | После разрешения имён консольный вывод заменён на `PrintStatement`. Написанные типы C++ получают семантические описания по профилю, сохраняя исходное написание. Потоки и предупреждения описывают получившееся дерево. |
| `FOLDED` | Дополнительно свёрнута безопасная константная арифметика. Потоки и предупреждения вычислены для итогового дерева. Стадия CLI по умолчанию. |

## Структура и свойства узла

Корень `Project` владеет списком `files()` и несинтаксическим деревом конфигурации `externalInputs()` (см. #19 ниже). Каждый `SourceFile` хранит путь, язык и упорядоченные элементы `items()`. Ниже находятся объявления (`Declaration`), инструкции (`Statement`), выражения (`Expression`) и записи типов (`TypeNode`). Это отдельные ветви общей иерархии `Node`.

| API | Назначение и пример |
|---|---|
| Именованные геттеры | `BinaryExpression.left()/right()` дают операнды, `VariableDeclaration.name()` — имя, `initializer()` — возможный инициализатор. `BlockStatement.items()` содержит объявления и инструкции в порядке исходника. |
| `children()` | Неизменяемый упорядоченный список детей. У листа он пуст. Для функции или метода последним ребёнком всегда идёт её собственный `exit()`. |
| `references()` | Разрешённые ссылки на другие узлы снимка. У `NameExpression` и `CallExpression` конкретную цель удобнее читать через `target()`. Для внешнего или неоднозначного имени цель может отсутствовать. |
| `range()` | `Optional<SourceRange>` даёт полный путь и полуоткрытый интервал исходника. Строки и столбцы с 1, смещения с 0. Столбцы и смещения в единицах UTF-16. У синтетического `Exit` диапазона нет. Свёрнутый литерал сохраняет диапазон исходного выражения. |
| `languages()`, `source(target)` | Допустимые языки непосредственной генерации поддерева и его текст. Для целых выходных файлов и адаптации точек входа используй `Cpg.sources(project, target)`. |
| `diagnostics()` | Неизменяемый список замечаний к конкретному узлу. Пустой список означает отсутствие прикреплённых замечаний на выбранной стадии. |

Обязательный ребёнок доступен напрямую. У необязательного ребёнка тип результата — `Optional`, у повторяющихся элементов — список. Например, выражение в `return x;` доступно через `ReturnStatement.value()`, а `return;` даёт `Optional.empty()`.

```java
project.walk(new NodeVisitor() {
    @Override public void visit(VariableDeclaration variable) {
        String type = variable.type()
                .filter(NamedType.class::isInstance)
                .map(NamedType.class::cast).map(NamedType::name).orElse("?");
        System.out.println(type + " " + variable.name());
    }
});
```

`accept(visitor)` вызывает обработчик одного узла. `walk(visitor)` проходит дерево в глубину, посещая родителя перед детьми. Обработчик семейства, например `visit(BinaryExpression)`, получает и сложение, и вычитание, если их перегрузки не переопределены. Обход дерева не следует по ссылкам на объявления или по рёбрам потоков.

## Обход CFG и DFG

Оба набора рёбер находятся в `project.flows()`. Каждый `FunctionFlow` описывает одну функцию или метод с телом. `entry()` возвращает объявление, а `exit()` — тот же объект, что и `entry().exit()`. Границы функций не пересекаются. Рекурсивный вызов может ссылаться на объявление функции через `CallExpression.target()`.

**CFG. Какие инструкции могут исполниться следующими?** У ребра `control()` есть `from()`, `to()` и `kind()`. Виды — `ENTRY`, `NEXT`, `TRUE`, `FALSE`, `BACK`, `RETURN`. Для ветвления вершиной служит выражение условия. Из `return` переход ведёт к общему выходу. Недостижимая инструкция остаётся в дереве, но в CFG к ней нет пути от входа.

```java
for (FunctionFlow flow : project.flows()) {
    Map<FlowVertex, List<FunctionFlow.ControlEdge>> outgoing = new IdentityHashMap<>();
    for (var edge : flow.control())
        outgoing.computeIfAbsent(edge.from(), v -> new ArrayList<>()).add(edge);

    Set<FlowVertex> seen = Collections.newSetFromMap(new IdentityHashMap<>());
    Deque<FlowVertex> pending = new ArrayDeque<>();
    pending.add(flow.entry());
    while (!pending.isEmpty()) {
        FlowVertex current = pending.removeFirst();
        if (!seen.add(current)) continue;
        for (var edge : outgoing.getOrDefault(current, List.of())) {
            System.out.println(current.getClass().getSimpleName() + " --" + edge.kind()
                    + "--> " + edge.to().getClass().getSimpleName());
            pending.addLast(edge.to());
        }
    }
}
```

Множество посещённых вершин позволяет закончить обход даже при обратном ребре цикла. Для обратного обхода индексируй по `to()`, начни с `exit()` и переходи к `from()`.

**DFG. Что даёт значение этому чтению?** Ребро `VALUE` направлено от значения операнда к потребителю, например от литерала к инициализируемой переменной. Ребро `DEFINITION` идёт от конкретной записи к чтению имени. В примере с `score` у чтения при выводе `target()` указывает на объявление `int score = 1;`, а входящее `DEFINITION` — от присваивания `score = 2`.

```java
for (FunctionFlow flow : project.flows()) {
    Map<Node, List<Node>> writesForRead = new IdentityHashMap<>();
    for (var edge : flow.data()) {
        if (edge.kind() == FunctionFlow.Dependency.DEFINITION)
            writesForRead.computeIfAbsent(edge.to(), n -> new ArrayList<>()).add(edge.from());
    }
    flow.entry().walk(new NodeVisitor() {
        @Override public void visit(NameExpression use) {
            for (Node write : writesForRead.getOrDefault(use, List.of()))
                System.out.println(use.name() + " <- " + write.getClass().getSimpleName()
                        + " " + write.range());
        }
    });
}
```

После слияния ветвей возможны несколько записей для одного чтения. Обратное ребро цикла может принести запись с предыдущей итерации. Чтобы найти все зависимые значения, используй тот же обход с очередью, что и для CFG, но построй индекс по `from()` из `flow.data()` и начни с интересующего узла. Для поиска всех источников результата разверни направление. Сравнивай узлы по идентичности внутри одного снимка.

Следующий фрагмент для каждого присваивания считает другие узлы, достижимые по исходящим рёбрам DFG обоих видов. В программе со `score` путь от второй записи проходит через чтение имени к вызову вывода.

```java
for (FunctionFlow flow : project.flows()) {
    Map<Node, List<Node>> consumers = new IdentityHashMap<>();
    for (var edge : flow.data())
        consumers.computeIfAbsent(edge.from(), n -> new ArrayList<>()).add(edge.to());

    flow.entry().walk(new NodeVisitor() {
        @Override public void visit(AssignmentExpression write) {
            Set<Node> reached = Collections.newSetFromMap(new IdentityHashMap<>());
            Deque<Node> queue = new ArrayDeque<>();
            queue.add(write);
            while (!queue.isEmpty()) {
                Node producer = queue.removeFirst();
                if (!reached.add(producer)) continue;
                for (Node consumer : consumers.getOrDefault(producer, List.of()))
                    queue.addLast(consumer);
            }
            System.out.println(write.range() + " -> " + (reached.size() - 1));
        }
    });
}
```

## Результаты проходов и редактирование

Данные проходов доступны через типизированные методы. Разрешение имён заполняет `target()`, анализ потоков — `Project.flows()`, диагностический проход — `Node.diagnostics()`. Нормализация и свёртка меняют само дерево: например, вместо вызова вывода появляется `PrintStatement`.

```java
project.walk(new NodeVisitor() {
    @Override public void visit(Node n) {
        for (Diagnostic d : n.diagnostics()) {
            String location = n.range().map(r -> r.file() + ":" + r.start().line()
                    + ":" + r.start().column()).orElse("?");
            System.out.println(location + " " + d.severity() + " [" + d.code() + "] " + d.message());
        }
    }
});
```

Правило `unread-write` ставит `WARNING` на конкретную инициализацию или присваивание, если значение не достигает чтения. В примере предупреждение относится к первой записи `score`. Для автоматизации используй стабильный `code()`, для человека — `message()`. В JSON диагностике соответствуют `code` и `severity`, а исходящие рёбра в `edges` содержат вид и числовой ID цели. ID назначаются при экспорте конкретного дерева; в Java API используются прямые ссылки.

Узел создаётся через вложенный строитель: `IntegerLiteral.create().setValue(2).build()`. Для правки вызывай `edit()`, меняй строитель и получай новый снимок через `build()`. После правки всего проекта прежние потоки и предупреждения сбрасываются. Если изменения затронули имена, снова разреши их; затем вычисли анализ для нового снимка. Например:

```java
Project edited = project.edit().build();
Project resolved = com.kniazkov.cpg.analysis.NameResolver.resolve(edited);
Project analyzed = com.kniazkov.cpg.analysis.UnreadWrites.analyze(resolved);
```

Для отдельных задач есть `ControlFlow.analyze` и `DataFlow.analyze`; перед DFG нужны разрешённые имена. `UnreadWrites.analyze` строит необходимый DFG. Все эти проходы возвращают результат; дальнейшие запросы делай к возвращённому проекту.

## Какие конструкции читаются из исходника

Таблица описывает штатный вход через `Cpg.read`. Наличие Java-класса в модели само по себе не означает, что соответствующий токен уже распознаётся парсером.

| Конструкция | Java (`.java`) | C++ (`.cpp`) |
|---|---|---|
| Верхний уровень | `class C { … }`, `public class C { … }` | `class`/`struct`, функции, переменные, `typedef`, пространства имён, их псевдонимы, `using`, перечисления и спецификации связывания (см. #23/#24) |
| Метод класса | `public static void main(String[] args)` | `static void main()` |
| Локальные объявления | `int x = expression;` | Фундаментальные/именованные типы, рекурсивные деклараторы, объявления через запятую, классы хранения, `typedef`, перечисления и вложенные типы (см. #23/#24) |
| Литералы и арифметика | Десятичные целые в диапазоне signed 32-bit, скобки, унарные и бинарные `+`, `-`, бинарные `*`, `/` | Десятичные/восьмеричные/шестнадцатеричные целые, суффиксы `U`/`L`/`UL`, значение узла signed 32-bit; та же арифметика и `<<` |
| Запись и сравнение | `=` (включая цепочки), `== != < <= > >=` | То же; `sizeof` типа/выражения с консервативными сведениями по профилю (см. #23) |
| Доступ и вызов | `obj.member`, `f(a, b)`, `C.main(args)` | `obj.member`, `f(a, b)`, `C::main()`, взятие адреса `&x`, разыменование `*p` |
| Управление | Блоки, `if`, `if/else`, `while`, `return;`, `return expr;` | То же |
| Комментарии и директивы | `//`, `/* … */` | Оба вида комментариев; включения, макросы и условные директивы (см. #15–#19 ниже) |
| Озеленение вывода | `System.out.println(x)` | `std::cout << x << std::endl` |
| Повреждённый вход | Строгий отказ | Строгий `Cpg.read`; отдельный диагностический режим с `ErrorExpression` (см. #21) |

Имя параметра Java `main` произвольное. Таблица описывает разбор синтаксиса; проверка типов и семантики языка компилятору не эквивалентна. Настроенные заголовки C++ раскрываются; возможности препроцессора описаны отдельно ниже и не расширяют синтаксическую грамматику. Рекурсивные деклараторы функций, указателей и массивов описаны в #23. Конструкторы, шаблоны, общий синтаксис инициализации, индексирование массивов, строки, `for`, `break` и `continue` пока вне входной грамматики; разбор объявления не означает поддержку всех операций над его типом.

**Есть классы узлов, но ещё нет разбора из текста:** остаток `%`, правый сдвиг `>>`, логическое отрицание `!`, доступ `p->field`. Для C, Python, JavaScript и Ascend C входных парсеров пока нет. Межъязыковая генерация проверена для небольших Java/C++ программ с поддерживаемыми формами `main` и консольного вывода; границы перевода описаны в README.

## Редакция C++03 и база компиляции

`new Cpg.Options(Language.CPP, stage)` сохраняет прежний C++03 по умолчанию.
Третий аргумент `"c++03"` означает явное переопределение, `null` — его отсутствие.
Иные редакции не поддерживаются; явная неподдерживаемая редакция отвергается
даже для пустого входа. Старый `Parser.parse` совместим, четвёртый аргумент
выбирает редакцию.

`CompilationDatabase.read(path)` возвращает неизменяемый `Build` из пакета
`com.kniazkov.cpg.build`. Для импорта и разбора служит
`Cpg.readCompilationDatabase(path, options)`, для явной сборки —
`Cpg.read(build, options)`. `Build.TranslationUnit` хранит физический источник,
рабочую папку, упорядоченные пути заголовков, операции определения/отмены
макросов и редакцию команды. `PhysicalSource`, `TranslationUnit` и
`IncludeInstance` разделяют физический файл, контекст единицы и отдельное
включение. Это входные записи, а не узлы синтаксиса. Обработка настроенных
заголовков и раскрытие макросов описаны ниже; #23 добавляет профиль платформы
для каждой единицы.

Приоритет редакции: явный API/CLI, последний `-std` записи, затем C++03.
Запись C++11 без переопределения сообщает файл и редакцию. Явный C++03 не
разрешает лямбды. `arguments` важнее `command`; кавычки команды разбираются
без запуска оболочки, подстановок или чтения response-файлов. Слитные и
раздельные `-I`, `-isystem`, `-iquote`, `-D`, `-U`, `-std` сохраняют порядок.
Неподдержанные ключи отвергаются с именем файла; только явно известные флаги
вывода, зависимостей и диагностики могут игнорироваться.

Относительная `directory` считается от папки базы, `file` и пути заголовков —
от рабочей папки записи. Текущая папка процесса на них не влияет. CLI принимает
`--compile-commands FILE` вместо `--input DIR` и необязательный
`--cpp-standard c++03`. [Команды и тесты](../src/test/resources/cpp03/compilation-database/README.md).

## Фазы лексики C++03 и физические позиции

`CppLexer.scan(file, source)` возвращает неизменяемый `Result`: логический
`text()` после фазы 3, `tokens()`, отображение каждого логического символа
`characterRanges()` и физический `eof()`. Вход — декодированная Java String;
смещения и колонки считаются в UTF-16. CRLF/CR становятся логическим переводом
строки. Триграфы заменяются до однопроходной склейки backslash-newline.
Комментарий заменяется одним пробелом и не склеивает соседние токены.
Внутренние физические переводы строк блочного комментария не завершают
логическую директиву; строчный комментарий заканчивается следующим логическим
переводом строки уже после склейки.

`PreprocessingToken` хранит вид, исходное логическое `spelling()`, отдельное
`canonicalSpelling()`, физический диапазон и полуоткрытые логические смещения.
Пробелы, переводы строк и EOF сохранены явно для препроцессора.
Диапазон склеенного токена охватывает исходные физические фрагменты, а
посимвольное отображение показывает сохранённые символы. Триграф отображается
на три исходных символа, пробел вместо комментария — на весь комментарий.

Различаются идентификаторы/UCN, preprocessing numbers, обычные/широкие
символьные и строковые литералы, имена заголовков, операторы и прочие символы.
Написание диграфов и альтернативных операторов сохраняется отдельно от формы
для парсера. Репертуар идентификаторов взят из приложения E C++03, а не из
современных категорий Java. Максимальное поглощение использует e/E со знаком
в pp-number; современные правила p/P, исключение `<::` и разбиение `>>` для
шаблонов не добавлены. Имена заголовков выделяются только в контексте include.
Незакрытые литералы, комментарии и заголовки сообщают физические позиции.

Лексика Java не изменена. Парсер C++ получает новый поток токенов, но его
поддерживаемый синтаксис остаётся меньше лексического репертуара. Наличие
токена ещё не означает вычисление литерала, поддержку всех выражений,
раскрытие заголовков или макросов. [Положительная приёмка](../src/test/resources/cpp03/lexical-phases/README.md),
[отрицательный литерал](../src/test/resources/cpp03/unterminated-literal/README.md).

## Включение заголовков и раскрытие макросов (C++03 #15)

`CppPreprocessor.preprocess(Build.TranslationUnit, source)` применяет упорядоченные `-D`/`-U` независимо для каждой единицы и выполняет лексические фазы для каждого физического заголовка. Объектные и функциональные макросы поддерживают пустое замещение, вложенные скобки аргументов, предварительное раскрытие аргументов, повторное сканирование с подавлением рекурсии, строкификацию `#` и склейку `##` исходных токенов. Результат склейки должен быть одним preprocessing token. Пустые фактические аргументы имеют неопределённое поведение в C++03 и диагностируются; вызов действительно беспараметрического `F()` и аргументы, ставшие пустыми после раскрытия, поддерживаются.

Для кавычек поиск идёт от каталога включающего файла через `-iquote`, `-I`, `-isystem`; для угловых скобок — `-I`, `-isystem`. Имя включения может получаться из макроса. Условные группы и полноценные выражения препроцессора описаны в разделе #19 ниже. Повторное включение выполняется в текущем контексте макросов, отсутствующий файл даёт всю цепочку включений. Только ранее моделируемый `<iostream>` остаётся непрозрачным при отсутствии настроенного файла. Другие отсутствующие системные заголовки дают ошибку. Глубина включений и объём раскрытия ограничены с диагностикой.

Парсер получает единый активный поток с физическими именами файлов и основными диапазонами раскрытия. Результат препроцессора содержит диапазоны написания и раскрытия, происхождение макросов и идентичность включений; перенос этого слоя в граф/JSON/SVG описан ниже в разделе #16. Сохранение вызовов макросов при генерации описано ниже в разделе #17. Минимальные объявления/определения `int name()` без аргументов нужны для двух единиц SQUARE; полная семантика функций и межфайловый поиск не заявляются. Границы проверяют `CppPreprocessorTest`, `PreprocessorIT` и сценарии `square`, `macros`, `missing-header`.

## API, JSON и SVG происхождения макросов (#16)

`Node.provenance()` возвращает необязательный `TokenProvenance`: полуоткрытый интервал итоговых токенов и неизменяемую запись единицы `Preprocessing`. `tokens()` даёт диапазоны написания/раскрытия, ID включений и событий; `expansions()` отдельно ведёт к событиям. `SourceFile.provenance().unit()` сохраняет все события, включая макросы без AST. Записи препроцессора не являются синтаксическими детьми или разрешёнными ссылками. Обычный Visitor также обходит принадлежащие проекту внешние узлы конфигурации, добавленные в #19. Edit/build копирует неизменяемые записи; результаты анализа сохраняют прежние правила устаревания.

Событие содержит уникальный в единице ID, действовавшее определение и фрагменты замещения, полный диапазон вызова, исходные аргументы, родителя, участников #/## и полуоткрытые границы итоговых токенов. Повторно использованный предварительно раскрытый аргумент сохраняет одно событие и может дать несколько участков вывода: общий интервал охватывает их, а ID на каждом токене задают точную принадлежность. Пустые события имеют равные границы. Включения различаются по экземпляру. Происхождение сохраняется отдельно; генерация проверяет возможность оставить неизменённый вызов макроса.

JSON хранит `preprocessing` один раз у SourceFile; `provenance.sourceFileId` узла задаёт область интервала и `expansionIds`. Все диапазоны содержат физический `file`. ID событий детерминированы для тех же входов и независимы между единицами; раскрытые дата/время дополнительно зависят от сохранённого момента трансляции. SVG показывает фиолетовые пунктирные рёбра к событию, родителю, вызову, определению, оператору, аргументу и участникам #/##. Слой включён по умолчанию; отключение: `DotVisualizer.toDot(root, false)`, `renderSvg(root, path, false)` или CLI `--provenance off`.

[Команды и ожидаемые фрагменты](../src/test/resources/cpp03/provenance/README.md): SQUARE(a) даёт два чтения и один аргумент, NEST(f()) — два вызова и один аргумент, '*' ведёт к заголовку. Отдельно проверены частичное выражение, несколько инструкций и пустое замещение. Полное происхождение после произвольных преобразований относится к последующим задачам истории.

Определения из командной строки используют явно синтетические буферы `<command-line:N>` в порядке операций. Их диапазоны относятся к нормализованному буферу определения, а не к файлу единицы; диапазоны вызовов остаются реальными. ID включения сохраняет контекст единицы трансляции.

## Правка одного раскрытия макроса (#17)

Вызовите `ProjectEditor.replace` для выбранного раскрытого операнда, затем `Cpg.sources(edited, Language.CPP)`. Свежая замена наследует недостающий диапазон и токенное происхождение; явно заданное происхождение сохраняется. Исходный снимок неизменяем. Для C++ с макросами или физическими включениями `Preprocessing.sources()` хранит исходные тексты, `configuration()` — настройки единицы. Генерация не перечитывает диск.

Редактированный синтаксис сравнивается с повторным разбором из памяти. Правка внутри макроса расширяется до представимого внешнего вызова, изменённое поддерево выводится со скобками и заменяет участок сохранённого текста. Остальные вызовы, директивы и заголовки сохраняют байты. Перед возвратом файлов весь результат препроцессируется и разбирается под отдельным виртуальным корнем вывода и сравнивается с требуемым синтаксисом. В карту файлов входят относительные пути заголовков; CLI создаёт каталоги после проверки конфликтов выходных путей. Для сборки результата нужны соответствующие флаги/база компиляции.

Область правок ограничена явно: фрагмент макроса без границы целого поддерева, структурные правки с потерей посторонних вызовов, несовместимые правки общего исходника, заголовки вне общего корня, абсолютные включения и непереносимые пути дают понятную ошибку. Неполный набор исходников не возвращается. Общие конфликты вариантов сборки и произвольное редактирование относятся к следующим задачам. Прежняя генерация без макросов/заголовков и межъязыковая адаптация сохраняют своё форматирование.

[Исполняемый пример публичного API](../examples/cpp03-square/README.md) заменяет только правый операнд SQUARE(a) на b: результаты 58 и 64, побайтно прежние заголовок и second.cpp, затем CLI видит a*b и c*c. Вложенный OUT(a) с заменой на b+1 сохраняет приоритет умножения и сложения. Корпус требует строгие GCC и Clang, ручная демонстрация также выполняется в CI. Это завершает первую вертикальную веху, а не весь чеклист C++03.

## Варианты единиц трансляции и составы сборок (#18)

`Build.TranslationUnit.variantId()` хеширует нормализованные физический путь, рабочий каталог, действующую редакцию, упорядоченные пути включений и операции макросов. C++03 по умолчанию и явный C++03 дают один ID; переопределение редакции согласованно меняет идентичность. Точные дубликаты конфигурации объединяются. ID стабилен для тех же абсолютных входов, но не обещает сохранность при переносе корня.

`Cpg.readCompilationDatabase` оставляет все конфигурации в одном `Project`. `build()` показывает входы, `variants(Path)` перечисляет версии, `SourceFile.variantId()` различает их. `Build.Composition(name, variantIds)` и `project.selectBuild(composition)` создают ограниченный неизменяемый снимок с новым разрешением, диагностикой и потоками. Альтернативы выбираются из исходного полного снимка. Метаданные сохраняются при edit/build и добавлении анализа. Неизвестные ID, повторный выбор и разные конфигурации одного файла в одном составе отвергаются.

`CallExpression.candidates()` показывает возможные цели, `resolution()` различает отсутствие цели, однозначность, неоднозначность и ODR-конфликт; прежний `target()` заполнен только при одной разрешённой цели. Локальный квалифицированный вызов предпочитает свою единицу, поэтому копии определения метода внутри класса из общего заголовка не создают ложный конфликт. При неизвестном составе свободная функция без локального определения получает возможные определения других единиц. Известный состав ограничивает поиск выбранными единицами и диагностирует конкурирующие определения свободной функции. Дубликаты внутри одной единицы конфликтуют даже без именованной сборки. Область [#24](#области-видимости-объявления-и-связывание-24) добавляет идентичность объявлений, внутреннее/внешнее связывание и языковое связывание C. Полный выбор перегрузки и ODR классов/шаблонов остаются последующими задачами.

JSON содержит входы сборки, необязательный состав, ID вариантов файлов, статус и ID целей вызова. Каноническая и межъязыковая генерация конкурирующих конфигураций одного физического файла требует выбрать состав. Сохраняющая исходный текст генерация C++ согласует варианты по правилам #20 ниже; CLI также может экспортировать общий граф только в JSON. [Пример SERVER/CLIENT](../examples/cpp03-builds/README.md) проверяет четыре единицы, изолированные вызовы/потоки, две возможные цели run() и две явно выбранные программы со своими флагами макросов.

## Условная компиляция, каталог и внешние входы (#19)

`#if`/`#ifdef`/`#ifndef`/`#elif`/`#else`/`#endif` выбирают единый активный поток до синтаксического разбора. Граница ветви может проходить внутри выражения или объявления. Неактивный текст не создаёт AST, CFG, DFG или синтаксических диагностик, не раскрывает макросы и не открывает заголовки. Фазы лексики всё равно выполняются: незакрытый комментарий ошибочен и в пропущенной ветви. Вложенность директив проверяется; условия под неактивным родителем и последующие ветви после уже выбранной не вычисляются.

Неизменяемый каталог доступен через `file.provenance().orElseThrow().unit()`:

- `definitions()` перечисляет все выполненные определения, включая неиспользованные и впоследствии отменённые. Поля: `id`, `name`, `functionLike`, `parameters`, `rawReplacement`, физический `range`, `includeId`, `originKind`, `sourceKey`. В тексте замещения сохраняются внутренние пробелы и комментарии. Новое определение после `#undef` получает отдельный ID. Для перехода к раскрытиям отфильтровать `expansions()` по `definitionId()`.
- `includeStates()` хранит карту действующих имён в ID определений **после завершения каждого вхождения заголовка**, включая корневой файл. Это всё видимое окружение в данной точке, а не только определения самого заголовка. ID разрешаются через `definitions()`; фильтр по `includeId` определения выделяет определения из конкретного вхождения. Произвольный запрос состояния макросов на любой момент этим API не предоставляется.
- `presenceChecks()` хранит обработанные `#ifdef`, `#ifndef` и `defined` отдельно от раскрытия значений. `present` означает наличие определения, `conditionResult` учитывает отрицание у `#ifndef`. Для `defined` это результат самого оператора, не всего выражения `#if`. При отсутствии определения `definitionId` равен null; `branchId` указывает ветвь. `-DDEBUG=0` делает `#ifdef DEBUG` истинным без события раскрытия. Пропущенное вложенное условие не создаёт проверку. Все операнды `defined` обрабатываемой директивы записываются до вычисления выражения, даже в операнде, который затем пропускается при коротком замыкании.
- `branches()` сохраняет `directive`, физический `directiveRange`, `rawSource`/`range`, ID родителя/вхождения, `parentActive`, `evaluated`, `conditionResult`, `active` и полуоткрытые границы итоговых токенов. Исходный текст ветви включает открывающую директиву и заканчивается перед следующей соседней директивой либо закрывающим `#endif`; внешняя ветвь может включать вложенные группы. `directives()` сохраняет текст директив, включая закрывающий `#endif`, пустые директивы и игнорируемые pragma. Вариант сборки доступен через `configuration().variantId()`.

`Project.externalInputs()` владеет деревом `ExternalInput` с полями `key`, `role`, `text`, `inputs()`. Узлы имеют строители, обходятся через `children()`/`NodeVisitor` и сохраняются при редактировании снимка, даже если исходник на них не ссылается. Путь для базы: проект → файл базы компиляции → запись команды → аргумент макроса. Сохраняется точный аргумент, например `-DDEBUG=0`; у раздельных аргументов операнд сохранён отдельно. Корни конфигурации Java API и CLI различаются; встроенные макросы принадлежат профилю C++03. `project.externalInput(definition.sourceKey())` находит реальный узел текущего снимка для внешнего определения. У определения в исходнике остаются физический ключ файла/диапазон, отдельный внешний узел ему не нужен.

JSON добавляет `externalInputs` проекту и массивы каталога в `preprocessing` каждого файла. У определения есть обратные `expansionIds`/`presenceCheckIds`, а у внешнего определения также `sourceNodeId`; раскрытие/проверка хранит `definitionId`, ветвь — `variantId`. Вариант проверки определяется через файл/ветвь без дублирования поля. SVG добавляет связи каталога, ветвей, проверок и источников конфигурации в отключаемый слой происхождения. Сравнение API/CLI проверяет эквивалентные синтаксис, анализы и эффективный препроцессинг, но происхождение непосредственного ввода API и CLI намеренно отличается (`java-api` и `cli`): полный JSON для разных способов задания входов не обязан совпадать побайтно.

`#line` раскрывает макросы в аргументах, принимает номер 1–32767 и необязательное обычное строковое имя файла. Последующие логические координаты меняются, физические диапазоны — нет. `logicalLocations()` хранит отображение для каждого вхождения. `__FILE__`/`__LINE__` используют логическую позицию вызова; `__cplusplus` раскрывается в `199711L`, `__DATE__`/`__TIME__` используют один сохранённый момент начала трансляции в UTC. Перегрузка препроцессора с `Instant` обеспечивает воспроизводимость; повторная обработка при генерации сохраняет этот момент. У динамических встроенных определений `rawReplacement` пуст, вычисленное значение находится в раскрытии/потоке токенов. Профиль оставляет `__STDC__` неопределённым. Активный `#error` даёт ошибку, пустая директива допустима, все pragma сохраняются и игнорируются, включая `#pragma once`. Переопределение/отмена зарезервированных имён и полученный из раскрытия `defined` диагностируются вместо назначения смысла неопределённому поведению C++03.

Вычислитель условий отделён от более узкого синтаксического парсера. Поддерживаются основания целых и суффиксы `U`/`L` C++03, обычные/широкие символьные константы, `true`/`false`, унарные операции, арифметика, сдвиги, сравнения, побитовые/логические операции и `?:` с приоритетами и коротким замыканием. Оставшиеся имена/ключевые слова заменяются нулём, кроме булевых литералов и альтернативных операторов. Пропущенные операнды всё равно проверяются синтаксически. Вещественные, `LL`/двоичные литералы, приведения, вызовы, присваивания и выражения с запятой отвергаются.

С #23 зависящие от реализации решения берутся из эффективного [профиля платформы](#профили-платформы-и-рекурсивные-деклараторы-23), а не у компилятора системы. Знаковые/беззнаковые вычисления препроцессора используют ширину `long` профиля (по умолчанию 64 бита); беззнаковая арифметика циклическая, знаковое деление округляет к нулю, знаковый сдвиг вправо сохраняет знак, сдвиг влево оставляет младшие биты целевой ширины. Вычисляемое знаковое арифметическое переполнение, деление на ноль и величина сдвига вне этой ширины диагностируются. Обычные символьные константы упаковывают байты `executionEncoding` в позиции целевых байтов; числовые escape сохраняют младший целевой байт. Каждый упакованный октет неотрицателен независимо от знаковости простого `char`; полное упакованное значение сохраняет младшие биты `long`. Широкие константы используют знаковость/ширину `wcharType` и последнюю кодовую единицу UTF-16 либо скаляр Unicode UTF-32 согласно `wideExecutionEncoding`. Многосимвольная упаковка остаётся явным решением реализации, а не обещанием совпадения с любым нативным компилятором. Полная семантика литералов и преобразований обычных выражений относится к #25.

Неизменённый условный исходник генерируется побайтно, включая неактивные фрагменты. Приёмку задают `CppConditionalExpressionTest`, `CppPreprocessorTest`, `ConditionalCatalogModelTest`, `ConditionalCatalogIT` и обязательный [сценарий conditional-catalog](../src/test/resources/cpp03/conditional-catalog/README.md). Правка активной ветви с проверкой всех альтернативных сборок и конфликтов общего исходника описана в #20 ниже.

## Общие заголовки нескольких конфигураций (#20)

Для вывода единого физического дерева передайте полный набор вариантов в `Cpg.sources(edited, Language.CPP)`. Для C++ со сохранёнными входами препроцессора генерация согласует физические правки до возврата файлов. Вариант с неизменённым активным фрагментом всё ещё требует исходный текст. Поэтому замена общего литерала в `return 1;` на `2` только для SERVER конфликтует с неизменённым вхождением CLIENT. Диагностика указывает физический файл/диапазон, ID и настройки затронутых вариантов и требуемый каждым текст. Явный выбор состава ограничивает требования выбранным снимком, но не доказывает сохранность поведения неэкспортируемых вариантов.

Одинаковые требования дают одну физическую правку. Неактивный в варианте фрагмент не задаёт требования активного синтаксиса: правка серверного возврата внутри существующего `#ifdef SERVER` сохраняет байты клиентской ветви `#else` и границы директив. Генератор не придумывает условную директиву для разрешения конфликта. Структурная правка, поглощающая директивы препроцессора или не представимая безопасным физическим патчем, отклоняется. Итоговый повторный разбор проверяет желаемый синтаксис всех экспортируемых вариантов по сохранённым входам, без повторного чтения исходных файлов.

Сначала получите полную карту исходников, затем создавайте каталоги и записывайте исходники/JSON/SVG. `Cpg.sources` работает в памяти; CLI и [пример публичного редактора](../examples/cpp03-shared-headers/README.md) выполняют эту проверку до экспорта. Каноническая и межъязыковая генерация по-прежнему требует выбранного состава, если конкурирующие варианты нельзя сохранить единым исходным деревом.


## Восстановление парсера и диагностический экспорт (#21)

`Cpg.readRecovering(Path, Options)`, `Cpg.readRecovering(Build, Options)` и `Cpg.readCompilationDatabaseRecovering(Path, Options)` сохраняют диагностический снимок C++03 при ошибке разбора исходника. Соответствующие методы `Cpg.read` / `readCompilationDatabase` остаются строгими: вместо повреждённого графа выбрасывают исключение. Разбор Java остаётся строгим в обоих режимах фасада. Неверные настройки компиляции, неподдержанные редакции/опции и ошибки чтения входной единицы трансляции не относятся к восстановлению исходника и по-прежнему не возвращают граф.

```java
Project project = Cpg.readCompilationDatabaseRecovering(
        Path.of("src/test/resources/cpp03/parser-recovery/compile_commands.json"),
        new Cpg.Options(Language.CPP, Cpg.Stage.RESOLVED));
if (project.hasErrors()) {
    for (SourceFile file : project.files()) {
        for (ParseProblem problem : file.parseProblems()) {
            System.out.println(problem.code() + ": " + problem.message());
        }
        file.stoppedAt().ifPresent(System.out::println);
    }
}
```

Для одного текстового буфера низкоуровневый `Parser.parseRecovering(file, source, language[, standard])` возвращает `SourceFile.Builder`; этот явно выбранный API парсера поддерживает восстановление и для Java. Настроенная перегрузка C++ принимает `Build.TranslationUnit` и может повторить обработку переданных исходных текстов с сохранённым временем трансляции. Ошибки лексики/препроцессора сохраняют доступный префикс токенов и конфигурацию/происхождение, не обещая восстановления произвольного повреждённого синтаксиса. Отсутствующий заголовок относится к диагностике исходника, а не к неверным опциям сборки.

`SourceFile.parseProblems()` возвращает неизменяемый список значений `ParseProblem`. Исходные пять полей и конструктор `ParseProblem(code, message, range, skippedText, recovered)` сохраняются; #22 добавляет основную позицию и контекст срабатывания, описанные ниже. `range` — физический `SourceRange`, `skippedText` — исходный физический фрагмент, а не текст, собранный обратно из токенов. Если `#line` задаёт отличающуюся логическую позицию, сообщение сохраняет её отдельным пояснением, не меняя физического диапазона. `recovered` означает продолжение с известной границы, а не исправление программы. `SourceFile.hasErrors()` и `Project.hasErrors()` показывают статус ошибки. `SourceFile.stoppedAt()` содержит необязательный физический диапазон нулевой длины в точке остановки единицы. Эти записи сохраняются при обычном копировании `edit().build()` и отделены от вычисляемых диагностик анализа.

Восстановление намеренно ограничено. Отсутствующий или повреждённый инициализатор переменной заменяется на `ErrorExpression`, только если парсер дошёл до точки с запятой без пересечения фигурной скобки, несогласованных круглых/квадратных скобок или нарушения строгой редакции; объявление остаётся, следующие инструкции могут быть разобраны. `ErrorExpression.problem()` хранит диагностику, а сам узел имеет строитель и участвует в `children()`/`NodeVisitor` как листовое выражение. Для `int x = ;` диапазон имеет нулевую длину непосредственно перед `;`, `skippedText` пуст. Для `int x = 1 + ;` диапазон начинается на первом токене инициализатора и заканчивается перед точкой с запятой, сохраняя внутренние и завершающие пробелы. При невосстановимой ошибке `range` и `skippedText` описывают остаток физического файла от позиции сбоя до EOF, а `stoppedAt` — только начало этого фрагмента. Если надёжной границы нет, единица останавливается без догадок о продолжении; завершённые объявления верхнего уровня и инструкции внутри уже открытой функции/блока вместе с собранной диагностикой остаются, другие единицы обрабатываются со своими настройками. Каждый шаг потребляет вход, завершает текущую конструкцию либо останавливает единицу, в том числе на EOF.

Проект с любой ошибкой разбора остаётся результатом стадии `PARSED`, даже если запрошены `RESOLVED`, `GREEN` или `FOLDED`. Для всего проекта пропускаются разрешение имён, преобразования, CFG, DFG и предупреждения анализа; пригодный синтаксис соседнего файла сохраняется, но корректность потоков не заявляется. Анализ полностью разобранных функций и пересчёт диагностики после исправления графа остаются отдельными задачами #31 и #43. `Cpg.sources` и генераторы исходников отклоняют повреждённый граф для любого языка до возврата текста.

CLI C++ использует режим восстановления. Он сообщает физические файл/строку/столбец, записывает запрошенные диагностические `--json` и `--svg` и возвращает код 1. При совместном `--out` каталог исходников и файлы не создаются. Диагностические пути должны быть вне заблокированного каталога исходников; конфликты путей выявляются до записи. Неверная конфигурация сборки и ошибка разбора Java по-прежнему не создают экспортов. В JSON добавляются `hasErrors: true` у проекта и повреждённых файлов, `parseProblems` у таких файлов, необязательный `stoppedAt` и `problem` у каждого `ErrorExpression`. В корректном снимке новые поля отсутствуют, прежние эталоны не меняются. SVG отмечает ошибку проекта, повреждённые файлы и точки остановки, показывая доступные узлы всех единиц.

Режим не разрешает расширения компилятора. Активные `__attribute__((packed))`, вариадические макросы, литералы `LL`, двоичные и raw string отвергаются в C++03 с координатами и причиной, называющей конструкцию. Атрибут диагностируется на `__attribute__` (столбец 8 в `struct __attribute__((packed)) ...`), а не на `struct`. То же объявление в неактивной ветви `#if 0` не создаёт синтаксического узла или ошибки и сохраняется при генерации. Диалекты GCC/Clang не реализованы.

`ParserRecoveryIT` проверяет упакованный CLI, отличие строгого и восстанавливающего API, пустой и непустой пропущенный фрагмент, независимые единицы, настоящие JSON/SVG, границы редакции и конечное выполнение. `ParserRecoveryTest` проверяет копирование модели и Visitor, `RecoveryExportTest` — JSON, DOT и запрет генерации. Обязательные сценарии [parser-recovery](../src/test/resources/cpp03/parser-recovery/README.md) и [inactive-extension](../src/test/resources/cpp03/inactive-extension/README.md) содержат команды воспроизведения.

## Происхождение и группировка диагностики (#22)

К пяти полям восстановления `ParseProblem` добавлены `primaryRange`, `reason`, `relatedRanges` и `context`. `primaryRange` указывает физическую причину, показываемую пользователю; он не обязан совпадать с пропущенным фрагментом восстановления в `range`. `reason` — стабильная причина со значимыми параметрами без случайных пояснений представления/контекста. `DiagnosticRelatedRange(role, label, range)` содержит машинно-читаемую роль, подпись и физический диапазон, в том числе из другого файла. Начало диапазона включительно, конец исключительно. Совместимый конструктор использует `range` как `primaryRange`, `message` как `reason`, пустой список дополнительных диапазонов и null-контекст.

`DiagnosticContext(translationUnit, variantId, includeChain, expansionChain)` хранит нормализованный абсолютный физический путь единицы трансляции, необязательный вариант сборки и списки значений `Preprocessing.Include` и `Preprocessing.Expansion` от внешнего контекста к внутреннему. Null в `variantId` означает единицу без конфигурации. Списки неизменяемы, ID действуют внутри единицы/конфигурации и не являются глобальными ID узлов. Контекст содержит записи-значения, а не ссылки на синтаксические узлы. Раскрытия сохраняют вызов, определение, фрагменты замещения, аргументы и операции #/##. Поэтому обычный `edit().build()` и повторный анализ сохраняют сведения без устаревших ссылок на узлы; исправление самой ошибки после изменения исходника остаётся задачей #43.

`Project.parseProblems()` возвращает все срабатывания, упорядоченные по физическому пути/диапазону, коду, причине и полному контексту с устойчивым разрешением совпадений. Для старой записи из пяти полей без контекста добавляется владеющая единица трансляции; `SourceFile.parseProblems()` по-прежнему возвращает исходные записи файла. `Project.diagnosticGroups()` объединяет срабатывания по **коду + физическому `primaryRange` + `reason`**, а не только по тексту сообщения или номеру строки. `DiagnosticGroup` предоставляет `code`, `primaryRange`, `reason`, `message`, отсортированные `occurrences` и три разных счётчика:

- `translationUnitCount()` — число разных физических путей единиц трансляции.
- `variantCount()` — число разных пар (путь единицы, ID варианта); единица без конфигурации имеет один вариант.
- `occurrenceCount()` — число всех срабатываний, включая повторные включения и конфигурации.

Ошибка общего заголовка у двух `.cpp` даёт одну группу и две затронутые единицы. Две конфигурации одного физического `.cpp` дают одну единицу, но два варианта. Разные результаты недопустимой склейки, например `+*` и `+/` в одном физическом вызове, остаются разными причинами/группами. Порядок групп и срабатываний не зависит от порядка обхода единиц; это гарантия для сводки диагностики, а не перестановки всех файлов или ID AST в проекте.

Значимые параметры причины также включают раскрытые операнды ошибочных директив `#line`/`#include` и условных выражений, прежнюю/новую сигнатуры замещения при несовместимом переопределении макроса. Физическая позиция директивы может совпадать при разных причинах. Ошибка директивы сохраняет цепочку раскрытий; пояснения переопределения имеют роли `previous-definition` и `new-definition`. Определения командной строки используют описанные выше синтетические буферы исходника, а не выдуманные физические файлы. Для двух независимых отсутствующих выражений в одном раскрытии физическое место причины внутри определения различает `reason`, даже если основные диапазоны обоих срабатываний указывают один вызов.

Для `#define ASSIGN(x) x =` и `ASSIGN(total);` отсутствующий правый операнд представлен `ErrorExpression` с пустым фрагментом восстановления и основной позицией нулевой длины перед `;`. Роли `macro-invocation` и `macro-definition` указывают полный вызов и токен `=` в определении. Восстановление на этой границе сохраняет независимую ошибку инициализатора следующей инструкции как отдельное срабатывание/группу. Для `JOIN(+, *)` с `#define JOIN(a,b) a ## b` в заголовке основной диапазон — вызов; роли `macro-argument-left`, `macro-argument-right` и `macro-paste-operator` указывают `+`, `*` и `##`. API/JSON сохраняют все три физических диапазона. Неудавшееся раскрытие также остаётся в цепочке раскрытий.

Восстановление присваивания не пересекает незакрытый внешний разделитель: `(x = ;`, `if (x = ;` и `f(x = ;` останавливают единицу с исходной ошибкой отсутствующего выражения, а не объявляют восстановление с последующими производными синтаксическими ошибками. Ошибка препроцессора также остаётся первичной причиной без второй ошибки парсера из-за оборванного префикса токенов. Такая ограниченная обработка не скрывает независимые ошибки после допустимой границы восстановления.

У повреждённого проекта корневой JSON добавляет `diagnosticGroups`. Каждая группа содержит ключ, сообщение, три счётчика и полные `occurrences`; каждое срабатывание — исходные поля восстановления, основную позицию, причину, дополнительные диапазоны и доступный контекст. Контекст сериализует значения включений/раскрытий, а не указатели на узлы; при null поле `variantId` отсутствует. `parseProblems` файла и `ErrorExpression.problem` используют ту же схему срабатывания. Корректные снимки не содержат корневых полей ошибки, прежние эталоны JSON не меняются.

CLI печатает одну строку `error [code]` в основной позиции группы, счётчики единиц/вариантов/срабатываний и отдельные, детерминированно упорядоченные строки `note [role]` для дополнительных диапазонов. Группировка не удаляет контексты срабатываний и не объединяет независимые ошибки после восстановления. Реализованная область — `ParseProblem` препроцессора/парсера, а не все семантические диагностики и не универсальный механизм зависимостей/подавления сообщений. Код 1, диагностические экспорты и запрет генерации исходников сохраняются. [Диапазоны и команды примера](../src/test/resources/cpp03/diagnostic-provenance/README.md) и `DiagnosticProvenanceIT` проверяют равенство API/CLI JSON, точные координаты, обратный обход и сохранность снимков.

## Профили платформы и рекурсивные деклараторы (#23)

### Целевые настройки и единицы

`com.kniazkov.cpg.build.PlatformProfile` — неизменяемое описание целевой платформы, независимое от машины с Java и нативного контрольного компилятора. `PlatformProfile.defaults()` и `builder()` используют полную таблицу ниже. **Обе числовые колонки заданы в битах**; целевой байт имеет `bitsPerByte = 8`, а `sizeof` возвращает количество целевых байтов.

| Категория хранения | Размер, бит | Выравнивание, бит |
|---|---:|---:|
| `bool` | 8 | 8 |
| `char`, `signed char`, `unsigned char` | 8 | 8 |
| `short`, `unsigned short` | 16 | 16 |
| `int`, `unsigned int` | 32 | 32 |
| `long`, `unsigned long` | 64 | 64 |
| `long long`, `unsigned long long` (только описание хранения) | 64 | 64 |
| `wchar_t` | 32 | 32 |
| `float` | 32 | 32 |
| `double` | 64 | 64 |
| `long double` | 128 | 128 |
| Обычный указатель | 64 | 64 |

Знаковые и беззнаковые варианты имеют общие настройки хранения, но разную идентичность типа. Отображаемое имя по умолчанию — `default-lp64`. Простой `char` по умолчанию знаковый; `wcharType` — `int`, `sizeType` — `unsigned long`, кодировки исходника и обычного исполнения — `UTF-8`, широкого исполнения — `UTF-32`. Целые представлены дополнительным кодом без битов заполнения, диапазон `bool` — 0..1. `integerRange(type)` возвращает границы произвольной точности; `sizeBits`, `sizeBytes`, `alignmentBits` — сведения о хранении. Запись `long long` **не** разрешает синтаксис типа C++11 или литералы `LL` в C++03. Таблица не задаёт формат вычислений с плавающей точкой или ABI указателя на член.

Например, частичное переопределение в `long32.json`:

```json
{
  "inherits": "default",
  "name": "long32",
  "sizes": {"long": 32},
  "alignments": {"long": 32}
}
```

`PlatformProfile.read(path)` читает JSON, `fromSettings(map)` принимает ту же схему. Обязательное поле `inherits` принимает `"default"` либо `"none"`. При `"default"` пропущенные настройки наследуют документированные значения; явное `"alignments": {"long": null}` вместо этого делает выравнивание long неизвестным. Уменьшение размера long без изменения наследуемого выравнивания 64 бита недопустимо. При `"none"` нужно задать `bitsPerByte`, все записи `sizes`, `charSigned`, `wcharType`, `sizeType`, все три кодировки и `aggregateLayout`; `name` необязательно, пропущенные выравнивания неизвестны. Ключи хранения: `bool`, `char`, `short`, `int`, `long`, `long long`, `wchar_t`, `float`, `double`, `long double`, `pointer`. `toSettings()` выдаёт полный эффективный профиль с `inherits: "none"` и явными null для неизвестных выравниваний, пригодный для повторного чтения.

`bitsPerByte` лежит в диапазоне 8–4096; каждый скалярный размер не превышает 4096 бит. Размеры и известные выравнивания должны быть положительным целым числом целевых байтов; выравнивание делит размер и в байтах является степенью двойки. Проверяются порядок целых/вещественных ширин, совпадение ширины `wchar_t` с `wcharType`, вместимость широкой кодировки, допустимые кодировки и `sizeType` (`unsigned int` либо `unsigned long`). `sourceEncoding` принимает доступную Java-кодировку; `executionEncoding` ограничена `UTF-8`, `ISO-8859-1`, `US-ASCII`, а `wideExecutionEncoding` — `UTF-16` или `UTF-32`. `wcharType` должен быть целым типом C++03, исключая `bool`, сам `wchar_t` и `long long`. Неверные или неизвестные настройки дают ошибку конфигурации, а не значения платформы машины. 16-битный целевой байт допустим при согласованных размерах/выравниваниях: `long = 64` тогда означает `sizeof(long) = 4`, а не 8.

### Выбор профиля

```java
import com.kniazkov.cpg.build.PlatformProfile;

PlatformProfile long32 = PlatformProfile.builder().name("long32")
        .sizeBits("long", 32).alignmentBits("long", 32).build();
Cpg.Options options = new Cpg.Options(Language.CPP, Cpg.Stage.FOLDED)
        .withPlatform(long32);
Project project = Cpg.read(Path.of("src/test/resources/cpp03/platform-declarators/sources"), options);
```

`Build.TranslationUnit.platform()` хранит эффективный профиль; `unit.withPlatform(profile)` задаёт его отдельно для единицы трансляции. Прежние конструкторы сохраняют профиль по умолчанию. Необязательное поле записи базы компиляции `"platformProfile": {...}` принимает встроенный объект той же схемы, а не имя файла. `Options.withPlatform(profile)` либо CLI `--platform-profile FILE` переопределяет профиль всех импортируемых единиц; без переопределения используются настройки записи, затем значения по умолчанию. Эти настройки применимы только к входу C++.

```sh
java -jar target/cpg-0.0.1-SNAPSHOT.jar --from cpp --stage folded \
  --input src/test/resources/cpp03/platform-declarators/sources \
  --platform-profile src/test/resources/cpp03/platform-declarators/long32.json \
  --json target/platform-long32.json
```

Профиль сохраняется в препроцессинге, при редактировании снимка и повторной обработке во время генерации. `stableIdentity()` включает эффективные семантические настройки, но исключает отображаемое имя; `TranslationUnit.variantId()` учитывает эту идентичность. Изменение только имени не создаёт вариант, а изменение ширины, выравнивания, кодировки или размещения создаёт. Один физический `.cpp` может существовать в проекте с двумя профилями. Это идентичность конфигурации, а не обещание совпадения с ABI нативного компилятора. В экспорте единицы сборки содержат полный эффективный объект `platform` (входное поле базы называется `platformProfile`). `externalInputs` владеет корнем `platform-profile` с дочерними предопределёнными макросами и записью `platform-selection` каждой конфигурации, включая вход из папки без объекта сборки.

Исходные файлы и заголовки декодируются через `sourceEncoding`. При выводе C++→C++ упакованный CLI кодирует корневые файлы и заголовки в сохранённой эффективной кодировке исходника. Конфликт кодировок одного физического файла или непредставимый в кодировке текст дают отказ до записи любого запрошенного экспорта. `Cpg.sources` возвращает Java-строки без привязки к кодировке; вывод Java/межъязыкового CLI остаётся UTF-8.

Предопределённые сведения о цели: `__CHAR_BIT__`, `__SIZEOF_SHORT__`, `__SIZEOF_INT__`, `__SIZEOF_LONG__`, `__SIZEOF_LONG_LONG__`, `__SIZEOF_FLOAT__`, `__SIZEOF_DOUBLE__`, `__SIZEOF_LONG_DOUBLE__`, `__SIZEOF_POINTER__`, `__SIZEOF_WCHAR_T__`, `__SCHAR_MAX__`, `__SHRT_MAX__`, `__INT_MAX__`, `__LONG_MAX__`, `__WCHAR_TYPE__`, `__WCHAR_MAX__`, `__SIZE_TYPE__`. При беззнаковых char/wchar добавляются `__CHAR_UNSIGNED__`/`__WCHAR_UNSIGNED__`. Эти определения нельзя отменять или переопределять в исходнике/команде; макросы идентичности компилятора/ОС не выдумываются. Профиль также определяет [выборы вычислителя условий препроцессора](#условная-компиляция-каталог-и-внешние-входы-19).

### Написанные типы и структурная идентичность

Парсер строит вложенные `NamedType`, `QualifiedType`, `PointerType`, `ReferenceType`, `ArrayType`, `FunctionType`, `MemberPointerType`. `NamedType.fundamentalKind()` классифицирует фундаментальное написание. `TypedefDeclaration.type()` владеет синтаксисом исходного типа; использование сохраняет написанное `NamedType.name()` и ссылку `alias()`. Для `typedef int Count; Count value;` написанный тип — `Count`, а `canonicalIdentity()` раскрывает псевдоним до `int`.

Деклараторы составляются от имени наружу с учётом скобок, абстрактных деклараторов параметра/type-id, объявлений через запятую, уровней cv, параметров функции и вариадических типов функций. Поэтому `int *a[3]` — массив указателей, `int (*a)[3]` — указатель на массив, `int (*f)(double)` — указатель на функцию. У `int C::*p` отдельно представлены тип владельца и тип члена; ссылка не является обычным указателем. `ArrayType.bound()` владеет необязательным выражением, не требуя численной длины. Строители, Visitor, неизменяемое копирование, JSON и генерация C++ сохраняют эти структуры. Распознавание typedef учитывает области из #24 ниже. Поддержаны псевдонимы указателя на функцию и объявления через typedef самой функции; последние сохраняют написанный псевдоним в `CallableDeclaration.writtenType()`. Простые тела class/struct по-прежнему поддерживают одну секцию доступа; аргументы по умолчанию, общая прямая инициализация, смешанные секции доступа и полная проверка допустимости объявления отложены. Классы хранения и вложенные объявления описаны в #24.

`TypeNode.canonicalType()` проходит внешние typedef; `canonicalIdentity()` рекурсивно описывает структуру и квалификаторы с поправкой массива/функции к указателю в параметре и обработкой верхнего cv параметра. Целевая ширина не определяет идентичность языка: 32-битные `int` и `long` различны. Переносимая целая арифметика границы канонизируется, если литералы без суффикса и промежуточные результаты помещаются в −32767..32767: `int[1+2]` и `int[3]` имеют общую идентичность. Отрицательное деление/остаток и зависимые от цели границы остаются символическими. Это структурная идентичность реализованного синтаксиса, не полная эквивалентность типов или разрешение перегрузок C++: неразрешённые имена и остальные символические границы требуют дальнейшей семантики. Области видимости, объявления и связывание описаны в [#24](#области-видимости-объявления-и-связывание-24); перегрузки, ADL и полная исходная идентичность остаются в #30.

### Озеленённые сведения, sizeof и консервативная свёртка

`TypeSemantics.profile(file)` возвращает профиль единицы трансляции. `describe(type, profile)` даёт `TypeRepresentation` с `canonicalIdentity`, `profileIdentity` и необязательными `sizeBits`, `sizeBytes`, `alignmentBits`, `integerRange`. `TypeNormalizer.green(project)` прикрепляет описание как `TypeNode.semanticType()`, не заменяя написанные узлы и связи typedef. Проход выполняется на `GREEN` и `FOLDED`; неизменённая копия сохраняет сведения, правка канонической идентичности делает устаревшее описание недоступным. После изменения типа или профиля нужно повторить нормализацию. JSON хранит ссылку typedef как `aliasId`, рекурсивные типы — через дочерние поля и `canonicalIdentity`, озеленённые сведения — в `semanticType`; неизвестные поля описания пропускаются. Границы `integerRange` называются `minimum`/`maximum`. Это отличается от явного null для выравнивания в эффективном профиле.

`TypeSemantics.sizeof(type, profile)` и `sizeof(sizeOfExpression, profile)` возвращают `Optional<BigInteger>` в **целевых байтах**. Известны фундаментальные объектные типы, обычные указатели, ссылки на известный тип и массивы с известным размером элемента и положительной константной границей. Ограниченное определение типа выражения учитывает связанные переменные/параметры и другие поддержанные выражения; непосредственный массив не превращается в указатель, но массив/функция в параметре имеет скорректированный тип указателя. `SizeofExpression` владеет ровно одним операндом: типом либо выражением. Выражение не вычисляется, его синтаксис не является исполняемым чтением или записью данных.

`TypeSemantics.layout(fields, profile)` — отдельная утилита для явно переданного списка обычных нестатических объектных полей в порядке объявлений. При `aggregateLayout: "sequential"` начало поля округляется до его выравнивания, выравнивание агрегата равно максимуму полей, а полный размер включает хвостовое заполнение до этого выравнивания (пустой список занимает минимум один целевой байт). Для `char, int` по умолчанию получаются смещения 0 и 4 целевых байта, размер 8 и выравнивание агрегата 32 бита. При выравнивании int в 8 бит — смещения 0 и 1, размер 5 и выравнивание 8 бит. `aggregateLayout: "unknown"`, неизвестный требуемый размер/выравнивание или поле-ссылка дают отсутствие результата. Неизвестное выравнивание само по себе не отменяет известный `sizeof` скалярного типа.

Утилита не выводит полное размещение класса из синтаксиса `struct`. Для `void`, функции, неполного/неразрешённого класса, указателя на член и немоделируемого размещения класса/баз/vtable размер не установлен. Корректные выражения `sizeof` с неизвестным значением и символические границы сохраняются без свёртки. #24 диагностирует `sizeof` класса, неполного в точке использования; остальные случаи недопустимого `sizeof` остаются в #28. В частности, структурный список полей не задаёт нативный C++ ABI.

Парсер обычных выражений C++ распознаёт десятичные, восьмеричные и шестнадцатеричные целые с `U`, `L` и составными суффиксами, выбирая тип-кандидат C++03 по целевому диапазону. Значения вне signed-32-bit поля узла пока диагностируются; полный диапазон литералов и сохранение их написания остаются в #25.

Свёртка C++ использует эффективные целые диапазоны, продвижения и знаковую/беззнаковую арифметику для поддержанных `+`, `-`, `*`, `/`, модельного `%` и унарных `+`/`-`, включая известный `sizeof` в границе массива. Беззнаковый результат циклический по целевой ширине; знаковое переполнение и деление на ноль блокируют свёртку вместо выдуманного значения. Внутренние вычисления используют `BigInteger`, но опубликованный `IntegerLiteral.value()` пока ограничен знаковыми 32 битами: большие доказанные результаты остаются выражениями. Синтезированные константы не-int сохраняют `cppType` и соответствующий суффикс C++. Полные исходные литералы, преобразования выражений и набор операций относятся к #25; произвольное символическое размещение объектов и остальные случаи неверного `sizeof` — к #28. Прежняя свёртка Java и тесты межъязыковой генерации сохраняются.

[Пример platform-declarators](../src/test/resources/cpp03/platform-declarators/README.md) и [контракт E2E](e2e.ru.md#профили-платформы-и-деклараторы-23) проверяют эти границы через публичный API и упакованный CLI. Нативное исполнение проверяет только исходный профиль; сведения произвольного профиля сравниваются через API/CLI, без навязывания чужого ABI компилятору машины.

## Области видимости, объявления и связывание (#24)

### Исходные объявления и принадлежность единице трансляции

Объявление остаётся конкретным исходным вхождением, а не заменяется одним символом на весь проект. `Declaration.isDefinition()` отличает определение от объявления; `previousDeclaration()` и `definition()` — необязательные ссылки без владения. `linkage()` возвращает `NONE`, `INTERNAL` или `EXTERNAL`, а `languageLinkage()` хранит `C++` или `C`. Это разные свойства: языковое связывание не открывает сущность с внутренним связыванием для другой единицы трансляции.

`NamespaceDeclaration.members()` владеет объявлениями одного открытия пространства имён, `anonymous()` отличает безымянное открытие. Повторные открытия сохраняют отдельные исходные узлы, но поиск учитывает общее пространство имён. `NamespaceAliasDeclaration` хранит `name()` и `targetName()` с необязательным `target()` пространства имён. `UsingDirective` хранит `namespaceName()` и `target()` пространства имён; `UsingDeclaration` хранит `qualifiedName()` и введённое объявление как `target()`. Цели ссылок не являются синтаксическими детьми. Обычный Visitor посещает каждое исходное объявление один раз, а не по одному разу для каждого поиска через него.

`EnumDeclaration.enumerators()` владеет упорядоченными исходными `EnumeratorDeclaration`; каждый перечислитель имеет `name()` и необязательное написанное выражение `value()`. Это обычные перечисления C++03, не scoped enum из C++11. `VariableDeclaration.modifiers()` сохраняет написанные классы хранения, `ParameterDeclaration.modifiers()` — допустимый для параметра `register`. Предварительное объявление class/struct использует прежний `ClassDeclaration` с `isDefinition() == false`; вложенные типы принадлежат своему классу. На исходных вхождениях доступны имена, диапазоны и происхождение препроцессора.

Два `.cpp`, включающие один физический заголовок, имеют независимые узлы объявлений, даже при полностью одинаковом `SourceRange`. [Пример scopes-linkage](../src/test/resources/cpp03/scopes-linkage/README.md) включает одну строку `typedef VALUE_TYPE Width;` из `config.h` по двум командам: с `-DWIDE` в `a.cpp` макрос раскрывается в `long`, а в `b.cpp` — в `int`. Один `Project` сохраняет оба typedef, каждое использование `Width` связано с объявлением своей единицы. Поэтому физический диапазон не является ключом сущности: при идентификации использования или объявления учитывай владеющий `SourceFile` и `variantId()`.

### Поиск написанного типа и полнота в точке использования

У `NamedType` метод `name()` хранит написание, необязательный `elaboratedKeyword()` — написанный префикс `class`/`struct`/`union`/`enum`, `declaration()` — найденное в этой точке объявление, `alias()` — непосредственный typedef, если он есть, а `resolutionSteps()` описывает путь поиска. Неизменяемый `TypeResolutionStep` содержит `kind()`, `via()` и `target()`. Оба узловых поля — ссылки без владения на объявления этого снимка. Путь объясняет поиск, не переписывая имя типа.

```cpp
namespace shop {
    typedef long RawId;
    typedef RawId OrderId;
    typedef int Count;
}
using namespace shop;
OrderId id;
Count count;
shop::OrderId qualified;
```

Неквалифицированные `OrderId` и `Count` имеют разные шаги разрешения, ссылающиеся на **один** `UsingDirective`, и свои найденные объявления в качестве целей. Сама директива ссылается на `shop`, а не на один из typedef. У явно квалифицированного `shop::OrderId` лишнего шага using-директивы нет. Переходы `alias().type()` показывают каждое написание последовательности typedef; `canonicalType()` проходит внешнюю цепочку, а `canonicalIdentity()` даёт `long` для `OrderId`. Генерация C++ сохраняет `OrderId id;`, не заменяя написанное имя на `long`.

```java
for (TypeResolutionStep step : written.resolutionSteps()) {
    System.out.println(step.kind() + ": " + step.via().getClass().getSimpleName()
            + " -> " + step.target().getClass().getSimpleName());
}
TypeNode current = written;
while (current instanceof NamedType name && name.alias().isPresent()) {
    current = name.alias().orElseThrow().type();
}
System.out.println(current.canonicalIdentity());
```

`completeAtUse()` — факт в исходной точке, а не проверка существования определения где-либо в готовом проекте. Для `class Order; Order *current; class Order { int id; };` именованный тип под указателем связан с видимым предварительным объявлением, а его `definition()` — с последующим определением класса. `completeAtUse()` этого использования остаётся false. Указатель допустим, но последующее определение не делает задним числом допустимым `sizeof(Order)` перед определением. Полнота не устанавливает размер или ABI класса: даже для полного класса результат `TypeSemantics.sizeof` может оставаться неизвестным (#28).

Первое введение типа записью `struct New *p;` создаёт неявное предварительное объявление `ClassDeclaration` (`implicit() == true`, JSON `implicit: true`). При генерации его вводит написанный `NamedType.elaboratedKeyword()`; отдельное дополнительное объявление не выводится. Редактирование, при котором написание противоречит неявному объявлению, отвергается вместо создания другой сущности. Квалифицированные использования переменных и перечислителей имеют необязательную ссылку без владения `MemberExpression.target()`, сериализованную как `targetId`.

### Поиск в исходной точке, связывание и диагностика

Тела встроенных функций-членов разбираются с завершённой средой имён типов окружающего класса, включая более поздние typedef. Остальные использования сохраняют видимость в исходной точке. Класс и перечисление становятся полными у закрывающей скобки; тела встроенных функций-членов учитывают исключение контекста полного класса. Объявления функции и extern-переменной в блоке наследуют связывание видимого более раннего объявления, в том числе внутреннее или языковое C. Унаследованное C-связывание не создаёт написанную спецификацию extern «C» внутри блока.

Среда имён типов парсера учитывает глобальную область, пространства имён, классы, параметры функций и блоки, включая затенение и повторные открытия namespace. Она различает `T(a);`: видимый тип `T` делает запись объявлением `a`, а видимая обычная вызываемая сущность `T` — выражением вызова. При видимых типах `T` и `U` запись `T x(U());` является объявлением функции с параметром функционального типа, а не прямой инициализацией. После разбора разрешение имён публикует соответствующие ссылки на объявления. Переменная вводится до её инициализатора: внутреннее использование `x` в `int x = 1; { int x = x; }` связано с внутренним объявлением.

Файловые `static` и сущности безымянного пространства имён изолированы по единице трансляции. Внешние функции сопоставляются по квалифицированному имени, языковому связыванию и реализованной идентичности типов параметров. Обычный поиск C++ требует видимого локального объявления: найденное определение в постороннем файле само по себе не делает необъявленное имя видимым. `extern "C"` использует сопоставление сущностей C, сохраняя написанную спецификацию связывания. Повторные объявления остаются отдельными вхождениями со связями `previousDeclaration()` и, при однозначности, `definition()`. При неизвестном составе сборки `CallExpression.candidates()` показывает возможные внешние определения без утверждения о межфайловом нарушении ODR; выбранный `Build.Composition` проверяет определения выбранных единиц совместно. Несколько определений внутри одной единицы ошибочны в обоих режимах. Совпадающие inline-определения разных единиц обрабатываются консервативно сравнением генерируемого синтаксиса; это не полная проверка ODR классов, шаблонов и inline с эквивалентностью токенов и результатов поиска.

`CallExpression.resolution()` сохраняет варианты `UNRESOLVED`, `RESOLVED`, `AMBIGUOUS`, `ODR_CONFLICT`. `target()` заполнен только для одной однозначно разрешённой вызываемой сущности. Разные перегрузки остаются кандидатами: #24 не ранжирует преобразования и не выбирает лучшую перегрузку (#30). Разрешённые объявления классов/перечислений имеют необязательный `Declaration.typeIdentity()`: квалифицированную идентичность, с контекстом единицы трансляции для локальных типов и безымянных пространств имён. `NamedType.canonicalIdentity()` использует её, не объединяя посторонние одноимённые классы в сигнатурах. Это расширяет структурную идентичность #23, не заявляя полной эквивалентности типов C++ или выбора перегрузок.

Разрешение прикрепляет семантические `Diagnostic.Severity.ERROR` со стабильными кодами:

- `incomplete-type`: для `sizeof` нужен полный тип в этой исходной точке, в том числе при typedef на неполный класс.
- `conflicting-declaration`: несовместимые объявления реализованной сущности переменной, typedef или функции, включая несовместимые сигнатуры C.
- `odr-conflict`: несколько недопустимых определений в одной единице трансляции или выбранном составе сборки.

Это `Node.diagnostics()`, а не записи `ParseProblem` или сгруппированные ошибки парсера из #22. `Project.hasErrors()` и `SourceFile.hasErrors()` по-прежнему показывают только ошибки **разбора**; при проверке семантической корректности учитывай также уровни диагностик. Строгие `Cpg.read`/`readCompilationDatabase` возвращают проанализированный граф, если разбор успешен, но разрешение нашло семантическую ошибку. На `PARSED` эти проверки ещё не выполнены. CLI печатает семантическую ошибку, возвращает код 1, сохраняет отдельно запрошенные JSON/SVG и не создаёт исходники. `Cpg.sources` и прямая генерация также отвергают снимок с прикреплённой семантической ERROR. Само по себе неизвестное значение размера или неразрешённое имя не является диагностикой ошибки или доказательством корректности программы.

### JSON, генерация и редактирование

JSON сохраняет владеющие объявления и добавляет необязательные ссылки, не дублируя целевые узлы:

- Пространство имён содержит `name`, `anonymous`, `members`; псевдоним — `name`, `targetName` и разрешённый `targetId`.
- Using-директива содержит `namespaceName` и разрешённый `targetId` пространства имён; using-объявление — `qualifiedName` и разрешённый `targetId` объявления.
- Перечисление содержит `name`, `enumerators`; перечислитель — `name` и необязательное принадлежащее ему `value`. Переменные и параметры содержат непустой `modifiers`.
- Метаданные объявления: `linkage` в нижнем регистре, если не `none`, `languageLinkage`, если не `C++`, `isDefinition: false` для не-определения необязательные `previousDeclarationId` / `definitionId` и необязательный `typeIdentity` класса/перечисления. Пропущенным метаданным соответствуют значения API по умолчанию `NONE`, `C++` и true; отсутствие поля ссылки означает отсутствие связи.
- Функция, объявленная через typedef, содержит принадлежащий ей `writtenType` помимо `returnType` и `parameters` вызываемой сущности. Для `typedef int F(double); F f;` сохраняются написание `F f;` и пригодная для анализа сигнатура. Определение функции через такой typedef отвергается как недопустимое в C++03.
- Именованный тип сохраняет необязательный `elaboratedKeyword`; разрешённый тип содержит `declarationId` и `completeAtUse`. Использования typedef сохраняют `aliasId` и `canonicalIdentity`. Непустой массив `resolutionSteps` содержит записи `{kind, viaId, targetId}`. Текущие виды шагов: `using-directive`, `using-declaration`, `namespace-alias`, `typedef`, `declaration`. Последний typedef на фундаментальный тип ссылается в шаге на себя, поскольку синтаксис фундаментального типа не является объявлением; конечный тип доступен через принадлежащий ему `type`.

Те же ссылки представлены общими рёбрами `ref`. ID указывают на узлы данного JSON-снимка, а не на глобальные символы проекта или физические диапазоны. DOT/SVG подписывает пути поиска написанного типа и связи предыдущего объявления/определения. `completeAtUse` имеет смысл вместе с найденным объявлением; для несвязанного имени значение API по умолчанию true не является доказательством полноты типа.

Каноническая генерация C++ выводит пространства имён, псевдонимы, using-объявления/директивы, перечисления, предварительные объявления и классы хранения. Вместо исходной группировки она может использовать отдельные блоки `extern "C" { ... }`; различие объявления/определения и семантика хранения сохраняются. Сохраняющий исходник путь оставляет неизменённые захваченные файлы/заголовки и по-прежнему проверяет согласование вариантов и повторный разбор из #20. Перевод этих конструкций в Java не добавляется: проверка переносимости отклоняет неподдержанный межъязыковой вывод, а не удаляет их молча.

`edit().build()` копирует принадлежащие дереву объявления и все цели ссылок в **новый** снимок, сохраняя общую директиву, цепочки типов и циклы предварительного объявления/определения. Поиск при этом не пересчитывается. Редактирование сбрасывает вычисляемые диагностики и потоки; после изменения имён, объявлений, порядка или типов выполни `NameResolver.resolve(edited)`, затем необходимые проходы нормализации/потоков до интерпретации или экспорта результата. Запрашивай возвращённый снимок, не прежние узлы. `ProjectEditor` проверяет принадлежность целей связей исходному проекту, перенаправляет ссылки при замене и запрещает удалять объявление с оставшимися входящими ссылками. Повторное разрешение пересчитывает привязки и очищает устаревшие ссылки поиска/импорта, не меняя прежний снимок.

Остаются отдельными полное разрешение перегрузок и ADL (#30), ABI/размер класса (#28), аргументы по умолчанию и общая инициализация, смешанные секции доступа класса, определение class/enum с последующим декларатором объекта в той же инструкции и полная семантика значений/диапазонов enum. Поддержка областей/объявлений не означает конструкторы, наследование, проверку доступа, шаблоны или полную проверку допустимости C++03. [Контракт E2E](e2e.ru.md#области-видимости-объявления-и-связывание-24) отделяет переносимое нативное исполнение от проверок поиска через API и отрицательных диагностических примеров.

## Литералы, выражения и стандартные преобразования (#25)

### Значение и написание литерала

Литералы C++03 хранят написание отдельно от значения и типа. `IntegerLiteral.bigValue()` возвращает точный `BigInteger`; совместимый метод `value()` возвращает `int`, только если значение представимо, иначе выбрасывает `ArithmeticException`. `cppType()` отражает выбор кандидата C++03 по эффективному профилю, основанию (десятичное/восьмеричное/шестнадцатеричное) и сочетанию суффиксов `U`/`L`. Одинаковая ширина не объединяет `int` и `long`. Значение вне диапазонов кандидатов, двоичные литералы и суффикс `LL` отвергаются.

`BooleanLiteral` хранит логическое значение. `FloatingLiteral.value()` — лексическое десятичное значение `BigDecimal`; `cppType()` различает `float`, `double`, `long double`, а `spelling()` сохраняет суффикс/экспоненту. Это **не** округлённое значение целевого плавающего типа и не полноценный вычислитель его арифметики. Экспонента вне поддержанного десятичного диапазона диагностируется.

`CharacterLiteral` хранит точное целое значение, `wide`, `cppType`, `spelling`, `codeUnitBits`, `valueBits`. Числовые escape-последовательности задают кодовые единицы; исходные символы и universal character names используют обычную/широкую кодировку исполнения профиля. Реализация многосимвольной константы явно выбрана: обычные единицы упаковываются старшими вперёд в целевой `int`, обрезаются до его ширины и интерпретируются с его знаковостью; широкая константа сохраняет последнюю единицу. Это модельное решение, а не переносимый нативный эталон.

`StringLiteral.codeUnits()` содержит декодированные единицы **без** завершающего нуля; тип — массив const `char`/`wchar_t` с границей, включающей этот ноль. Соседние токены образуют один узел; наличие широкого токена выбирает широкую кодировку. `spelling()` объединяет написания токенов пробелами, не обещая побайтового сохранения промежуточных комментариев/пробелов. Сохранение неизменённого физического текста — отдельный контракт сохраняющего генератора.

### Операторы, тип и категория

Парсер/генератор представляют приоритеты от постфиксных операций, индексации и доступа к членам через унарные операции, `.*`/`->*`, арифметику, сдвиги, сравнения, побитовые/логические операции, `?:`, присваивания/составные присваивания до запятой. Префиксные/постфиксные инкременты и декременты имеют разные узлы. `ConditionalExpression` владеет условием и двумя ветвями; `CompoundAssignmentExpression` — целью/значением и написанием оператора. Генерация и повторный разбор проверяют скобки, включая особую грамматику условного выражения и запятой. Логические операции сохраняют синтаксис короткого замыкания; это не обещание полноты CFG/DFG или свёртки всех операторов.

После разрешения `Expression.semanticInfo()` предоставляет неизменяемый `ExpressionInfo`: необязательный канонический `resultType()` и `category()` (`LVALUE`, `RVALUE`, `UNKNOWN`). Идентичность типа — строковое значение, не владеющий узел или ссылка на объявление; она отделена от вычисленного значения константы. Отсутствие типа/неизвестная категория не доказывают корректность выражения. `TypeSemantics` определяет встроенные арифметические типы и продвижения, результаты указательных операций/индексации/указателя на член, категории присваивания/запятой/условного выражения с учётом профиля.

`NameResolver.resolve` вызывает `StandardConversions.analyze` после разрешения имён/вызовов. Консервативный проход вставляет поддержанные преобразования инициализаторов, присваиваний, аргументов однозначно разрешённого вызова (включая продвижения вариадических аргументов), унарных/арифметических/логических операндов и условных выражений. Представлены lvalue-to-rvalue, переход массива/функции к указателю, целочисленные/плавающие продвижения, арифметические преобразования, квалификации указателей, нулевая целая константа указателя и поддержанное связывание ссылок. Построение ограничено представимыми фундаментальными/cv/указательными/ссылочными/функциональными типами: это не выбор перегрузки, пользовательское/произвольное классовое преобразование или полный валидатор языка. Продвижения enum и угаданный `ptrdiff_t` для разности указателей не предоставляются.

### Явный синтаксис, неявные узлы и экспорт

`ConversionExpression` владеет `operand()` и `targetType()`, хранит `kind()`, `isExplicit()` и необязательный канонический `sourceType()`. Явный `static_cast<long>(x)` имеет вид `STATIC_CAST` и диапазон написанного приведения. При единственной цели `f(long)` вызов `f(x)` для `int x` получает неявные обёртки. Оба случая предоставляют исходный/целевой тип, но `static_cast` печатает только явный узел; неявная обёртка прозрачно печатает операнд. Анализ не добавляет написанное приведение, способное изменить последующий выбор перегрузки. Другие формы приведений, `new`/`delete`, размещение класса и полная типизированная свёртка остаются #28; аргументы по умолчанию — #26; перегрузки/ADL/пользовательские преобразования — #30.

JSON добавляет `semanticInfo: {resultType?, category}` к проанализированным выражениям. Литералы экспортируют значения/написания/типы; большие целые остаются точными JSON-числами, поэтому потребителю нельзя терять их точность при чтении через binary double. Строки экспортируют `codeUnits`. Преобразование содержит владеющие `operand`/`targetType`, `explicit`, `conversionKind`, необязательный `sourceType`. DOT/SVG подписывает литералы и преобразования. Копирование сохраняет факты и владеющие типы в новом снимке; после семантической правки нужно повторить разрешение. Специфичные для C++ литералы/операторы/преобразования не транслируются молча в Java: неподдержанный межъязыковой вывод отвергается, прежние Java-регрессии сохраняются.

[Сквозной контракт](e2e.ru.md#литералы-выражения-и-преобразования-25) отделяет модельные проверки профиля от переносимого нативного исполнения.

## Функции и аргументы по умолчанию (#26)

Ограничения имён в аргументах по умолчанию соответствуют принятой базе C++03/N1638: параметры (включая текущий) и локальные переменные запрещены даже внутри `sizeof`. Позднейшее послабление CWG 2082 не применяется; современные компиляторы могут принимать такие случаи в режиме `-std=c++03`. Основание в сохранённом тексте: 3.3.1/1, 3.4.1/11 и 8.3.6/7,9.


`ParameterDeclaration.defaultValue()` — необязательное **принадлежащее параметру** выражение только в месте, где значение по умолчанию написано. Диапазон и происхождение параметра включают это выражение. Объявления и определения функций сохраняют прежние типы результата/параметров, признак переменного числа аргументов, модификатор inline и деклараторы ссылок/массивов. Значения по умолчанию не входят в тип или сигнатуру функции.

`CallExpression.arguments()` содержит только написанные аргументы. Пропущенные аргументы разрешённого вызова представлены в `defaultArguments()`: каждый `DefaultArgument` содержит индекс с нуля `parameterIndex()`, видимое объявление-источник `declaration()` и его `parameter()`. `expression()` возвращает общее выражение этого параметра. Это ссылки без владения, а не копии синтаксиса или заранее вычисленные аргументы. Поэтому два вызова с пропуском в `void log(int level = next()); log(); log(2); log();` ссылаются на один исходный `next()`, а средний владеет явным аргументом. При исполнении каждый пропуск вычисляет значение независимо.

JSON вкладывает `defaultValue` в параметр, а непустой `defaultArguments` вызова содержит `parameterIndex`, `declarationId`, `parameterId`, `expressionId`. DOT показывает подписанные связи с объявлением, параметром и выражением. Копирование снимка перенаправляет связи внутрь копии. Генерация C++ печатает значения только при написанных объявлениях параметров и сохраняет пропуски в вызовах; правка с сохранением исходника не удаляет посторонние комментарии и вызовы макросов. Генерация Java отвергает значения по умолчанию и неподдержанные сигнатуры, а не стирает их.

Значения берутся из видимых объявлений, не из будущего определения или динамической цели. Вызовы через указатель на функцию не наследуют значения из объявления функции. Полные перегрузки/ADL (#30), виртуальная диспетчеризация и выбор значения по статическому типу (#29), межпроцедурные эффекты (#42) остаются отдельными задачами. См. [контракт E2E](e2e.ru.md#функции-и-аргументы-по-умолчанию-26).

## Классы, инициализация и время жизни (#27)

`Declaration.access()` хранит доступ каждого члена, `isFriend()` — дружбу отдельно
от владения и класса хранения. `ClassDeclaration.memberAccess()` остаётся начальной
секцией. У class/struct/union сохраняются члены, вложенные типы и `bases()`;
`BaseSpecifier` владеет написанным типом и хранит доступ и `isVirtual()`.
`VariableDeclaration.bitWidth()` владеет шириной именованного или безымянного
битового поля. Модификаторы static/mutable сохраняются. Написанное квалифицированное
имя внешнего определения сохраняется, а разрешение связывает его с членом класса.

`CallableDeclaration.kind()` различает обычную функцию, конструктор и деструктор.
Последним не добавляется вымышленный возвращаемый тип. `initializers()` конструктора
владеет узлами `MemberInitializer` с именем и аргументами в **написанном порядке**,
который не следует путать с порядком выполнения. `MemberInitializer.target()` — невладеющая ссылка на поле или написанное объявление класса/typedef базы; JSON содержит `targetId`. Поиск имени инициализатора исключает параметры конструктора, различает псевдоним базы и поле, скрывающее имя базы. Копирующий конструктор и
`operator=` остаются исходными объявлениями с наблюдаемыми телами.

`InitializationExpression` различает `DIRECT` со скобками, `AGGREGATE` с фигурными
скобками и типизированное создание `TEMPORARY`. Обычное `= expression` сохраняет
инициализацию копированием. Пустое создание временного — value-initialization;
отсутствующий инициализатор — default-initialization. Для определённых объектов
статической длительности отдельно указана нулевая фаза. `T x()` остаётся функцией,
а форма C++11 `T x{...}` отвергается. Генератор не подменяет эти формы друг другом.

`ClassSemantics` вычисляет неизменяемые невладеющие сведения по текущему снимку:

- `specialMembers(class)` описывает конструктор по умолчанию, копирующий конструктор,
  копирующее присваивание и деструктор состояниями `IMPLICIT`, `USER_DECLARED`,
  `SUPPRESSED` и ссылками на исходные объявления. Пользовательский конструктор
  подавляет неявный конструктор по умолчанию, но не остальные специальные функции.
  Неявная функция представлена описателем, а не вымышленным исходным узлом. API не
  обещает допустимость её определения для любого сочетания типов полей.
- `aggregate(class)` проверяет представленные условия агрегата C++03.
- `constructionOrder(class, constructor)` возвращает прямые невиртуальные базы,
  затем нестатические поля в порядке объявления и соответствующий написанный
  инициализатор, если он есть. `destructionOrder` разворачивает порядок подобъектов;
  тело деструктора выполняется раньше. При транзитивной виртуальной базе, неразрешённой базе или неполной иерархии API порядка явно отказывает; конструктор получает предупреждение `unsupported-constructor-flow`, частичный CFG не публикуется. Допустимый инициализатор косвенной виртуальной базы не объявляется неизвестным полем. CFG поддержанного конструктора упорядочивает написанные
  инициализаторы так же; DFG учитывает вычисление их аргументов.
- `initialization(project, variable)` возвращает длительность, фазы, класс и
  написанное выражение. `constructorCandidates` даёт исходные кандидаты с подходящим
  числом аргументов, не результат ранжирования перегрузок.
- `lifetimes(project)` различает выход из блока, завершение программы, конец полного
  выражения временного и продление до времени жизни непосредственно связанной
  ссылки. Это лексические факты, не трасса исполнения и не порядок между единицами.

JSON сохраняет новые узлы, доступ, friend и описатели специальных функций;
DOT/SVG — владение и ссылки. При известных сбоях ранжирования/триангуляции Graphviz генератор SVG повторяет тот же полный граф слева направо с прямыми линиями, не удаляя узлы, рёбра или подписи. Копирование перенаправляет ссылки, сведения класса после
правок вычисляются заново. Неподдержанная трансляция этих конструкций в Java явно
отвергается.

Поиск унаследованных членов и виртуальные базы/диспетчеризация (#29), полное разрешение перегрузок и проверка
доступа (#30), ABI/new/delete (#28), допустимость всех неявных определений,
необязательное устранение копирования и полный межпроцедурный анализ времени жизни
не заявлены. См. [обязательный сценарий](../src/test/resources/cpp03/classes-initialization/README.md).

При неподдержанной иерархии `FunctionFlow.complete()` равен false, списки рёбер пусты, JSON содержит `flowComplete: false`; DFG и unread-write не считают такой результат полным.

## Размеры объектов, приведения и выделение памяти (#28)

`SizeofExpression` и `TypeidExpression` владеют написанным типом либо выражением.
`sizeof` не вычисляет операнд. Вычисление полиморфного операнда RTTI и поиск во
время исполнения не заменяются вымышленными вызовами. `ConversionExpression.kind()`
различает `STATIC_CAST`, `DYNAMIC_CAST`, `CONST_CAST`, `REINTERPRET_CAST`,
`C_STYLE_CAST`; функциональная запись представлена типизированным
`InitializationExpression` формы `TEMPORARY`. Полная проверка допустимости
приведений, выполнение RTTI и выбор пользовательских преобразований не заявлены.

`NewExpression.type()` владеет выделяемым типом, включая границы `ArrayType`.
`placementArguments()` и `initializerArguments()` — отдельные списки дочерних
выражений; `hasInitializer()` различает `new T` и `new T()`.
`isGlobal()` и `isParenthesizedType()` сохраняют форму записи.
`DeleteExpression.operand()` — дочерний операнд, `isArray()` и `isGlobal()` —
признаки формы. Это исходные операции, а не синтетические вызовы функций
выделения, конструкторов или деструкторов. Поиск функций выделения, очистка при
исключениях и динамическое время жизни кучи не входят в эти синтаксические факты.

Генерация C++ сохраняет формы и приоритеты; генерация Java отказывается от них.
JSON содержит операнды, `conversionKind`, отдельные списки аргументов и признаки
формы; DOT различает приведения, placement new и delete[]. Копирование сохраняет
владение и перенаправляет семантические ссылки в копию.

Профиль отделяет номинальную идентичность типа от представления объекта.
`fieldAlignment` (`natural`, `packed1`, `unknown`), `aggregateAlignment`
(`maximum-field`, `unknown`), `tailPadding` (`alignment`, `unknown`) задают
размещение поддержанных агрегатов. По умолчанию используются естественное
выравнивание полей, максимум выравниваний и округление хвоста. Самостоятельный
профиль `inherits: none` без этих политик оставляет размещение неизвестным.
`packed1` — политика целевой платформы, не вставляемая pragma и не утверждение
о настройках компилятора на машине проверки.

`TypeSemantics.layout(ClassDeclaration, profile)`, `describe` и `sizeof` учитывают
полные поддержанные агрегаты, вложенные агрегаты и массивы. Статические поля
не занимают место в объекте; пустой агрегат занимает один байт. Union, базы,
виртуальные члены, неагрегаты, битовые поля, поля-ссылки, неразрешённое и
рекурсивное размещение остаются неизвестными. При восьмибитном байте и
четырёхбайтовом int размер `struct S { char a; int b; };` равен 8 при естественном
выравнивании на 4 и 5 при плотном на 1. Неизвестная политика сохраняет
`sizeof(S)` символически. `ArrayType.bound()` по-прежнему владеет `sizeof(S) + 1`
и ссылкой на объявление: повторный анализ с известным профилем может получить
9, не заменяя написанное выражение и не меняя исходный снимок. Переход long с
64 на 32 бита меняет sizeof с 8 на 4, но не сливает перегрузки int и long.

## Наследование и виртуальные методы (#29)

`BaseSpecifier` сохраняет каждую написанную непосредственную базу, доступ и
признак `virtual`. `CallableDeclaration.isPureVirtual()` хранит написанное `= 0`;
`virtual` остаётся в исходных модификаторах и не добавляется в переопределения.
Внешние определения сохраняют квалифицированное имя и связи с объявлениями.
`InheritanceSemantics.isVirtual(project, method)`, `overrides(project, method)` и
`overriddenBy(project, method)` выводят виртуальность и связи переопределения в
обе стороны по иерархии, независимо от наличия вызовов. Совпадение имени при
разных сигнатурах параметров не создаёт связи переопределения.

`CallExpression.target()` — статически выбранное объявление; `candidates()` и
`resolution()` описывают статический поиск. Написанные `arguments()` неизменны.
Пропущенные значения остаются отдельными ссылками `defaultArguments()` на
видимое статическое объявление, параметр и принадлежащее ему выражение.
Диспетчеризация не подменяет их значениями из возможной реализации.
`isVirtualDispatch()` и `virtualTargets()` отдельно описывают возможные реализации;
`virtualTargetsComplete()` — полноту этого анализа. Это невладеющие связи, не
клоны синтаксиса и не обещание о фактическом объекте во время выполнения.
После семантической правки нужно повторное разрешение, а не использование копии
старого анализа как нового результата. Квалифицированный вызов подавляет
виртуальную диспетчеризацию.

JSON разделяет `pureVirtual`/семантический `virtual`, `overridesIds`/
`overriddenByIds`, `staticTargetId`, `defaultArguments`, `virtualDispatch`,
`virtualTargetIds` и `virtualTargetsComplete`. DOT отдельно подписывает
статическую цель, значения по умолчанию, возможные реализации и оба направления
переопределения. Генерация сохраняет базы, `virtual`, `= 0`, квалифицированные
определения и пропущенные аргументы; Java отвергает эти формы C++.
Копирование сохраняет ссылки внутри нового снимка. Модель не выдумывает ABI,
размещение объекта, vtable, выполнение RTTI или единственную фактическую цель по
ссылке на базу. Полное ранжирование перегрузок, ADL и пользовательские
преобразования остаются #30.

Порядок конструирования имеет явный контекст вызова:
`ClassSemantics.constructionOrder(owner, constructor, ConstructionContext.COMPLETE_OBJECT)`
включает виртуальные базы в порядке конструирования наиболее производного
объекта; `ConstructionContext.BASE_SUBOBJECT` исключает их, поскольку за их
инициализацию отвечает наиболее производный объект. Перегрузка с двумя
аргументами использует `COMPLETE_OBJECT`; `destructionOrder` принимает тот же
контекст и обращает соответствующий порядок конструирования. Этот структурный
порядок не означает полное моделирование выполнения: CFG функции остаётся
неполным для виртуальной иерархии при неизвестном контексте вызова
конструктора/деструктора.

Несколько известных конечных переопределений одного виртуального базового
подобъекта дают ошибку `multiple-final-overriders` даже без вызовов. Собственное
переопределение производного класса, в том числе чистое, устраняет конфликт;
независимые невиртуальные подобъекты проверяются отдельно. Неполная или циклическая
иерархия не дополняется догадками. Внешние определения сохраняют virtual/pure
статус и аргументы по умолчанию внутриклассового объявления. Явная квалификация
вызова через объект подавляет диспетчеризацию. Вызов на текущем объекте внутри
конструктора/деструктора не достигает более производной реализации; для других
получателей сохраняется модель открытого мира.
Правки синтаксиса объявлений/баз через ProjectEditor консервативно очищают
сохранённые цели виртуальных вызовов во всём снимке; повторное разрешение
восстанавливает их. Копия без правок сохраняет и перенаправляет эти ссылки.

## Перегрузки, ADL и номинальная идентичность типов (#30)

Поддержанный выбор попарно сравнивает последовательности преобразований:
точное совпадение, продвижение, стандартное, пользовательское преобразование,
затем многоточие. Стоимости разных аргументов не суммируются: встречные
улучшения/ухудшения оставляют неоднозначность. Учитываются квалификаторы,
связывание ссылок, поддержанные пути производный–базовый, нулевые указатели,
допустимые аргументы по умолчанию и вариативность. Неизвестное преобразование
оставляет выбор неразрешённым. ADL добавляет связанные классы, базы и пространства
имён, включая скрытых друзей и пространство enum. Выбор недоступного члена
диагностируется, а не заменяется худшей доступной перегрузкой. Конструкторы
преобразования без `explicit` и функции преобразования участвуют при известной
поддержанной последовательности; `explicit` не даёт неявного преобразования
аргумента.

Выбор перегрузки опирается на номинальную идентичность типа C++, а не ширину
хранения. При 32-битных `int` и `long` вызов `f(1)` выбирает `f(int)`, а
`f(1L)` — `f(long)`. Написанные типы, употребления typedef и суффиксы литералов
сохраняются при генерации; одинаковый диапазон не делает типы псевдонимами.

Написанный оператор остаётся владельцем синтаксиса. В `price + tax` для `Money`
узел `AddExpression` по-прежнему владеет левым и правым операндами.
`Expression.operatorTarget()` — невладеющая ссылка на выбранное объявление;
`operatorCandidates()` и `operatorResolution()` сохраняют альтернативы и
неоднозначность без выдуманной единственной цели. Они отделены от обычной
цели `CallExpression.target()` и её кандидатов. Копирование переводит ссылки
в новый проект. Исходник сохраняет `price + tax`, а не заменяет его вызовом
`operator+(price, tax)`.

JSON содержит `operatorResolution`, `operatorCandidateIds` и, при выборе
реализации, `operatorTargetId`. Это ID назначений, не повторно вложенные дети.
DOT добавляет рёбра `operator implementation` или кандидатов к обычным
пунктирным ссылкам. Написанные номинальные типы и `1L` видны в том же снимке.

Функция преобразования — `CallableDeclaration` вида `CONVERSION`. Её
владеющий `conversionType()` хранит написанный conversion-type-id и
экспортируется как `conversionType`; `returnType()` отсутствует. Генератор
пишет `operator int() const`, но не `int operator int() const`.
Пользовательские операторы и функции преобразования не переводятся в Java
молчаливой подменой смысла.

Выбранный перегруженный логический оператор вычисляет оба операнда как
функциональная операция. Встроенные `&&` и `||` сохраняют короткое замыкание.
Анализ и свёртка не должны стирать выбранную пользовательскую реализацию или
считать её встроенной арифметикой только из-за написания `+`, `&&` или `||`.
Контракт не заявляет полного разрешения шаблонных перегрузок, полного ABI или
угаданной семантики неизвестных внешних/пользовательских тел.

### Инструкции, исключения и служебные вершины потока C++03 (#31)

В модели есть отдельные `EmptyStatement`, `DoWhileStatement`, `ForStatement`,
`SwitchStatement`, `CaseStatement`, `BreakStatement`, `ContinueStatement`,
`GotoStatement`, `LabelStatement`, `TryStatement` и `CatchClause`.
`ForStatement` владеет списком инициализаторов, необязательными условием и шагом,
а также телом. `CaseStatement` владеет следующей инструкцией; отсутствие значения
обозначает `default`. Вложенные метки и соседние `case` сохраняют порядок исходника
и не превращаются в отдельные области. `ConditionDeclarationExpression` владеет
переменной условия. У `ThrowExpression` отсутствие `value()` означает повторное
возбуждение, у `CatchClause` отсутствие параметра означает `catch (...)`.

У функций и функциональных типов `hasExceptionSpecification()` отличает отсутствие
спецификации от явного `throw()`, а `exceptionTypes()` хранит перечисленные типы.
`functionTryBlock()` и `handlers()` сохраняют форму
`Guard() try : member() { ... } catch (...) { ... }`.
`bodyComplete()` и `BlockStatement.complete()` отмечают оборванный синтаксис.
Его можно экспортировать, но нельзя генерировать как исходник, в том числе отдельно
от файла с ошибкой.

`AuxiliaryFlowVertex` не является узлом AST. Он хранит владельца-функцию, устойчивый
индекс внутри потока, вид `EXCEPTIONAL_EXIT`, `TERMINATE_EXIT`, `IMPLICIT_CONSTRUCTOR` либо `IMPLICIT_DESTRUCTOR` и невладеющие
ссылки на объект и выбранный конструктор/деструктор, если они известны. JSON назначает таким
вершинам ID после исходного синтаксиса, но до каталога конфигурации: различия
атрибуции API/CLI не сдвигают ID потоков. Они помещаются в `flowVertices` функции:
`ownerId`, `index`, `objectId`, `constructorId` либо `destructorId`. Рёбра CFG используют эти же ID.
DOT использует отдельное пространство имён из владельца и индекса, подписывает
ссылки на объект и конструктор/деструктор. Отсутствие ссылки на деструктор не означает явного
вызова или наличия пользовательского объявления деструктора.
`flowComplete: false` отмечает неполный/недоступный анализ; у сохранённого полного
потока флаг по прежнему контракту опускается. Отсутствие всей информации о потоке
само по себе не доказывает полноту анализа.

Генератор идёт только по владеющему синтаксису, сохраняет автоматическую длительность
хранения и не вставляет вызовы из неявных вершин очистки. Исключения C++, объявления
в условиях и `goto` не переводятся на Java. Общие формы пустой инструкции, циклов,
`break`/`continue` и `switch` доступны, если вложенный синтаксис принадлежит общему
поддерживаемому подмножеству.

Выбранная функция неявного конструктора доступна через `constructor()` и
`constructorId`, а не через `destructor()` или `destructorId`. Копирование графа
с диагностикой переподключает эти ссылки.

Текущий CFG явно отмечает соответствующий поток неполным и не публикует вводящие
в заблуждение частичные рёбра для следующих неподдержанных случаев:

- Массивы объектов классов, включая частично созданные массивы.
- Явные и неявные временные prvalue-объекты классов, требующие учёта времени жизни.
- Вложенный throw внутри группы выражений с неустановленным порядком вычисления.
- Неизвестное или запрещённое выходящее исключение при непустой спецификации:
  пользовательский обработчик `unexpected` может изменить результат.
- Пути конструктора/деструктора с зависимой от контекста обработкой виртуальных баз.

Выходящее исключение при пустой спецификации `throw()` ведёт в `TERMINATE_EXIT`.
Второе исключение из деструктора во время раскрутки стека также ведёт в
`TERMINATE_EXIT`, а не в обычный обработчик или исключительный возврат.
Неполнота анализа сама по себе не делает сохранённый AST или исходник ошибочным;
синтаксические и семантические ошибки по-прежнему отдельно блокируют генерацию.
Флаг полноты не означает покрытия всех исключений и правил времени жизни C++.

## Физические комментарии и явное удаление (#32)

Комментарии C++ — физические данные, а не синтаксические токены. Структурный разбор Doxygen описан ниже.
`Comment` хранит `Kind.LINE`/`Kind.BLOCK`, точный физический `text()` с разделителями,
склейками строк и внутренними переводами строк, а также полуоткрытый физический
`range()`. `SourceFile.comments()` единолично владеет каждым физическим комментарием,
включая захваченные заголовки и неактивные ветви. `Node.commentReferences()` задаёт
невладеющие поясняющие связи `HAS_COMMENT`, отдельно от семантических `references()`.
Группа последовательных ведущих строчных комментариев может пояснять следующее
объявление; хвостовой комментарий группы деклараций относится к последней;
комментарий после запятой аргументов — к следующему аргументу. Это эвристика, не
разбор документации. Копирование и редактирование перенаправляют ссылки в новый
снимок. Поведение парсера Java не меняется: захват комментариев для него не добавлен.

JSON вкладывает комментарии один раз в `comments` исходного файла с `commentKind`,
`text` и обычными координатами. Поясняющие рёбра имеют `kind: "HAS_COMMENT"` и ID
назначения. DOT показывает номерные рёбра владения и пунктирные `HAS_COMMENT`.
Обход посещает каждый комментарий один раз; поясняющие ссылки не становятся
дополнительными синтаксическими детьми.

Обычные `Source.files`/`Cpg.sources` сохраняют комментарии захваченного C++:
неизменённый текст побайтно совпадает, включая неактивные ветви. Проверяемая правка
AST оставляет окружающий текст; при замене целого поддерева его внутренние
комментарии сохраняются один раз перед заменой. `Source.render` — каноническая
печать фрагмента, а не сохранение разметки: принадлежащие и поясняющие комментарии
печатаются один раз перед фрагментом с исходным текстом для обеих целевых языков.
Для сохранения физического расположения используется файловая генерация. Правки
каталога комментариев в сохраняющей генерации явно отвергаются, а не теряются;
каноническая печать позволяет вывести каталог после ручной правки.

`com.kniazkov.cpg.utilities.Comments.remove(Project)` явно создаёт отдельный проект
C++ без комментариев. Утилита материализует проверенные правки AST, очищает все
захваченные физические файлы, включая заголовки и неактивные ветви, затем повторно
разбирает и анализирует их с исходной конфигурацией сборки и временем трансляции.
Исходный снимок и содержимое литералов не меняются. Перегрузка
`Comments.remove(String file, String source)` выполняет лексическую очистку одного
файла. Пробелы не позволяют склеить соседние токены; сохранённые/склеенные физические
переводы строк удерживают семантику строк препроцессора. Проектная утилита требует
полный захваченный C++ и отвергает Java, отсутствие provenance и ошибочные снимки.
Чтение, анализ, генерация и CLI никогда не запускают её автоматически.

Каноническая печать сохраняет исходный текст каждого комментария как точную
подстроку, но может добавлять разделяющие переводы строк. В частности, комментарий
`//` на EOF с конечным `\` или `??/` требует двух переводов строк перед последующим
кодом, иначе склейка строк поглотит этот код; диапазон повторно распознанного
комментария поэтому может отличаться. Неизменённая физическая файловая генерация
ничего не переносит и остаётся точной. Генерация Java отвергает написания комментариев,
в которых склейка/разделители C++ или Unicode escapes Java могут превратить текст
комментария в код, вместо незаметного изменения смысла.

## Связанная документация Doxygen и безопасное переименование (#33)

`Comment.documentationEntries()` владеет упорядоченными `DocumentationEntry` для
`@brief`, `@param`, `@tparam`, `@return` и вариантов с обратной косой чертой.
Полный физический текст комментария остаётся основным: неизвестные команды и
свободный текст сохраняются. Запись содержит вид, имя, описание, диапазон тега и
точный диапазон имени параметра. `bindings()` хранит конкретное объявление функции
и целевой параметр (включая шаблонный) в каждом контексте include/configuration.
Это невладеющие ссылки, перенаправляемые при копировании. JSON экспортирует порядок,
ID объявления/цели и контекст единицы трансляции/include; DOT показывает владение и
привязки. Неизвестное имя получает диагностику, а не угаданную цель.

`analysis.Documentation.forDeclaration(project, callable)` собирает документацию
связанных объявлений и определения; `commentsForDeclaration` сохраняет отдельные
комментарии и оба brief, устраняя повтор одного физического текста заголовка.
`forParameter(project, parameter)` сопоставляет параметры по позиции, даже если
прототип использует `count`, а определение — `n`. Запрос не меняет исходную привязку.

`utilities.Documentation.renameParameter(project, parameter, "amount")` возвращает
новый независимый проект. Изменяются только идентификатор выбранного параметра,
связанные использования в коде и имена точно привязанных тегов. Переименование
заголовочного `count` не затрагивает `n`; переименование `n` не меняет `@param count`.
Свободный текст сохраняется побайтно. Совместимые повторения заголовка изменяются
вместе. Конфликтующие контексты, макрорасширения, возможный захват имени, отсутствие
provenance и ещё не применённые синтаксические правки отвергаются. Захваченные файлы
повторно разбираются с исходными конфигурациями и временем трансляции; диапазоны,
привязки и анализ вычисляются заново. Утилита не пишет файлы и не ослабляет общий
запрет произвольной правки каталога комментариев. Предыдущие правки сначала нужно
сгенерировать и повторно разобрать.

Минимальные объявления шаблонных функций имеют `templateParameters()` с узлами
`TemplateParameterDeclaration`, методами `name()`/`keyword()` (`class`/`typename`),
ссылками из зависимых написанных типов, генерацией C++ и экспортом JSON/DOT.
Переименование шаблонного параметра обновляет связанные типы и имя `@tparam`.
Общая инстанциация, специализация и вывод аргументов шаблона этим не реализуются.

## Базовые шаблоны и зависимые имена (#34)

Написанный шаблон сохраняет обобщённое тело. `templateParameters()` функции и
класса владеет упорядоченными параметрами типов, значений и шаблонов, вложенными
параметрами и аргументами по умолчанию. `TemplateArgument` владеет типом либо
выражением. Сегменты `NamedType` сохраняют квалификатор, аргументы и маркеры
`typename`/`template`; template-id выражений также хранит аргументы. Каноническая
генерация разделяет закрывающие `>` в соответствии с C++03.

В обобщённой функции `template<class T> unsigned long count(const T& x)` вызов
`x.size()` остаётся неразрешённым зависимым вызовом. Базовая подстановка типов
создаёт отдельный элемент `Project.templateInstances()` с копией функции и типами
аргументов; `origin()`, `cause()` и `source()` — невладеющие ссылки. Исходное тело
не изменяется. Первоначальный контракт #34 сообщал `basic-type-substitution` и
`complete = false`; описанный ниже контракт #35 заменяет этот начальный статус,
не заявляя полного соответствия всем правилам C++03.

Каталог #36 заменяет минимальную предпосылку #34. Полные встроенные данные
деклараций находятся вне возвращаемого Project. `standardLibrary()` — необязательная
владеющая коллекция `StandardLibrary` с заголовками `headers()`; совместимый метод
`librarySources()` возвращает невладеющее плоское представление этих же файлов.
Активные системные include имеют связь `libraryHeader()`. Физический заголовок из
настроенного пути остаётся обычным исходным файлом. Видимость учитывает единицу
трансляции и позицию include.

Публикуются только востребованные объявления, их владельцы, выбранные специализации
и необходимые зависимости. Просмотр кандидата перегрузки не делает его востребованным.
Заголовок без использований может остаться пустым; после удаления последнего include
и использования исчезает вся коллекция. Полный текст и токены каталога не попадают
в provenance оставленного заголовка. Общий шаблон класса находится в заголовке,
конкретные типы — в `classTemplateInstances()`, причём каждый содержит только
востребованные конкретные члены. `Declaration.templateOrigin()` связывает их с
исходными объявлениями. Выбранные библиотечные конструктор и деструктор доступны
через `VariableDeclaration.constructorTarget()` и `destructorTarget()`.

`OpaqueLibraryType` хранит идентичность и известную категорию типа с зависимым от
реализации представлением, не выдумывая размер, размещение или определение класса.
Тел реализации контейнеров и поведения аллокатора в каталоге нет. Разрешённый вызов
без модели поведения остаётся C++-вызовом; DFG сохраняет входящие определения и
учитывает возможные записи в объект, переданные по ссылке данные и доступное хранилище.
Непрозрачные создание и уничтожение также могут менять доступные данные в своих
точках CFG. Источник такой зависимости DFG — объявление объекта со связями целей
времени жизни, а не выдуманный явный вызов.
Покрытие деклараций и поведения по семействам описано в `library-catalogue.ru.md`.
Обычному анализу нужен только JDK; нативные проверки используют настоящие заголовки.

JSON отдельно экспортирует написанный синтаксис, каталог и экземпляры с ID
невладеющих связей. `standardLibrary` владеет заголовками, совместимое поле
`librarySources` содержит их ID. JSON и DOT экспортируют типизированные связи
`LIBRARY_HEADER`, `TEMPLATE_ORIGIN`, `CONSTRUCTOR_TARGET`, `DESTRUCTOR_TARGET`.
DOT отмечает каталог и экземпляры. Копирование перепривязывает
связи к новому снимку. Физическая генерация проходит только по `Project.files()`:
сохраняет include и обобщённое тело, не печатает каталог или тела экземпляров.
Границы проверяют `TemplateExportTest` и шаблонный сценарий корпуса.

Анализ экземпляра использует язык и профиль платформы запросившей его единицы
трансляции. CFG/DFG, преобразования типов, нормализация и свёртка обходят отдельное
конкретное тело, не изменяя общий шаблон.

## Синтаксис специализаций и экспорт инстанцирований (#35)

`templateKind()` отличает первичный шаблон, полную специализацию, частичную
специализацию класса и явное инстанцирование от обычного объявления.
`templateArguments()` владеет написанными аргументами специализации;
`hasTemplateArguments()` сохраняет и пустое `<>`. `exportedTemplate()` хранит
написанный C++03 `export`. Каноническая генерация печатает эти объявления,
включая `template <>` и `template struct Box<int >;`. Физическая генерация не
добавляет синтетические тела экземпляров и объявления библиотечного каталога.

`TemplateInstance.requests()` перечисляет все непосредственные места запроса,
включая объявления явного инстанцирования. `causes()` оставляет только вызовы;
совместимый `cause()` возвращает первый вызов либо null для экземпляра,
потребованного только явным инстанцированием. JSON содержит `requestIds` и
`causeIds`, а при наличии вызова также прежнее `causeId`. Ребро `CALL_TARGET`
ведёт от вызова к вызываемому объявлению; `INSTANTIATION_CAUSE` ведёт от
запросившего узла к обёртке экземпляра. Обратное `INSTANTIATION_REQUEST` позволяет
найти все запросы. Это разные отношения. Вложенный запрос принадлежит конкретному
внешнему телу, а не неизменённому обобщённому шаблону. Экземпляры классов отдельно
принадлежат `Project.classTemplateInstances()`: `origin()` указывает на первичный
шаблон, `selected()` на выбранное объявление, `declaration()` владеет конкретным
классом. JSON экспортирует аргументы и места запроса в том же снимке. Все ID
ссылок обязаны указывать на узлы проекта; висячее ребро блокирует экспорт.

Диагностики узлов содержат `code`, `severity`, `message`, `primaryRange` и, при
наличии, упорядоченные `relatedRanges`. Первичная позиция ошибки инстанцирования
относится к ошибочному выражению, а не вызывающему коду; сообщение содержит
подставленный тип. Позиции запросов идут от непосредственного внешнего экземпляра
к его вызывающему коду. Это семантические диагностики, отдельные от
`parseProblems` и групп препроцессорных вхождений. Их следует читать и без CFG/DFG.

Сохранённый маркер `export` не доказывает поддержку раздельной трансляции шаблонов.
`scripts/probe-cpp03-export.sh` создаёт заголовок с объявлением, отдельное
экспортированное определение и клиентскую единицу. GCC 14.2 и Clang 19.1.7
предупреждают, что экспортируемые шаблоны не поддержаны/маркер проигнорирован,
затем линковка требуемой специализации завершается ошибкой. Добавление явного
инстанцирования даёт успешную сборку и запуск в обоих компиляторах, но это
контрольный пример, не реализация `export`. Совместное использование видимого
через общий заголовок определения в двух TU проверяется отдельно. Из этих
результатов нельзя заключать о полной поддержке C++03 exported-template lookup.

Реализованный путь вывода для функций работает с параметрами типов, явными
целочисленными аргументами, выводом по границам массивов и шаблонными параметрами
из структурированных template-id. Подстановка в непосредственном контексте
сигнатуры проверяется до выбора кандидата.
Отсутствующий зависимый вложенный typedef может исключить кандидата (SFINAE),
тогда как ошибочный доступ к члену в выбранном конкретном теле остаётся ошибкой.
Это не заявление о полном выводе нетиповых/шаблонных параметров функций, всех
формах expression SFINAE или полном двухфазном поиске. Выбор специализации класса
сопоставляет структурированные аргументы и сравнивает частичные специализации
выводом в обоих направлениях; несравнимые подходящие варианты дают диагностику,
а не выбираются по порядку в файле. Полные специализации и явные инстанцирования
остаются отдельными написанными объявлениями. Частичная специализация функций
отвергается. Ограничение ресурсов класса имеет отдельный код
`template-instantiation-limit`, вложенных функций — `template-instantiation-depth`.
Исчерпание бюджета не означает успешного полного анализа.
`unsupported-export-template` сообщает о семантической границе, хотя написанный
маркер export сохраняется при круговом проходе.

`TemplateInstance.structuredArguments()` владеет упорядоченными узлами
`TemplateArgument` видов TYPE, VALUE и TEMPLATE. Совместимый `arguments()`
возвращает уже принадлежащие этим узлам типы, а не отдельные копии, и пропускает
аргументы-значения. JSON вкладывает каждый узел один раз в `structuredArguments`,
добавляя `structuredArgumentIds` для обёрток и `argumentIds` для совместимого
представления типов. Второго вложенного массива `arguments` у экземпляра функции
нет. У экземпляров классов сохраняется свой структурированный массив `arguments`.
DOT использует то же единственное дерево владения и подписывает вид аргумента.
Копии сохраняют отношения обёрток и содержимого, перенаправляя ссылки в новый
снимок. `TemplateInstantiationExportTest` проверяет уникальность JSON ID для
всех трёх видов аргументов функций и отсутствие лишних тел в исходниках.

Экземпляр функции сообщает `status = instantiated`, только когда тело существует
и полно, не содержит ERROR-диагностик, зависимых выражений и неразрешённых вызовов;
иначе статус равен `incomplete-instantiation`. `complete()` отражает то же
условие конкретного экземпляра. Это локальный результат анализа, а не заявление
о реализации всех правил вывода и инстанцирования C++03.

`Project.hasErrors()` учитывает семантические находки уровня ERROR вместе с
ошибками разбора. Для различения успешно разобранного, но семантически
недопустимого исходника используйте `parseProblems().isEmpty()`.
`semanticDiagnostics()` возвращает неизменяемые находки независимо от построения
потоков, включая упорядоченные позиции запросов инстанцирования. Ошибки лимита
ресурсов, прикреплённые к корню, сохраняются после проходов CFG/DFG.

## Общая семантика vector (#37)

Снимки GREEN/FOLDED владеют `dynamicArrayTypes()` и `dynamicArraySemantics()`.
Это общие семантические узлы, а не замена написанного C++-дерева. Тип ссылается на
конкретный доверенный библиотечный класс, тип элемента и написанные места типа.
Операция хранит исходный узел, объект назначения, упорядоченные источники,
общий тип и выбранную C++-цель. JSON экспортирует ссылки, DOT — типизированные
рёбра `COMMON_TYPE`, `COMMON_OPERATION`, `SOURCE`, `DESTINATION`, `CPP_TARGET`,
`ELEMENT_COPY_CONSTRUCTOR`. Генерация сохраняет написание vector и вызовов;
понижение в контейнеры Java этими узлами не заявляется.

Для обычного `std::vector<T, std::allocator<T> >` различаются EMPTY, COUNT, FILL,
RANGE, COPY, ASSIGN_COPY, ASSIGN_FILL, ASSIGN_RANGE и APPEND. Отбор основан на
разрешённой библиотечной идентичности и перегрузке, не на имени метода. Для
скалярных элементов доступны эти операции; диапазоны пока требуют указателей.
Добавление, заполнение и копирование Record выбирают доступный явный конструктор
копирования из `const T&`, если он есть, и сохраняют ссылку на его эффекты. Для
неявного копирования не выдумывается объявление: эффекты подобъектов и деструкторов
учитываются консервативно. Точное
число внутренних копий, стратегия выделения, рост ёмкости и глубокое копирование

В DFG источники читаются общей операцией, которая становится новым определением
контейнера. Присваивание изменяет прежний объект и видно через ссылки на него;
копирование создаёт отдельный контейнер. Элементы-указатели сохраняют идентичность
источника и могут разделять объект назначения. Доступные эффекты конструктора
копирования учитываются консервативно. Правки синтаксиса, целей, сигнатур или
происхождения сбрасывают производные факты; повторный анализ строит их заново.

Прокси `vector<bool>`, пользовательский аллокатор, явно переданные аргументы
аллокатора, пользовательские итераторы, создание Record по количеству и
присваивание Record сохраняют разрешённые C++-операции, если эквивалентность общей
модели не установлена. Неизвестные библиотечные эффекты остаются консервативными.
Доступ к элементам, размер/ёмкость, действительность итераторов, вставка/удаление
и swap относятся к отдельным группам #38.
