# Модель графа и анализ программ

[English version](model-guide.en.md) · [README](../README.md)

Этот справочник описывает публичный API и грамматику, реализованные на 4 ноября 2026 года. Примеры рассчитаны на Java 21. При добавлении конструкции обновляй обе версии справочника, таблицу покрытия в конце и соответствующий тест парсера или CLI.

## Получить снимок проекта

```java
import com.kniazkov.cpg.Cpg;
import com.kniazkov.cpg.model.*;
import java.nio.file.Path;
import java.util.*;

// Внутри метода, при запуске из корня репозитория
Project project = Cpg.read(Path.of("examples/unread-write/java"),
        new Cpg.Options(Language.JAVA, Cpg.Stage.RESOLVED));
SourceFile file = project.files().getFirst();
```

Пример читает папку с программой, где первое значение переменной `score` перезаписывается до чтения. Чтение папки нерекурсивное, на запуск выбирается один язык. Файлы обрабатываются в порядке имён. Ошибка разбора даёт `parser.ParseException` с именем файла, строкой и столбцом. Успешный вызов возвращает целый неизменяемый проект.

| Стадия | Какой снимок получишь |
|---|---|
| `PARSED` | Исходное синтаксическое дерево с позициями. `Exit` уже существует. Разрешение имён и анализ ещё не запускались. |
| `RESOLVED` | Разрешённые имена и вызовы, CFG, DFG и диагностика исходных конструкций. Эту стадию удобно выбирать для исследования исходника. |
| `GREEN` | После разрешения имён распознанный консольный вывод заменён на `PrintStatement`. Потоки и предупреждения описывают получившееся дерево. |
| `FOLDED` | Дополнительно свёрнута безопасная константная арифметика. Потоки и предупреждения вычислены для итогового дерева. Стадия CLI по умолчанию. |

## Структура и свойства узла

Корень `Project` владеет списком `files()`. Каждый `SourceFile` хранит путь, язык и упорядоченные элементы `items()`. Ниже находятся объявления (`Declaration`), инструкции (`Statement`), выражения (`Expression`) и записи типов (`TypeNode`). Это отдельные ветви общей иерархии `Node`.

| API | Назначение и пример |
|---|---|
| Именованные геттеры | `BinaryExpression.left()/right()` дают операнды, `VariableDeclaration.name()` — имя, `initializer()` — возможный инициализатор. `BlockStatement.items()` содержит объявления и инструкции в порядке исходника. |
| `children()` | Неизменяемый упорядоченный список детей. У листа он пуст. Для функции или метода последним ребёнком всегда идёт её собственный `exit()`. |
| `references()` | Разрешённые ссылки на другие узлы снимка. У `NameExpression` и `CallExpression` конкретную цель удобнее читать через `target()`. Для внешнего или неоднозначного имени цель может отсутствовать. |
| `range()` | `Optional<SourceRange>` даёт полный путь и полуоткрытый интервал исходника. Строки и столбцы с 1, смещения с 0. Столбцы и смещения в единицах UTF-16. У синтетического `Exit` диапазона нет. Свёрнутый литерал сохраняет диапазон исходного выражения. |
| `languages()`, `source(target)` | Допустимые языки непосредственной генерации поддерева и его текст. Для целых выходных файлов и адаптации точек входа используй `Cpg.sources(project, target)`. |
| `diagnostics()` | Неизменяемый список замечаний к конкретному узлу. Пустой список означает отсутствие прикреплённых замечаний на выбранной стадии. |

Обязательный ребёнок доступен напрямую. У необязательного ребёнка тип результата — `Optional`, у повторяющихся элементов — список. Например, выражение в `return x;` доступно через `ReturnStatement.value()`, а `return;` даёт `Optional.empty()`.

```java
project.walk(new NodeVisitor() {
    @Override public void visit(VariableDeclaration variable) {
        String type = variable.type()
                .filter(NamedType.class::isInstance)
                .map(NamedType.class::cast).map(NamedType::name).orElse("?");
        System.out.println(type + " " + variable.name());
    }
});
```

`accept(visitor)` вызывает обработчик одного узла. `walk(visitor)` проходит дерево в глубину, посещая родителя перед детьми. Обработчик семейства, например `visit(BinaryExpression)`, получает и сложение, и вычитание, если их перегрузки не переопределены. Обход дерева не следует по ссылкам на объявления или по рёбрам потоков.

## Обход CFG и DFG

Оба набора рёбер находятся в `project.flows()`. Каждый `FunctionFlow` описывает одну функцию или метод с телом. `entry()` возвращает объявление, а `exit()` — тот же объект, что и `entry().exit()`. Границы функций не пересекаются. Рекурсивный вызов может ссылаться на объявление функции через `CallExpression.target()`.

**CFG. Какие инструкции могут исполниться следующими?** У ребра `control()` есть `from()`, `to()` и `kind()`. Виды — `ENTRY`, `NEXT`, `TRUE`, `FALSE`, `BACK`, `RETURN`. Для ветвления вершиной служит выражение условия. Из `return` переход ведёт к общему выходу. Недостижимая инструкция остаётся в дереве, но в CFG к ней нет пути от входа.

```java
for (FunctionFlow flow : project.flows()) {
    Map<FlowVertex, List<FunctionFlow.ControlEdge>> outgoing = new IdentityHashMap<>();
    for (var edge : flow.control())
        outgoing.computeIfAbsent(edge.from(), v -> new ArrayList<>()).add(edge);

    Set<FlowVertex> seen = Collections.newSetFromMap(new IdentityHashMap<>());
    Deque<FlowVertex> pending = new ArrayDeque<>();
    pending.add(flow.entry());
    while (!pending.isEmpty()) {
        FlowVertex current = pending.removeFirst();
        if (!seen.add(current)) continue;
        for (var edge : outgoing.getOrDefault(current, List.of())) {
            System.out.println(current.getClass().getSimpleName() + " --" + edge.kind()
                    + "--> " + edge.to().getClass().getSimpleName());
            pending.addLast(edge.to());
        }
    }
}
```

Множество посещённых вершин позволяет закончить обход даже при обратном ребре цикла. Для обратного обхода индексируй по `to()`, начни с `exit()` и переходи к `from()`.

**DFG. Что даёт значение этому чтению?** Ребро `VALUE` направлено от значения операнда к потребителю, например от литерала к инициализируемой переменной. Ребро `DEFINITION` идёт от конкретной записи к чтению имени. В примере с `score` у чтения при выводе `target()` указывает на объявление `int score = 1;`, а входящее `DEFINITION` — от присваивания `score = 2`.

```java
for (FunctionFlow flow : project.flows()) {
    Map<Node, List<Node>> writesForRead = new IdentityHashMap<>();
    for (var edge : flow.data()) {
        if (edge.kind() == FunctionFlow.Dependency.DEFINITION)
            writesForRead.computeIfAbsent(edge.to(), n -> new ArrayList<>()).add(edge.from());
    }
    flow.entry().walk(new NodeVisitor() {
        @Override public void visit(NameExpression use) {
            for (Node write : writesForRead.getOrDefault(use, List.of()))
                System.out.println(use.name() + " <- " + write.getClass().getSimpleName()
                        + " " + write.range());
        }
    });
}
```

После слияния ветвей возможны несколько записей для одного чтения. Обратное ребро цикла может принести запись с предыдущей итерации. Чтобы найти все зависимые значения, используй тот же обход с очередью, что и для CFG, но построй индекс по `from()` из `flow.data()` и начни с интересующего узла. Для поиска всех источников результата разверни направление. Сравнивай узлы по идентичности внутри одного снимка.

Следующий фрагмент для каждого присваивания считает другие узлы, достижимые по исходящим рёбрам DFG обоих видов. В программе со `score` путь от второй записи проходит через чтение имени к вызову вывода.

```java
for (FunctionFlow flow : project.flows()) {
    Map<Node, List<Node>> consumers = new IdentityHashMap<>();
    for (var edge : flow.data())
        consumers.computeIfAbsent(edge.from(), n -> new ArrayList<>()).add(edge.to());

    flow.entry().walk(new NodeVisitor() {
        @Override public void visit(AssignmentExpression write) {
            Set<Node> reached = Collections.newSetFromMap(new IdentityHashMap<>());
            Deque<Node> queue = new ArrayDeque<>();
            queue.add(write);
            while (!queue.isEmpty()) {
                Node producer = queue.removeFirst();
                if (!reached.add(producer)) continue;
                for (Node consumer : consumers.getOrDefault(producer, List.of()))
                    queue.addLast(consumer);
            }
            System.out.println(write.range() + " -> " + (reached.size() - 1));
        }
    });
}
```

## Результаты проходов и редактирование

Данные проходов доступны через типизированные методы. Разрешение имён заполняет `target()`, анализ потоков — `Project.flows()`, диагностический проход — `Node.diagnostics()`. Нормализация и свёртка меняют само дерево: например, вместо вызова вывода появляется `PrintStatement`.

```java
project.walk(new NodeVisitor() {
    @Override public void visit(Node n) {
        for (Diagnostic d : n.diagnostics()) {
            String location = n.range().map(r -> r.file() + ":" + r.start().line()
                    + ":" + r.start().column()).orElse("?");
            System.out.println(location + " " + d.severity() + " [" + d.code() + "] " + d.message());
        }
    }
});
```

Правило `unread-write` ставит `WARNING` на конкретную инициализацию или присваивание, если значение не достигает чтения. В примере предупреждение относится к первой записи `score`. Для автоматизации используй стабильный `code()`, для человека — `message()`. В JSON диагностике соответствуют `code` и `severity`, а исходящие рёбра в `edges` содержат вид и числовой ID цели. ID назначаются при экспорте конкретного дерева; в Java API используются прямые ссылки.

Узел создаётся через вложенный строитель: `IntegerLiteral.create().setValue(2).build()`. Для правки вызывай `edit()`, меняй строитель и получай новый снимок через `build()`. После правки всего проекта прежние потоки и предупреждения сбрасываются. Если изменения затронули имена, снова разреши их; затем вычисли анализ для нового снимка. Например:

```java
Project edited = project.edit().build();
Project resolved = com.kniazkov.cpg.analysis.NameResolver.resolve(edited);
Project analyzed = com.kniazkov.cpg.analysis.UnreadWrites.analyze(resolved);
```

Для отдельных задач есть `ControlFlow.analyze` и `DataFlow.analyze`; перед DFG нужны разрешённые имена. `UnreadWrites.analyze` строит необходимый DFG. Все эти проходы возвращают результат; дальнейшие запросы делай к возвращённому проекту.

## Какие конструкции читаются из исходника

Таблица описывает штатный вход через `Cpg.read`. Наличие Java-класса в модели само по себе не означает, что соответствующий токен уже распознаётся парсером.

| Конструкция | Java (`.java`) | C++ (`.cpp`) |
|---|---|---|
| Верхний уровень | `class C { … }`, `public class C { … }` | `class C { public: … };`, `int main() { … }` |
| Метод класса | `public static void main(String[] args)` | `static void main()` |
| Локальные объявления | `int x = expression;` | `int x = expression;` |
| Литералы и арифметика | Десятичные целые в диапазоне signed 32-bit, скобки, унарные и бинарные `+`, `-`, бинарные `*`, `/` | То же, плюс `<<` |
| Запись и сравнение | `=` (включая цепочки), `== != < <= > >=` | То же |
| Доступ и вызов | `obj.member`, `f(a, b)`, `C.main(args)` | `obj.member`, `f(a, b)`, `C::main()` |
| Управление | Блоки, `if`, `if/else`, `while`, `return;`, `return expr;` | То же |
| Комментарии и директивы | `//`, `/* … */` | Оба вида комментариев, сохранение `#include <…>`, `#include "…"` |
| Озеленение вывода | `System.out.println(x)` | `std::cout << x << std::endl` |

Имя параметра Java `main` произвольное. Таблица описывает разбор синтаксиса; проверка типов и семантики языка компилятору не эквивалентна. Заголовки C++ не раскрываются. Произвольные сигнатуры функций, конструкторы, шаблоны, массивы общего вида, строки, `for`, `break` и `continue` пока вне входной грамматики.

**Есть классы узлов, но ещё нет разбора из текста:** остаток `%`, правый сдвиг `>>`, логическое отрицание `!`, взятие адреса `&x`, разыменование `*p`, доступ `p->field`. Для C, Python, JavaScript и Ascend C входных парсеров пока нет. Межъязыковая генерация проверена для небольших Java/C++ программ с поддерживаемыми формами `main` и консольного вывода; границы перевода описаны в README.

[Файловый корпус C++03](e2e.ru.md) проверяет API и упакованный CLI на одинаковых обычных исходниках, с исполнением через строгие GCC и Clang. Начальное покрытие: возврат литерала, арифметика/нормализация печати и диагностика недопустимого символа. Набор поддерживаемых конструкций этим изменением не расширяется.

[Пример SQUARE](../src/test/resources/cpp03/square/README.md) добавляет две единицы трансляции, общий макрос и базу компиляции. Строгие нативные прогоны проверяют 58 до правки и 64 для ручного эталона результата. Импорт и препроцессор реализованы в #13–#15; происхождение и правка раскрытий реализованы в #16–#17.

## Редакция C++03 и база компиляции

`new Cpg.Options(Language.CPP, stage)` сохраняет прежний C++03 по умолчанию.
Третий аргумент `"c++03"` означает явное переопределение, `null` — его отсутствие.
Иные редакции не поддерживаются; явная неподдерживаемая редакция отвергается
даже для пустого входа. Старый `Parser.parse` совместим, четвёртый аргумент
выбирает редакцию.

`CompilationDatabase.read(path)` возвращает неизменяемый `Build` из пакета
`com.kniazkov.cpg.build`. Для импорта и разбора служит
`Cpg.readCompilationDatabase(path, options)`, для явной сборки —
`Cpg.read(build, options)`. `Build.TranslationUnit` хранит физический источник,
рабочую папку, упорядоченные пути заголовков, операции определения/отмены
макросов и редакцию команды. `PhysicalSource`, `TranslationUnit` и
`IncludeInstance` разделяют физический файл, контекст единицы и отдельное
включение. Это входные записи, а не заявление о готовом раскрытии макросов.

Приоритет редакции: явный API/CLI, последний `-std` записи, затем C++03.
Запись C++11 без переопределения сообщает файл и редакцию. Явный C++03 не
разрешает лямбды. `arguments` важнее `command`; кавычки команды разбираются
без запуска оболочки, подстановок или чтения response-файлов. Слитные и
раздельные `-I`, `-isystem`, `-iquote`, `-D`, `-U`, `-std` сохраняют порядок.
Неподдержанные ключи отвергаются с именем файла; только явно известные флаги
вывода, зависимостей и диагностики могут игнорироваться.

Относительная `directory` считается от папки базы, `file` и пути заголовков —
от рабочей папки записи. Текущая папка процесса на них не влияет. CLI принимает
`--compile-commands FILE` вместо `--input DIR` и необязательный
`--cpp-standard c++03`. [Команды и тесты](../src/test/resources/cpp03/compilation-database/README.md).

## Фазы лексики C++03 и физические позиции

`CppLexer.scan(file, source)` возвращает неизменяемый `Result`: логический
`text()` после фазы 3, `tokens()`, отображение каждого логического символа
`characterRanges()` и физический `eof()`. Вход — декодированная Java String;
смещения и колонки считаются в UTF-16. CRLF/CR становятся логическим переводом
строки. Триграфы заменяются до однопроходной склейки backslash-newline.
Комментарий заменяется одним пробелом и не склеивает соседние токены.
Внутренние физические переводы строк блочного комментария не завершают
логическую директиву; строчный комментарий заканчивается следующим логическим
переводом строки уже после склейки.

`PreprocessingToken` хранит вид, исходное логическое `spelling()`, отдельное
`canonicalSpelling()`, физический диапазон и полуоткрытые логические смещения.
Пробелы, переводы строк и EOF сохранены явно для препроцессора.
Диапазон склеенного токена охватывает исходные физические фрагменты, а
посимвольное отображение показывает сохранённые символы. Триграф отображается
на три исходных символа, пробел вместо комментария — на весь комментарий.

Различаются идентификаторы/UCN, preprocessing numbers, обычные/широкие
символьные и строковые литералы, имена заголовков, операторы и прочие символы.
Написание диграфов и альтернативных операторов сохраняется отдельно от формы
для парсера. Репертуар идентификаторов взят из приложения E C++03, а не из
современных категорий Java. Максимальное поглощение использует e/E со знаком
в pp-number; современные правила p/P, исключение `<::` и разбиение `>>` для
шаблонов не добавлены. Имена заголовков выделяются только в контексте include.
Незакрытые литералы, комментарии и заголовки сообщают физические позиции.

Лексика Java не изменена. Парсер C++ получает новый поток токенов, но его
поддерживаемый синтаксис остаётся меньше лексического репертуара. Наличие
токена ещё не означает вычисление литерала, поддержку всех выражений,
раскрытие заголовков или макросов. [Положительная приёмка](../src/test/resources/cpp03/lexical-phases/README.md),
[отрицательный литерал](../src/test/resources/cpp03/unterminated-literal/README.md).

## Включение заголовков и раскрытие макросов (C++03 #15)

`CppPreprocessor.preprocess(Build.TranslationUnit, source)` применяет упорядоченные `-D`/`-U` независимо для каждой единицы и выполняет лексические фазы для каждого физического заголовка. Объектные и функциональные макросы поддерживают пустое замещение, вложенные скобки аргументов, предварительное раскрытие аргументов, повторное сканирование с подавлением рекурсии, строкификацию `#` и склейку `##` исходных токенов. Результат склейки должен быть одним preprocessing token. Пустые фактические аргументы имеют неопределённое поведение в C++03 и диагностируются; вызов действительно беспараметрического `F()` и аргументы, ставшие пустыми после раскрытия, поддерживаются.

Для кавычек поиск идёт от каталога включающего файла через `-iquote`, `-I`, `-isystem`; для угловых скобок — `-I`, `-isystem`. Имя включения может получаться из макроса. Guards используют `#ifdef`/`#ifndef`/`#else`/`#endif`; полноценные выражения `#if` остаются в #19. Повторное включение выполняется в текущем контексте макросов, отсутствующий файл даёт всю цепочку включений. Только ранее моделируемый `<iostream>` остаётся непрозрачным при отсутствии настроенного файла. Другие отсутствующие системные заголовки дают ошибку. Глубина включений и объём раскрытия ограничены с диагностикой.

Парсер получает единый активный поток с физическими именами файлов и основными диапазонами раскрытия. Результат препроцессора содержит диапазоны написания и раскрытия, происхождение макросов и идентичность включений; перенос этого слоя в граф/JSON/SVG описан ниже в разделе #16. Сохранение вызовов макросов при генерации описано ниже в разделе #17. Минимальные объявления/определения `int name()` без аргументов нужны для двух единиц SQUARE; полная семантика функций и межфайловый поиск не заявляются. Границы проверяют `CppPreprocessorTest`, `PreprocessorIT` и сценарии `square`, `macros`, `missing-header`.

## API, JSON и SVG происхождения макросов (#16)

`Node.provenance()` возвращает необязательный `TokenProvenance`: полуоткрытый интервал итоговых токенов и неизменяемую запись единицы `Preprocessing`. `tokens()` даёт диапазоны написания/раскрытия, ID включений и событий; `expansions()` отдельно ведёт к событиям. `SourceFile.provenance().unit()` сохраняет все события, включая макросы без AST. `children()`, `references()` и обычный Visitor не обходят происхождение. Edit/build копирует неизменяемые записи; результаты анализа сохраняют прежние правила устаревания.

Событие содержит уникальный в единице ID, действовавшее определение и фрагменты замещения, полный диапазон вызова, исходные аргументы, родителя, участников #/## и полуоткрытые границы итоговых токенов. Повторно использованный предварительно раскрытый аргумент сохраняет одно событие и может дать несколько участков вывода: общий интервал охватывает их, а ID на каждом токене задают точную принадлежность. Пустые события имеют равные границы. Включения различаются по экземпляру. Происхождение сохраняется отдельно; генерация проверяет возможность оставить неизменённый вызов макроса.

JSON хранит `preprocessing` один раз у SourceFile; `provenance.sourceFileId` узла задаёт область интервала и `expansionIds`. Все диапазоны содержат физический `file`. ID детерминированы для тех же входов и независимы между единицами. SVG показывает фиолетовые пунктирные рёбра к событию, родителю, вызову, определению, оператору, аргументу и участникам #/##. Слой включён по умолчанию; отключение: `DotVisualizer.toDot(root, false)`, `renderSvg(root, path, false)` или CLI `--provenance off`.

[Команды и ожидаемые фрагменты](../src/test/resources/cpp03/provenance/README.md): SQUARE(a) даёт два чтения и один аргумент, NEST(f()) — два вызова и один аргумент, '*' ведёт к заголовку. Отдельно проверены частичное выражение, несколько инструкций и пустое замещение. Полное происхождение после произвольных преобразований относится к последующим задачам истории.

Определения из командной строки используют явно синтетические буферы `<command-line:N>` в порядке операций. Их диапазоны относятся к нормализованному буферу определения, а не к файлу единицы; диапазоны вызовов остаются реальными. ID включения сохраняет контекст единицы трансляции.

## Правка одного раскрытия макроса (#17)

Вызовите `ProjectEditor.replace` для выбранного раскрытого операнда, затем `Cpg.sources(edited, Language.CPP)`. Свежая замена наследует недостающий диапазон и токенное происхождение; явно заданное происхождение сохраняется. Исходный снимок неизменяем. Для C++ с макросами или физическими включениями `Preprocessing.sources()` хранит исходные тексты, `configuration()` — настройки единицы. Генерация не перечитывает диск.

Редактированный синтаксис сравнивается с повторным разбором из памяти. Правка внутри макроса расширяется до представимого внешнего вызова, изменённое поддерево выводится со скобками и заменяет участок сохранённого текста. Остальные вызовы, директивы и заголовки сохраняют байты. Перед возвратом файлов весь результат препроцессируется и разбирается под отдельным виртуальным корнем вывода и сравнивается с требуемым синтаксисом. В карту файлов входят относительные пути заголовков; CLI создаёт каталоги после проверки конфликтов выходных путей. Для сборки результата нужны соответствующие флаги/база компиляции.

Область правок ограничена явно: фрагмент макроса без границы целого поддерева, структурные правки с потерей посторонних вызовов, несовместимые правки общего исходника, заголовки вне общего корня, абсолютные включения и непереносимые пути дают понятную ошибку. Неполный набор исходников не возвращается. Общие конфликты вариантов сборки и произвольное редактирование относятся к следующим задачам. Прежняя генерация без макросов/заголовков и межъязыковая адаптация сохраняют своё форматирование.

[Исполняемый пример публичного API](../examples/cpp03-square/README.md) заменяет только правый операнд SQUARE(a) на b: результаты 58 и 64, побайтно прежние заголовок и second.cpp, затем CLI видит a*b и c*c. Вложенный OUT(a) с заменой на b+1 сохраняет приоритет умножения и сложения. Корпус требует строгие GCC и Clang, ручная демонстрация также выполняется в CI. Это завершает первую вертикальную веху, а не весь чеклист C++03.
