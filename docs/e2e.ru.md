# Сквозные тесты CLI

Из корня проекта запусти `mvn verify` на JDK 21. Maven сначала выполняет модульные тесты и собирает исполняемый JAR со всеми зависимостями. Затем Failsafe запускает классы `*IT` и сохраняет отчёты в `target/failsafe-reports`. Для одного сценария используй, например, `mvn "-Dit.test=PackagedCliIT#completeCppSnapshotAndSource" verify`.

## Как добавить сценарий

Помести тест в пакет `com.kniazkov.cpg.e2e` в `src/test/java`. Дай классу имя с окончанием `IT` и передай каталог JUnit `@TempDir` в `CliSandbox`. Каждый вызов `source` добавляет исходный файл в одну папку. Каждый вызов `run` запускает новый процесс `java -jar` в отдельном рабочем каталоге и запрашивает генерацию исходников и JSON. Можно обработать те же входные файлы на разных стадиях без перезаписи результата.

```java
var cli = new CliSandbox(temp).source("main.cpp", "int main() { return 0; }");
var run = cli.run("cpp", "--stage", "resolved").expectStatus(0);
run.expectSources(Map.of("main.cpp", "/e2e/return-zero.cpp"));
var graph = run.snapshot();
graph.exactly("/json/return-zero.json", Map.of("FILE_PATH", cli.input.resolve("main.cpp").toString()));
```

## Что сравнивать

- `expectSources` сверяет весь набор сгенерированных имён и содержимое каждого файла с ресурсом. Учитываются пробелы и завершающий перенос строки, CRLF и LF считаются эквивалентными.
- `exactly` сверяет JSON целиком. Порядок свойств объекта и отступы свободны. Для массивов важны длина и порядок. При расхождении сообщение содержит путь, например `$.files[0].items[0].body.items[0].value`. Абсолютный путь зависит от временной папки, поэтому его задают в ожидаемом документе явным маркером `"FILE_PATH"`. Остальные значения, включая позиции и ID, сравниваются буквально.
- `containsNode` ищет один узел, у которого одновременно совпадают все заданные поля. `excludesNode` проверяет отсутствие таких узлов. Вложенные объекты сопоставляются рекурсивно. Элементы массива в образце должны встречаться в том же порядке, между ними допустимы дополнительные элементы. Образец `{"diagnostics":[]}` проверяет наличие поля-массива с любым количеством элементов. Для точного сравнения пустого массива используй полный эталон.
- `expectEdge` выбирает начало и конец двумя образцами, каждый из которых должен соответствовать ровно одному узлу. Проверяется исходящее ребро указанного вида именно к ID выбранной цели. При загрузке любого снимка также проверяются уникальность ID и существование целей рёбер.
- Для ошибки исходника C++ при корректной конфигурации проверь код 1, причину в `stderr()` и вызови `diagnosticSnapshot()`: он проверяет JSON и отсутствие каталога исходников. Запрошенный SVG проверяй отдельно. Для неверной конфигурации/опций, ошибки Java и отказа до получения диагностического графа используй `expectNoExports()`. Для диагностического предупреждения о непрочитанной записи ожидается успешный статус, а само предупреждение проверяется в JSON и stderr.

Полный эталон удобен для короткого примера с фиксированной структурой. Для нового прохода обычно достаточно зафиксировать изменяемый фрагмент, его связи и отсутствие ошибочной отметки. После изменения формата проверяй различия перед обновлением эталона.

## Файловый корпус C++03

Перечень: `src/test/resources/cpp03/scenarios.txt`. Каждый каталог содержит обычные исходники в `sources/` и ожидания в `scenario.properties`. `Cpp03CorpusIT` читает те же файлы через публичный API и упакованный CLI. Положительные случаи используют строгий `Cpg.read`; отрицательные C++03 проверяют исключение строгого входа и диагностический снимок CLI, а отдельные тесты также проверяют `Cpg.readRecovering`. Сценарий восстановления по базе использует соответствующие входы базы компиляции; `CliSandbox.directory` сохраняет вложенные пути и заголовки. Единицы трансляции выбираются из каталога или базы компиляции; пользовательские заголовки обрабатываются рекурсивно.

- `return-zero`: код 0, пустой вывод, возврат целого нуля.
- `arithmetic`: код 0, вывод `40` с переводом строки, узел печати после свёртки.
- `invalid-token`: код CLI 1, `main.cpp:2:5: Unsupported character: @`, исключение строгого API, диагностический JSON CLI и отсутствие сгенерированных исходников.

Идентификатор Failsafe для всех сценариев: `Cpp03CorpusIT#corpus`. Один пример: `mvn -Dit.test=Cpp03CorpusIT -Dcpg.cpp03.scenario=arithmetic verify`. Ручной CLI: `java -jar target/cpg-0.0.1-SNAPSHOT.jar --from cpp --stage folded --input src/test/resources/cpp03/arithmetic/sources --out target/manual-cpp --json target/manual.json`. Для остальных примеров нужна стадия `resolved`; отрицательный пример намеренно завершается ошибкой.

Для `mvn verify` обязательны JDK 21, `g++`, `clang++` и Graphviz (`dot`). Graphviz нужен уже во время Maven для проверки настоящего диагностического SVG, а не только для последующего демонстрационного скрипта. Каждый исполняемый сценарий собирается обоими компиляторами, до и после генерации, с `-std=c++03 -pedantic-errors`. Код выхода и точный вывод сравниваются с независимыми ожиданиями. При сбое видны команда и версия. Отсутствие компилятора считается ошибкой, а не пропуском; это отдельно проверяет `missingCompilerIsAnError`.

После полного прогона CI выполняет `python3 scripts/check-cpp03-reports.py`: число результатов должно совпадать с числом сценариев плюс две проверки инфраструктуры; ошибки и пропуски запрещены. `inventoryAndNestedCopy` проверяет полноту перечня, дубликаты и копирование вложенного заголовка. После намеренно отфильтрованного локального запуска проверку полноты не выполняют.

Новые конструкции сопровождаются положительными, отрицательными и совместными сценариями, обновлением матрицы и справочников RU/EN. Сначала проверяем существующие узлы; новому узлу нужны строитель, Visitor, диапазон, экспорт и генерация. Для правок графа задаём независимые ожидания до и после. Новые конструкции C++03 принимаются по графу и обратной генерации C++03, без обязательного расширения перевода в Java. Прежние простые Java/C++ сценарии сохраняются.


Пятый сценарий `compilation-database` импортирует смешанную базу C++03/C++11 с явным C++03 и сравнивает API/CLI, исходный и сгенерированный код обоими компиляторами. `CompilationDatabaseIT` проверяет старый вызов по папке, эквивалентность явной редакции, ошибку без переопределения, запрет лямбды, имена файлов при неподдержанных ключах и равенство явной конфигурации с упорядоченными путями с пробелами и `-D`/`-U`. Запуск: `mvn -Dit.test=CompilationDatabaseIT verify`. [Исходники и команды](../src/test/resources/cpp03/compilation-database/README.md).

`lexical-phases` и `unterminated-literal` доводят обязательный корпус до семи сценариев. `LexicalPhasesIT` проверяет посимвольные физические координаты, диапазон триграфа, альтернативное написание и равенство графов API/CLI. Положительный исходник выполняется обоими строгими компиляторами; отрицательный даёт ошибку 2:5, запрошенный диагностический JSON и не создаёт исходников (#21). Команды находятся в README сценариев. CI запускается при открытии, обновлении и повторном открытии PR, а также при push в `master` (включая слияние). Push ветки больше не дублирует PR-проверку; ручной запуск сохранён.

Сценарии `macros` и `missing-header` доводят обязательный корпус до девяти. `square` теперь проходит полный путь базы компиляции → API/CLI → одинаковый JSON → две операции умножения → генерация → нативный результат 58. Настоящая правка графа и независимый ручной эталон дают 64 (#17). `macros` проверяет имя включения из макроса, guards, строкификацию, склейку, вложенные аргументы, подавление рекурсии и повторное включение с изменёнными определениями. `missing-header` требует ошибку с цепочкой из трёх файлов, запрошенный диагностический JSON и отсутствие сгенерированных исходников (#21); строгий API по-прежнему выбрасывает исключение. `PreprocessorIT` проверяет эти же обычные исходники через публичный API и упакованный CLI. Запуск: `mvn -Dit.test=PreprocessorIT,Cpp03CorpusIT verify`.

`provenance` — десятый обязательный сценарий. `ProvenanceIT` проверяет разные узлы с общим происхождением аргумента, вложенные события, частичные/множественные/пустые границы токенов, API/CLI и сохранность при edit/build. `scripts/demo.sh` создаёт настоящий SVG со слоем и без него и проверяет ссылки к координатам. Команды — в README примера.

`MacroEditingIT` проверяет сохранённые исходники, замену одного операнда, прежний заголовок/второй вызов, повторный CLI-разбор и приоритет вложенных раскрытий. Корпус square компилирует настоящую правку графа в обоих компиляторах; scripts/demo.sh запускает examples/cpp03-square/EditSquare.java через публичный API и проверяет 58→64.

`build-variants` — одиннадцатый обязательный сценарий. База из четырёх команд импортируется через API и JSON-only CLI; server/client выбираются через API, генерируются, повторно разбираются и собираются обоими строгими компиляторами с нужным -D. `BuildVariantsIT` отдельно различает неоднозначность неизвестного состава и ODR-конфликт известной сборки. Демонстрация выбора через публичный API также запускается в scripts/demo.sh.

`conditional-catalog` — двенадцатый обязательный сценарий. `ConditionalCatalogIT` проверяет неиспользованные определения заголовка, отдельные ID переопределений, связи к раскрытиям/проверкам наличия, отсутствие имени и `DEBUG=0`, владение внешними входами двух команд и профиля C++03, физические координаты и `#line`. Неактивный ошибочный синтаксис и неоткрытый отсутствующий заголовок остаются в сохранённом исходнике без AST и выполненных проверок. Обе ветви частичного инициализатора разбираются через API; исходные/сгенерированные файлы корпуса исполняются строгими GCC/Clang с `-DDEBUG=0` и без него (`native.also-without-flag=true`). Отрицательные тесты активируют ошибочную ветвь или убирают `#endif`; CLI сохраняет запрошенный диагностический JSON и блокирует генерацию исходников (#21). Запуск: `mvn -Dit.test=ConditionalCatalogIT,Cpp03CorpusIT verify`. [Команды и ожидания](../src/test/resources/cpp03/conditional-catalog/README.md).

Происхождение конфигурации теперь различает `java-api`, `cli` и базу компиляции. `SnapshotAssertions.assertEquivalent` сравнивает эффективные синтаксис/анализы/препроцессинг, исключая только поля происхождения входов, когда способы вызова различаются; отдельные тесты проверяют эти поля владения. Для одной базы без различающихся переопределений сохраняется полное сравнение JSON. Раздельные эталоны `return-zero` для API и CLI фиксируют намеренное различие источника. Зависящие от реализации решения вычислителя целых/символьных условий проверяются напрямую и не используются как переносимый нативный эталон.

`shared-headers` — тринадцатый обязательный сценарий. Фикстуры `common` и `conditional` импортируют один физический main.cpp дважды с настройками SERVER/CLIENT. `SharedHeaderGenerationIT` проверяет отказ серверной правки общей строки: в диагностике есть оба варианта, координаты и требуемые тексты, каталог экспорта не создаётся. Одинаковые правки дают один изменённый заголовок; правка существующей серверной ветви сохраняет клиентскую побайтно, включая CRLF, табуляцию, комментарии и пробелы. Строгие прогоны GCC/Clang сравнивают исходные 1/1, общую правку 2/2 и условную правку 2/1. `SharedSourceRequirementsTest` проверяет границы согласования. [Пример публичного редактора](../examples/cpp03-shared-headers/README.md) и `scripts/demo.sh` воспроизводят все три исхода. Запуск: `mvn -Dit.test=SharedHeaderGenerationIT,Cpp03CorpusIT verify`.


## Восстановление парсера и диагностический экспорт (#21)

`parser-recovery` и `inactive-extension` — четырнадцатый и пятнадцатый обязательные сценарии. Предыдущие числа выше описывают этапы добавления фикстур; текущий перечень задаёт `scenarios.txt`. Для ошибок исходника при корректной конфигурации C++03 действует диагностический экспорт вместо прежнего запрета всех экспортов CLI. Строгий Java/API-контракт не меняется.

- [parser-recovery](../src/test/resources/cpp03/parser-recovery/README.md) задаёт базу компиляции с повреждённым `a.cpp` и корректным `b.cpp`, каждый со своей настройкой макроса. `ParserRecoveryIT` и `Cpp03CorpusIT` требуют функцию перед ошибкой, точку остановки и исходный пропущенный фрагмент в `a.cpp`, весь ожидаемый синтаксис `b.cpp`, одинаковый JSON восстанавливающего API/CLI, настоящий читаемый SVG и код 1. Проверяются запрос только JSON/SVG и совместный запрос исходников; C++ не выдаётся в обоих случаях.
- [inactive-extension](../src/test/resources/cpp03/inactive-extension/README.md) сохраняет packed-атрибут в `#if 0`, успешно экспортирует и исполняет исходный/сгенерированный C++ обоими строгими компиляторами. Парный активный тест сообщает `main.cpp:1:8` на `__attribute__`, причину с C++03, выдаёт диагностический JSON и блокирует исходники.
- `ParserRecoveryIT` также проверяет диапазон/текст отсутствующего инициализатора, точный непустой пропущенный фрагмент, продолжение со следующего объявления, вариадические макросы, литералы `LL`/двоичные/raw, повторяющиеся неожиданные токены, оборванные функции и EOF. Повреждённая единица обязана завершиться и не скрыть пригодного соседа. `ParserRecoveryTest` проверяет копирование и Visitor, `RecoveryExportTest` — формат JSON, DOT и запрет генерации.

Корректные эталоны JSON не содержат необязательных полей ошибок и остаются прежними. Повреждённый снимок остаётся на `PARSED` при любой запрошенной стадии, без CFG/DFG и обещаний анализа; восстановление потоков отдельных функций не относится к #21.

```sh
mvn -Dit.test=ParserRecoveryIT,Cpp03CorpusIT verify
python3 scripts/check-cpp03-reports.py
```

Проверку отчётов запускай только после полного корпуса без фильтра сценариев. В CI Graphviz устанавливается до Maven, чтобы SVG входил в приёмку.

## Происхождение диагностики и сводка групп (#22)

[diagnostic-provenance](../src/test/resources/cpp03/diagnostic-provenance/README.md) — шестнадцатый обязательный сценарий. `DiagnosticProvenanceIT` и корпус вызывают общий приёмочный помощник на четырёх обычных базах компиляции:

- `assignment`: `ASSIGN(total);` сохраняет точку отсутствующего выражения перед `;`, пояснение вызова и точный токен `=` в заголовке. Независимый отсутствующий инициализатор после восстановления остаётся второй ошибкой, его объявление сохраняется.
- `paste`: `JOIN(+, *)` даёт одну основную ошибку CLI на вызове. API/JSON обязаны содержать три подписанных диапазона: левый и правый аргументы в `.cpp` и `##` в заголовке. Проверяются роль, абсолютный физический путь, смещения начала/конца, строки и столбцы, а также контекст неудавшегося раскрытия.
- `shared`: одна ошибка физического заголовка из `a.cpp` и `b.cpp` даёт одну группу, две единицы трансляции и оба контекста. Отдельная проверка API использует два варианта одного физического `.cpp`: одна единица, два варианта.
- `causes`: две команды по-разному определяют `BAD`, получая `+*` и `+/` в одном физическом вызове макроса. Разные причины должны дать две группы, а не объединиться по строке/диапазону.

Каждый случай сравнивает полный JSON API/CLI, число основных строк `error [code]` с числом групп, проверяет вариант сборки и цепочки включений/раскрытий, а также сохранность групп после `edit().build()` и `NameResolver.resolve`. Случаи общего заголовка и разных причин обращают порядок единиц и требуют равенства записей групп и корневого JSON `diagnosticGroups`. Это проверка детерминированности сводки, а не требования одинаковых ID AST или порядка файлов после перестановки входов. Ошибочные исходники имеют диагностический эталон, а не эталон нативного исполнения. Код 1 и запрет выдачи исходников сохраняются; группировка семантических диагностик и автоматическое исправление ошибки не заявляются.

Дополнительные регрессии `DiagnosticProvenanceIT` проверяют два независимых отсутствующих выражения в одном макросе, небезопасное восстановление присваивания внутри скобок/условия/вызова и разные раскрытые операнды (`40000`/`50000`) ошибочных директив `#line`/`#include`. Для директив сравниваются API/CLI JSON, цепочки раскрытий и сводки при обратном обходе; небезопасное восстановление обязано остановиться с одной исходной ошибкой без каскада. `DiagnosticProvenanceTest` также проверяет операнды условий, сигнатуры несовместимых переопределений и подписанные прежнее/новое определения, ID повторного включения, происхождение строгого исключения и ту же безопасную границу присваивания в низкоуровневом восстанавливающем парсере Java.

```sh
mvn -Dit.test=DiagnosticProvenanceIT verify
mvn -Dit.test=Cpp03CorpusIT -Dcpg.cpp03.scenario=diagnostic-provenance verify
# Полная регрессия и перечень обязательного корпуса, без фильтра сценариев:
mvn verify
python3 scripts/check-cpp03-reports.py
```

Проверку отчётов запускай только после полного корпуса. На этапе #22 шестнадцать сценариев требовали восемнадцать результатов корпуса, включая две проверки инфраструктуры; текущий перечень описан ниже. Прежние тесты Java/C++ и строгие GCC/Clang-прогоны корректных программ корпуса остаются обязательными. README примера содержит команды упакованного CLI и точный эталон физических координат; [справочник модели](model-guide.ru.md#происхождение-и-группировка-диагностики-22) описывает поля API и JSON.

## Профили платформы и деклараторы (#23)

[platform-declarators](../src/test/resources/cpp03/platform-declarators/README.md) — семнадцатый обязательный сценарий. `PlatformDeclaratorsIT` и `Cpp03CorpusIT` используют общий `PlatformDeclaratorsAcceptance` на одних обычных исходных файлах. Проверяются различия массива указателей, указателя на массив и указателя на функцию, абстрактные параметры функций, указатель на член, cv-квалификаторы, ссылки, локальные объявления через запятую и написанный typedef со ссылкой на канонический тип. Копия `PARSED` сохраняет полный JSON-снимок; снимки PARSED публичного API и упакованного CLI совпадают с учётом документированного различия происхождения входа.

Проверки цели сопоставляют стандартный и `long32` профили, целевой байт 8/16 бит, диапазоны long, пропущенное и явное null-выравнивание, неверные настройки и отдельные варианты единиц. Написанные типы и записи `TypeRepresentation` стадии `GREEN` переживают неизменённое редактирование; полное равенство JSON не требуется, поскольку редактирование сбрасывает производные рёбра CFG/DFG. `FOLDED` даёт возврат 20 в профиле по умолчанию и 16 в `long32`, с паритетом API/CLI. Размещение обычных полей проверяется отдельно: `char, long, char` по умолчанию имеет смещения 0/8/16 целевых байтов и размер 24; long в 32 бита с выравниванием 32 бита даёт размер 12. Неизвестные сведения о размещении должны оставаться неизвестными, без подстановки настроек машины.

`PlatformEncodingIT` отдельно создаёт исходник/заголовок ISO-8859-1, экспортирует через упакованный CLI, сверяет точные байты и повторно читает с тем же профилем. Непредставимый сгенерированный текст или конфликт кодировок одного физического файла обязаны не оставлять экспортов. Эти проверки не добавляют записи перечня корпуса.

Корпус компилирует и исполняет исходный и сгенерированный текст стандартного профиля через `g++` и `clang++` с `-std=c++03 -pedantic-errors`: ожидаются пустой вывод и код 20. Размеры/результат произвольного `long32` — **модельные эталоны API/CLI**, а не нативное исполнение с утверждением, что компилятор машины использует этот ABI. Нативный эталон по умолчанию относится к контрольной конфигурации репозитория, не ко всем целям C++03. Размещение функций/указателей на члены/классов и полная работа с литералами, преобразованиями и перегрузками не входят в #23; границы описаны в [справочнике](model-guide.ru.md#профили-платформы-и-рекурсивные-деклараторы-23).

```sh
mvn -Dit.test=PlatformDeclaratorsIT,PlatformEncodingIT verify
mvn -Dit.test=Cpp03CorpusIT -Dcpg.cpp03.scenario=platform-declarators verify
# Полная приёмка, без фильтра корпуса:
mvn verify
python3 scripts/check-cpp03-reports.py
```

На этапе #23 семнадцать сценариев требовали девятнадцать результатов корпуса, включая две проверки инфраструктуры; текущий перечень описан ниже. Запускай её только после полного корпуса, не после фокусированного прогона. JDK 21, оба строгих компилятора C++ и Graphviz остаются обязательными, как и прежние регрессии Java/C++ и межъязыковая генерация.

Подсценарий `platform-declarators/signed-min` также собирается и выполняется
обоими обязательными компиляторами до и после свёртки. Проверка перегрузок
`int`/`long` должна возвращать 1: генерация минимума знакового типа не меняет
тип выражения. Это нативная проверка исходников, не завершение разрешения
перегрузок в CPG (#30).

## Области видимости, объявления и связывание (#24)

[scopes-linkage](../src/test/resources/cpp03/scopes-linkage/README.md) — восемнадцатый обязательный сценарий. `ScopesLinkageIT` и `Cpp03CorpusIT` используют общий `ScopesLinkageAcceptance`, читая три одинаковых обычных `.cpp` через их базу компиляции. Положительный контракт проверяет:

- Два вхождения typedef из `config.h` с одинаковым физическим диапазоном и каноническими типами `long` и `int`. `WIDE` задаёт только команда `a.cpp`; каждое использование `Width` должно ссылаться на typedef своей единицы трансляции.
- Отдельные файловые функции `static helper` и функции `hidden` безымянных пространств имён в `a.cpp` и `b.cpp`; вызовы остаются внутри своей единицы и после выбора полного состава сборки.
- Повторное открытие пространства имён, его псевдоним, using-объявление, последовательные typedef и одну using-директиву для двух разных использований типов. API/JSON сохраняют обе цепочки, общую директиву и её ссылку на namespace; явно квалифицированное имя не получает лишнего шага using.
- Именованный тип под указателем со ссылкой на видимое предварительное объявление класса, переход от него к определению и false для полноты в ранней точке; связанные объявления/определения с языковым связыванием C.
- Полный паритет JSON публичного API и упакованного CLI для одной базы, принадлежность всех целей ссылок снимку, сохранность текста заголовка, повторный разбор генерации с теми же флагами каждой единицы и равнозначные связи в копии и выбранном составе.

Нативный эталон отдельно компилирует каждую единицу через `g++` и `clang++` с `-std=c++03 -pedantic-errors`, применяет `-DWIDE` **только к `a.cpp`**, затем связывает объектные файлы. Исходная и сгенерированная программы должны иметь пустой stdout и код возврата 33. Общий `-DWIDE` для всех файлов проверял бы другую программу и не заменяет этот контракт. Ошибочные случаи неполного типа и нарушения ODR не имеют эталона нативного исполнения.

`ScopesLinkageIT` отдельно проверяет `sizeof` перед определением класса как отрицательный семантический случай. Указатель на предварительно объявленный класс допустим, но последующее определение не исправляет более ранний `sizeof`. Проанализированный API-граф содержит `incomplete-type` с уровнем ERROR без ошибки парсера; CLI должен вернуть 1, записать запрошенные диагностические JSON/SVG и не создать каталог исходников. Тот же отрицательный исходник должны отвергнуть оба нативных компилятора с `-fsyntax-only`. Сам разбор (`PARSED`) не выполняет это семантическое правило; диагностический граф запрашивается на `RESOLVED`.

`ScopeDeclarationParserTest`, `ScopedResolutionTest` и `ScopedExportTest` покрывают области блоков/функций/классов, затенение и точку объявления, вложенные типы, enum, классы хранения, различение `T(a);` и `T x(U());`, повторные объявления, конфликты связывания, запрет семантически ошибочной генерации и принадлежность ссылок после правки/пересчёта. Проверки экспорта проходят ID `resolutionSteps` и обычные ссылочные рёбра JSON, сверяют одну директиву для двух использований, сохраняют предварительные/определяющие ссылки в копии и отвергают неподдержанный перевод в Java. Правки общего заголовка сохраняют проверку согласования #20 для namespace, не разворачивая условный текст в плоские объявления.

```sh
mvn -Dit.test=ScopesLinkageIT verify
mvn -Dit.test=Cpp03CorpusIT -Dcpg.cpp03.scenario=scopes-linkage verify
java -jar target/cpg-0.0.1-SNAPSHOT.jar --from cpp --stage resolved \
  --compile-commands src/test/resources/cpp03/scopes-linkage/compile_commands.json \
  --out target/scopes-linkage-cpp --json target/scopes-linkage.json
# Полная приёмка, без фильтра корпуса:
mvn verify
python3 scripts/check-cpp03-reports.py
```

На этапе #24 перечень содержал восемнадцать сценариев: проверка отчётов требовала **двадцать** результатов корпуса/инфраструктуры без провалов, ошибок и пропусков. Её запускают только после полного корпуса. JDK 21, GCC, Clang и Graphviz остаются обязательными; фокусированный локальный запуск не заменяет полную приёмку. [Справочник модели](model-guide.ru.md#области-видимости-объявления-и-связывание-24) задаёт точные поля и границы: полное разрешение перегрузок/ADL, ABI классов и все правила объявлений/ODR C++03 этим сценарием не заявляются.

## Литералы, выражения и преобразования (#25)

delete[], допустимые приведения, unsigned wrap и сохранённые побочные эффекты.

## Наследование и виртуальные методы (#29)

инфраструктуры**, без ошибок и пропусков проверок компиляторами.

## Перегрузки, ADL и номинальная идентичность типов (#30)

`OverloadExportTest` проверяет исходник/повторный разбор и копирование сложения
`Money`, невладеющие ссылки на реализации внутри проекта, отдельные поля
привязки операторов в JSON и метки реализаций DOT. Проверяются функции
преобразования без написанного возвращаемого типа и отказ перевода в Java.
Явный профиль с одинаковой шириной подтверждает разные цели `f(int)` / `f(long)`
для `f(1)` / `f(1L)`; написание `long` и суффикс `L` переживают генерацию.
Команда: `mvn -Dtest=OverloadExportTest test`.

Нативная приёмка сопоставляет исходный, сгенерированный и свёрнутый C++03
в GCC и Clang, включая вычисление обоих операндов перегруженного `&&` и
контрольный встроенный оператор с коротким замыканием. Ссылки на реализации
и написанный синтаксис проверяются отдельно от результата выполнения;
неизвестным телам не приписывается выдуманная арифметическая семантика.
См. [контракт](model-guide.ru.md#перегрузки-adl-и-номинальная-идентичность-типов-30).

Обязательный `overloads-adl` задаёт профиль int32/long32 для зелёных снимков

арифметика long, namespace ADL, сложение Money, возвращающие класс операнды
перегруженного &&, наблюдаемые эффекты функции преобразования/преобразующего
конструктора и отказ неявного применения explicit. Нативные компиляторы
используют ABI своей машины: проверяется сохранённый выбор перегрузок, а не

### Проверки экспорта инструкций и исключений (#31)

`StatementExceptionExportTest` проверяет повторный разбор генерации пустой инструкции,
инициализаторов `for`, `do/while`, fall-through в `switch`, меток и `goto`; спецификации
исключений, типизированные обработчики, `catch (...)` и повторное возбуждение; порядок
инициализаторов в function-try-block конструктора. Отдельно проверяются JSON после
edit/copy и DOT со ссылками служебных вершин очистки. Оборванное тело остаётся видимым
в JSON/DOT, но не допускается к генерации исходников.

В нативных сценариях очистки нужно сравнивать с путями CFG не только порядок, но и число
событий: обычный выход разрушает `b, a`, исключение из работы разрушает `b, a`, а неуспех
конструктора `b` разрушает только успешно созданный `a`. Генерация сохраняет обычные
локальные объявления, без вставки явных вызовов деструкторов. Парный пример с `void work();`
и `void work() throw();` внутри try/catch различает возможную исключительную очистку
и небросающий вызов. Ошибка в другой части файла не должна удалять поток полностью
разобранной функции; оборванная функция не должна выглядеть полностью проанализированной.

Обязательный `statements-exceptions` запускает исходную, сгенерированную и свёрнутую
версии в GCC и Clang в строгом режиме C++03. `StatementsExceptionsAcceptance`
сравнивает JSON API/CLI и копии снимков, проверяет цели очистки и исключительные
рёбра независимо от нативного результата. Журналы: `1221` при нормальном обратном
разрушении, `12219` при исключении из работы и внешнем обработчике, `119` при
неуспехе второго конструктора, `1189` при очистке function-try-block конструктора.
Function-try-block деструктора даёт `122189`: оба поля разрушаются до его обработчика
и внешнего обработчика. Каждый путь также проверяет число разрушений. Есть нативные
контроли return, goto, continue/break, вложенного switch, объявлений в условиях
и повторного возбуждения. Отдельные ошибочный и оборванный входы экспортируют
диагностики и полноту потоков без сгенерированных исходников.
Команда: `mvn -Dit.test=Cpp03CorpusIT -Dcpg.cpp03.scenario=statements-exceptions verify`.
Корпус #31 содержит **25 сценариев и 27 результатов вместе с инфраструктурными тестами**.

## Экспорт специализаций и исследование C++03 export (#35)

Точечные проверки синтаксиса и экспорта:

```sh
mvn -Dtest=TemplateInstantiationExportTest,TemplateExportTest test
scripts/probe-cpp03-export.sh g++ clang++
```

Модульные проверки покрывают синтаксис полной/частичной специализации, явное
инстанцирование, сохранение `export`, раздельное владение общим и конкретным телом,
типизированные рёбра вызовов и запросов, обратные запросы, копии и отсутствие
висячих ссылок. Проба компиляторов печатает версии и диагностики и удаляет свои
временные файлы; отсутствующий компилятор явно отмечается SKIPPED. Код возврата
скрипта не является заключением о соответствии: нужно читать оба результата
сборки/линковки. GCC 14.2 и Clang 19.1.7 не линкуют отдельное экспортированное
определение, а контроль с явным инстанцированием собирается и запускается.
Проигнорированное ключевое слово и успешный контроль не закрывают поддержку
C++03 `export`. Инстанцирование общего видимого заголовка в совместимых TU
проверяется отдельно от этого исследования.

`TemplateInstantiationExportTest` также проверяет аргументы функций
TYPE/VALUE/TEMPLATE, уникальность JSON ID и совместимые представления типов
в копиях снимков.

Обязательный корпус `template-instantiation` использует две физические единицы
трансляции с общим заголовком. Проверяются общий экземпляр outer/inner и обратные
связи запросов, сохранность общих тел, SFINAE непосредственного контекста,
упорядочение функций, полные и частичные специализации классов, явное
инстанцирование функции, вывод границы массива, аргументы-значения и
аргументы-шаблоны, копии и эквивалентность API/CLI JSON/SVG. Исходная,
сгенерированная и свёрнутая программы используют настоящий системный `<vector>`
и совпадают под GCC и Clang. Отдельные недопустимые примеры проверяют вложенную
ошибку выбранного тела с упорядоченными позициями, частичную специализацию
функции и неоднозначные частичные специализации классов. Полный корпус содержит
**29 сценариев и 31 результат с проверками инфраструктуры**. Отдельный запуск:
`mvn -Dit.test=Cpp03CorpusIT -Dcpg.cpp03.scenario=template-instantiation verify`.

Обязательный `vector-semantics` проверяет равенство API/CLI JSON, типизированные
семантические связи в SVG, копии снимка, генерацию GREEN/FOLDED и настоящий запуск
GCC/Clang в C++03. Различаются количество/значение/диапазон, присваивание прежнему
контейнеру, независимые размеры копий, общие объекты через указатели, выбор
const-конструктора Record, bool-прокси и эффекты аллокатора. Вложенный пример
copy-overloads проверяет наблюдаемый выбор const-копирования без точного числа
копий. Оригинал, GREEN и FOLDED обоих примеров компилируются обоими компиляторами.

`vector-access` исполняет доступ, исключение выхода за границу at, reserve/resize,
перегрузки insert/erase, возвращённые итераторы, прямой/обратный/константный обход,

### Самостоятельная история преобразований

`snapshot-history` проводит программу вывода через четыре стадии и читает JSON
обычным парсером. Проверяются schemaVersion=1, явный stage, уникальные локальные
ID и разрешимость исторических ссылок, затем путь от свёрнутого 5 к предыдущему
AddExpression и координатам. Посторонняя старая функция исключена из истории.
API проверяет вклад stream/value/newline/flush, обе обратные роли endl и
неизменность прежних снимков. Ошибочные снимки сохраняют явно выбранную стадию.
Все выданные варианты выполняются строгими GCC/Clang.

Сценарий `pass-history` проверяет историю выполнения отдельно от происхождения
узлов: пустой набор находок всё равно подтверждает запуск, область одной функции
не подменяет результат другой, после правки пересчитываются зависимости DFG,
а прежний снимок остаётся неизменным. Записи JSON проверяются обычным парсером;
исходный и изменённый варианты сохраняют поведение на GCC/Clang. Модульные тесты
дополнительно охватывают удалённые функции, публичные проходы без изменений и
детерминированный экспорт истории.
