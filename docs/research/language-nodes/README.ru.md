# Общие узлы для C, C++, Java, Python и JavaScript

Исследование от **3 ноября 2026 года**. Это предложение по развитию модели, а не описание уже реализованных возможностей и не новая спецификация парсера.

## Что согласовано

- Приоритет — максимальное переиспользование узлов и алгоритмов обхода.
- Сопоставляем прежде всего **синтаксические конструкции**. Типы и семантику затрагиваем там, где без них объединение становится вводящим в заблуждение.
- Стандартные библиотеки исключены. В частности, сопоставление функций вывода, контейнеров и строковых API здесь не проводится. Существующий `PRINT` прототипа остаётся отдельным решением.
- Версии отмечаются по существенным изменениям, без полной истории поправок.
- Предлагаются общие поля, необязательные поля и ограничения; перед реализацией каждой сложной возможности потребуется отдельная проверка спецификации.
- Реализация остаётся монолитной библиотекой на Java с рукописными парсерами. Исследование не вводит плагины, генератор парсеров или новые зависимости.

## Основной результат

**Общая форма узла полезна даже при разной семантике.** Для поиска всех вызовов достаточно общего `Call`; для перестановки вызовов нужна информация о побочных эффектах. Эти задачи не должны требовать одинаковой глубины понимания языка.

Лучшие кандидаты на немедленное переиспользование: имена и ссылки, литералы, блоки, выражения, вызовы, доступ к членам, объявления переменных, параметры, функции, условные конструкции и простые циклы. Следующий слой — типовые объявления, лямбды, шаблоны связывания, выбор ветви, исключения, импорты. Они тоже допускают общие структуры, но требуют больше различающихся вариантов.

Не стоит превращать всё в один `UniversalNode` с десятками nullable-полей. Предлагается **общее семейство + небольшие типизированные варианты**. Например, `Loop` может иметь варианты `While`, `ForControl`, `ForEach`: алгоритм поиска циклов работает со всеми, а генератор видит точную форму.

### Переиспользование класса и «зелёность» — разные свойства

Один Java-класс `VariableDeclaration` может обслуживать C, C++, Java и JavaScript. Но экземпляр с C++-ссылкой `int&` не становится переносимым в JavaScript от того, что соседний экземпляр этого же класса переносим.

Предлагается вычислять допустимость по **значениям полей, детям, контексту и профилю языка**. Профиль включает язык, редакцию и включённые расширения. Полностью зелёный граф должен проходить проверку генерации во всех целевых профилях поддерживаемого подмножества. Это уточнение реализации ранее согласованной модели цветов; третьего цвета не требуется.

Для грубой оценки можно использовать пересечение множеств языков узлов. Для окончательного ответа его недостаточно: `return` требует функции, ссылка — подходящего объявления, а локальная переменная без указанного типа может потребовать вывода типа. Поэтому проверка целого графа предшествует генерации. Невозможная генерация должна давать объяснимую ошибку, а не молча удалять неподдерживаемые поля.

### Синтаксическое объединение не разрешает произвольные оптимизации

Общий `Binary(ADD, left, right)` позволяет обойти оба операнда. Он сам по себе не доказывает ни числовой тип, ни отсутствие перегрузки, ни безопасность перестановки. Предлагается оставлять такие факты неизвестными до соответствующего анализа. «Похожий» результат межъязыковой генерации допускается требованиями проекта; это не основание менять поведение при обычной регенерации исходного языка.

Особенно важно не смешивать три независимые вещи:

1. Синтаксис типа в исходнике: явно указан, указан placeholder, отсутствует.
2. Вычисленный анализатором тип: известен или ещё неизвестен.
3. Переносимость конструкции и доступный способ её генерации.

### Озеленение остаётся отдельным проходом

Парсер сохраняет конструкцию настолько точно, чтобы её можно было воспроизвести на исходном языке. Затем отдельные проходы разрешают ссылки и преобразуют подходящие формы. Общий интерфейс обхода доступен уже до озеленения: для поиска `Call` или `BindingTarget` не требуется уничтожать языковые различия.

Рекомендованный критерий хорошего объединения: **общий алгоритм получает полезные именованные поля, а языковой генератор не восстанавливает потерянную информацию догадками**.

## Что исследование не обещает

Это выборочное сопоставление значимых семейств, а не полное покрытие грамматик. Здесь нет универсальной модели памяти, ABI, полной типизации, разрешения перегрузок, библиотечных соответствий и доказательства эквивалентности трансляции. Диалект AscendC не исследован по собственной спецификации: предлагается только способ размещения его будущих конструкций.

Документы сохраняют текущие требования к неизменяемому валидному графу, отдельной мутабельной модели и перенаправлению ссылок при замене. Имена новых узлов и API предварительные; изменения исходного кода этим исследованием не вносятся.
