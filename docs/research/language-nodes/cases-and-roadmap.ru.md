# Примеры объединения и следующие шаги

[Обзор](README.ru.md) · [Матрица](syntax-matrix.ru.md) · [Модель](node-model.ru.md) · [Источники](sources-and-versions.ru.md)

Примеры ниже составлены для исследования. Это фрагменты соответствующих языков, а не входы, уже поддерживаемые прототипом. Компиляционные тесты этих примеров в рамках исследования не запускались.

## 1. Один узел переменной, несколько форм типа

| Фрагмент | Представление при разборе | Пояснение |
|---|---|---|
| C: `int count = 6;` | VariableDeclaration + Explicit(int) + ExpressionInit(6) | Явный тип |
| C23: `auto count = 6;` | VariableDeclaration + Placeholder(C_AUTO) + ExpressionInit(6) | В более раннем C `auto` не означает такой вывод типа |
| C++11+: `auto count = 6;` | VariableDeclaration + Placeholder(CPP_AUTO) + ExpressionInit(6) | Синтаксически общий вид с отдельным placeholder |
| Java10+, внутри метода: `var count = 6;` | VariableDeclaration + Placeholder(JAVA_VAR) + ExpressionInit(6) | Это не универсальная замена типа поля или возвращаемого типа |
| JS: `let count = 6;` | VariableDeclaration(kind=LET, typeUse отсутствует) | Не нужно выдумывать тип в исходном AST |
| Python: `count = 6` | Assignment(NameTarget(count), 6) | Не объявлять автоматически первой декларацией по позиции в файле |
| Python: `count: int = 6` | AnnotatedAssignment(target, annotation, value) | Аннотация хранится отдельно от результата анализа типа |

Основания: [C23] §6.7.9; [CPP-AUTO]; [J-STMT] §14.4; [JS-STMT] §14.3; [PY-SIMPLE] §7.2. После анализа Python-binding подходящую конструкцию можно озеленить. `AnnotatedAssignment` здесь — уточнение исходной формы, совместимое с семейством Assignment в модели.

Практический вывод: пример пользователя хорошо объединяется для C/C++/Java/JS. Для включения Python без потери информации нужен дополнительный слой связывания или отдельный проход. У всех вариантов можно сразу предоставить общую роль `BindingWrite` для анализа записей.

## 2. Общая функция и арифметическое тело

```c
/* C */
int twice(int value) { return value * 2; }
```

```cpp
// C++
int twice(int value) { return value * 2; }
```

```java
// Java: член класса
static int twice(int value) { return value * 2; }
```

```python
# Python
def twice(value):
    return value * 2
```

```javascript
// JavaScript
function twice(value) { return value * 2; }
```

Во всех случаях переиспользуются Callable, Parameter, Block, Return, Binary, NameReference, Literal. Различаются placement, типовые записи и модификаторы. Для общего алгоритма «найти возвращаемые выражения» этого достаточно. Для оптимизации умножения знания о типе и правилах операций потребуются отдельно.

Предложение озеленения: оставить зелёным подходящее тело, а оболочку функции считать переносимой только при наличии правил размещения в целевом языке. Не объявлять C-функцию автоматически методом Java. Это преобразование программы, а не форматирование.

## 3. Группировка не должна скрывать declarator

```c
int *cursor, length;
```

Правильная структура: группа с общим базовым specifier `int`, двумя декларациями и разными declarators. В нормализованном представлении тип `cursor` — pointer-to-int, тип `length` — int. Неверная структура — один общий PointerType на всю группу [C23, declarators].

```cpp
Widget first(3);
Widget second{3};
```

Даже если список аргументов выглядит одинаково, формы DirectInit и ListInit сохраняются. Печатать обе через круглые скобки нельзя без отдельного анализа [CPP-INIT]. Это хороший пример необязательных полей, которым лучше предпочесть типизированный вариант.

## 4. Общее сравнение без двойного вычисления

```python
lower < read_value() < upper
```

Предлагаемый AST: ComparisonChain из трёх operands и двух operators. Нельзя просто заменить его на два Binary с копией Call: у Python средний operand вычисляется один раз, а продолжение коротко замыкается [PY-EXPR, comparisons].

Возможное последующее понижение требует временной переменной и сохранения порядка. Оно может быть полезно для межъязыковой генерации, но не должно происходить в парсере. Аналогично `and`/`or` Python и JS `&&`/`||` не следует считать безусловно булевыми результатами [PY-EXPR, JS-EXPR].

## 5. Три разных задачи со списком имён

```cpp
// C++17
const auto& [left, right] = pair;
```

```javascript
const {left, right: renamed = 0} = pair;
```

```python
left, *remaining = values
```

Переиспользуются компоненты SequenceBinding/ObjectBinding/RestBinding, имена и default expression. Сохраняются различия: C++ structured binding с reference/qualifiers, JS property-to-binding mapping и Python assignment unpacking [CPP-BIND, JS-STMT, PY-SIMPLE].

Pattern matching добавляет ещё одну роль. Python `case Point(x, y)` и Java record pattern можно сопоставить через DeconstructionPattern, но они не являются обычными вызовами или списками присваиваний. Поэтому рекомендуются общие составляющие, а не один узел «всё с запятыми».

## 6. Цикл с дополнительной ветвью

```python
for item in items:
    if accept(item):
        break
else:
    missing = True
```

В предлагаемой структуре `normalExitBody` хранит последнее присваивание. Это не тело, выполняемое после любого завершения: `break` меняет поведение [PY-COMPOUND, for]. Понижение в обычный цикл может использовать флаг, но должно учитывать вложенные циклы и точную цель break.

JS `for (const key in object)` и `for (const value of iterable)` помещаются в одно семейство обхода с разными `iterationKind`, а не в один неразличимый ForEach [JS-STMT]. Анализ «найти все циклы» остаётся общим.

## 7. Одинаковые слова — разные конструкции

| Сходство | Почему недостаточно одинакового узла | Решение модели |
|---|---|---|
| Java `yield` и Python/JS `yield` | В Java это результат switch, не приостановка генератора | Transfer(SWITCH_YIELD) и Suspend — разные семейства [J-STMT, PY-EXPR, JS-FUNC] |
| Python `with`, Java try-with-resources, C++ RAII | Разные механизмы входа/выхода; в C++ нет соответствующего отдельного синтаксического блока | Общая роль resource region возможна позже, исходные формы сохраняются |
| Python decorator и Java annotation | Decorator — выражение с применением к определению, не просто декларативная метка | Разные варианты MetadataApplication [PY-COMPOUND, J-INTERFACE] |
| C++ `#include` и Java/JS `import` | Препроцессор работает с текстом и токенами; import — языковая конструкция | Отдельный PreprocessorDirective, общая роль dependency для навигации |
| Python `__init__` и Java constructor | Первое разбирается как обычный def со специальным именем | Распознавание специального назначения отдельным анализом |
| C++ template и Java generic | Общие параметры не делают одинаковыми specialization/instantiation | Общие компоненты, отдельная template-оболочка [CPP-TEMPLATE, J-TYPE] |
| `null`, `None`, `nullptr`, `undefined` | Даже синтаксический статус различается; undefined в JS может быть затенённым именем | Не превращать NameReference в literal без разрешения [JS-LEX] |

## 8. Что это означает для рукописного парсера

**Общие узлы не означают один общий парсер.** Лучше разделить переиспользование инфраструктуры и правила каждого языка. Общее: позиция в источнике, token stream, диагностика, создание builders, приоритетные выражения, списки элементов. Отдельное: лексические режимы, грамматика и контекстные ограничения.

| Затруднение | Последствие для архитектуры |
|---|---|
| C/C++ typedef-name и неоднозначность declaration/expression | В перспективе нужен контекст имён при разборе; одной таблицы приоритетов недостаточно |
| C/C++ макросы | Выбор режима preprocessing должен быть явным. Сохранить `#include` и раскрыть всю translation unit — разные уровни поддержки |
| Python отступы и логические строки | Lexer должен выдавать структуру indentation; нельзя заранее удалить все пробелы [PY-LEX] |
| JS `/` и regexp, newline-sensitive формы | Нужна координация lexer/parser и сохранение информации о переносах [JS-LEX] |
| Java contextual keywords и версии | Профиль должен проверяться в нужном контексте, а не только глобальным списком keywords |
| Новые операторы диалекта | Точки расширения нужны для tokens, parsing forms, validation и emission, а не только новый Kind |

Для собственного диалекта сначала выбрать: это новый modifier, атрибут, оператор, вид выражения или самостоятельная конструкция? Если достаточно существующего узла и типизированной детали, переиспользовать его. Если требуется новая форма, дать ей общие expression/body/binding-дети. Затем добавить диагностику и генерацию; лишь после этого — правило озеленения, если оно существует.

Нельзя честно обещать «моментально добавить любой диалект»: локальный qualifier добавляется существенно проще, чем новый контекстный синтаксис. Цель проекта реалистичнее формулируется как минимальное число изменений для локальных расширений.

## 9. Рекомендуемый порядок реализации

Приоритеты — рекомендация исследования, не новый согласованный объём ближайшего прототипа.

| Этап | Результат | Критерий завершения |
|---|---|---|
| A. Явные роли и профиль | Разделить syntax children и references; сформулировать значения TypeUse/Initializer; сохранить API прототипа | Текущие примеры продолжают работать; новые варианты не теряются при mutable → immutable |
| B. Общие повседневные конструкции | VariableDeclaration, Callable/Parameter, If/While/ForControl, выражения и вызовы | Собственные небольшие примеры C/C++/Java и отрицательные случаи соответствуют заявленному подмножеству |
| C. Python и JS | Отдельные lexer/parser, общие узлы, языковые binding-формы | Не потеряны indentation, var/let/const, assignment-vs-declaration, line terminators |
| D. Новые общие семейства | ForEach, Lambda, TypeDeclaration, Selection, Try, BindingTarget | Понятны ограничения каждого варианта и цели генерации |
| E. Сложные красные формы | Макросы, templates/requires, match, comprehensions, async, modules | Добавлять по востребованности; совместный обход работает без обязательного озеленения |
| F. Диалект | Одна реальная конструкция компании, встроенная в библиотеку | Разбор → валидный граф → исходник, затем возможное озеленение |

Первое практическое действие после исследования: выбрать 2–3 семейства из B и сделать для них небольшую конкретную спецификацию Java API. Не стоит сразу вводить все перечисленные здесь классы.

## 10. Проверка каждой будущей возможности

Для включения новой формы достаточно небольшого, но содержательного набора проверок:

- Точное соответствие структуры собственному примеру и сохранение различающих полей.
- Отрицательный пример для неподдерживаемой версии или неправильной комбинации полей.
- Parse → emit → parse с сопоставлением нормализованной структуры. При доступном компиляторе — проверка исходного языка.
- Mutation → build: ссылки не ведут в старый снимок, входящие ссылки перенаправлены, незаконное удаление отклонено.
- Для озеленения: один положительный случай и один похожий, который преобразовывать нельзя.
- Для оптимизации: отдельные условия корректности. Общая синтаксическая форма не является таким условием.

Ключевой результат исследования — переиспользование можно наращивать постепенно. Для этого достаточно точно представлять общие части и сохранять языковые различия там, где они нужны; полная унификация типов и библиотек этому не предшествует.
