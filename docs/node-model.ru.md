# Структура классов узлов — согласованные решения

Обсуждение начато 3 ноября 2026 года. Этот документ фиксирует решения по развитию прототипа; реализация пока не изменена. Исследовательские предложения из [обзора языковых конструкций](research/language-nodes/README.ru.md) не считаются принятыми автоматически.

## 1. Отдельные классы конструкций

Принято: конкретные конструкции получают собственные Java-классы с именованными типизированными геттерами. Для общих алгоритмов классы объединяются базовыми категориями Node, Expression, Statement и другими по мере необходимости.

Примеры предполагаемых классов: BinaryExpression, CallExpression, IfStatement. Примеры доступа: left(), right(), operator(), callee(), arguments(), condition(), thenBranch(), elseBranch(). Полный состав классов и окончательное именование методов будут согласованы отдельно.

Класс соответствует конструкции и может переиспользоваться несколькими языками. Существенно отличающаяся конструкция получает отдельный класс. Цвет не закрепляется наследованием: допустимые языки могут зависеть от содержимого конкретного узла.

Общие возможности узлов сохраняются: обход детей, генерация исходника, получение поддерживаемых языков. Сохраняются неизменяемость готового графа и отдельная мутабельная модель. Каждому конкретному неизменяемому классу соответствует мутабельный класс: например, BinaryExpression и его вложенный BinaryExpression.Builder. Они предоставляют доступ к тем же смысловым составляющим; мутабельный вариант дополнительно имеет методы изменения. Сигнатуры доступа к ещё не заполненным обязательным полям уточняются отдельно с учётом запрета возвращать null.

## 2. Возвращаемые значения

Принято: методы API модели не возвращают null.

- Обязательное одиночное значение возвращается непосредственно как T. В валидном неизменяемом узле оно всегда присутствует.
- Необязательное одиночное значение возвращается как Optional<T>. При отсутствии — Optional.empty(); сам Optional никогда не равен null.
- Коллекция возвращается непосредственно как коллекция, без Optional. Отсутствие элементов обозначается пустой коллекцией, а не null.
- Коллекции, возвращаемые неизменяемыми классами, неизменяемы. Их содержимое не должно изменяться вслед за внешним списком или последующими изменениями билдера.
- Коллекции модели не содержат null-элементов.

Пример контракта:

```java
Expression condition();           // Обязательный ребёнок.
Optional<Statement> elseBranch();  // Необязательный ребёнок.
List<Expression> arguments();      // Неизменяемый, возможно пустой список.
```

Это правила публичного результата, а не требование хранить Optional в каждом внутреннем поле. Правила приёма null в аргументах, организация полей и доступ к коллекциям мутабельной модели ещё не согласованы.

## 3. Вложенные строители и циклические связи

Принято по итогам примера Johnny/Freddy: мутабельный класс строителя объявляется как public static Builder внутри соответствующего неизменяемого класса. Логика объекта и его построения сосредоточена в одном месте. Это решение заменяет прежнюю договорённость о разнесении мутабельных и неизменяемых классов по разным пакетам.

Готовый объект не хранит строитель. Его поля содержат значения и ссылки на другие готовые объекты. Строитель содержит собственные значения и ссылки на другие строители. Изменения строителя после сборки не затрагивают ранее созданные объекты.

Согласованный образец API:

- Статический create() создаёт пустой строитель.
- Сеттеры возвращают тот же строитель для цепочек вызовов.
- edit() создаёт отдельную мутабельную копию достижимой структуры с сохранением циклов и общих ссылок.
- build() создаёт новый независимый неизменяемый результат из достижимой структуры строителей.
- Обязательные связи проверяются; отсутствие необязательной связи внутри может представляться null, снаружи — Optional.

В одной операции build() используется общий контекст соответствия строителей новым объектам. Объект создаётся и регистрируется до рекурсивного заполнения ссылок. Повторное посещение строителя возвращает тот же объект текущей сборки, замыкая цикл. Частично заполненные объекты не публикуются через публичный API. Ошибка сборки не возвращает частичный граф.

Для edit() действует отдельный контекст обратного направления: исходные объекты → новые строители. Строитель также регистрируется до обхода связей. Соответствия учитывают идентичность объектов, а не структурное равенство.

Неизменяемость обеспечивается отсутствием доступного пути изменения опубликованного объекта, а не обязательным модификатором final у каждого поля. Пустой конструктор приватный; заполнение полей выполняется внутри сборки. Корректная публикация между потоками и доступность внутренних методов требуют отдельной проработки.

Следующее направление проектирования: заменить карту Object → Object специализированными контекстами. Предлагаются общий базовый тип узлов и интерфейс BaseBuilder<T>. Точные имена, сигнатуры и механизм типобезопасного хранения разнородных пар пока не утверждены.

## 4. Следующие вопросы

- Типизированные BuildContext и EditContext; общий базовый тип узла и контракт BaseBuilder<T>.
- Общий обход детей при наличии именованных геттеров.
- Способ построения узлов, валидация и представление дополнительных ссылок.
- Именование методов и размещение классов по пакетам.
