# Структура классов узлов — согласованные решения

Обсуждение начато 3 ноября 2026 года. Этот документ фиксирует решения по развитию прототипа; реализация пока не изменена. Исследовательские предложения из [обзора языковых конструкций](research/language-nodes/README.ru.md) не считаются принятыми автоматически.

## 1. Отдельные классы конструкций

Принято: конкретные конструкции получают собственные Java-классы с именованными типизированными геттерами. Для общих алгоритмов классы объединяются базовыми категориями Node, Expression, Statement и другими по мере необходимости.

Примеры предполагаемых классов: BinaryExpression, CallExpression, IfStatement. Примеры доступа: left(), right(), operator(), callee(), arguments(), condition(), thenBranch(), elseBranch(). Полный состав классов и окончательное именование методов будут согласованы отдельно.

Класс соответствует конструкции и может переиспользоваться несколькими языками. Существенно отличающаяся конструкция получает отдельный класс. Цвет не закрепляется наследованием: допустимые языки могут зависеть от содержимого конкретного узла.

Общие возможности узлов сохраняются: обход детей, генерация исходника, получение поддерживаемых языков. Сохраняются неизменяемость готового графа и отдельная мутабельная модель. Каждому конкретному неизменяемому классу соответствует мутабельный класс: например, BinaryExpression и MutableBinaryExpression. Они предоставляют доступ к тем же смысловым составляющим; мутабельный вариант дополнительно имеет методы изменения. Сигнатуры доступа к ещё не заполненным обязательным полям уточняются отдельно с учётом запрета возвращать null.

## 2. Возвращаемые значения

Принято: методы API модели не возвращают null.

- Обязательное одиночное значение возвращается непосредственно как T. В валидном неизменяемом узле оно всегда присутствует.
- Необязательное одиночное значение возвращается как Optional<T>. При отсутствии — Optional.empty(); сам Optional никогда не равен null.
- Коллекция возвращается непосредственно как коллекция, без Optional. Отсутствие элементов обозначается пустой коллекцией, а не null.
- Коллекции, возвращаемые неизменяемыми классами, неизменяемы. Их содержимое не должно изменяться вслед за внешним списком или последующими изменениями билдера.
- Коллекции модели не содержат null-элементов.

Пример контракта:

```java
Expression condition();           // Обязательный ребёнок.
Optional<Statement> elseBranch();  // Необязательный ребёнок.
List<Expression> arguments();      // Неизменяемый, возможно пустой список.
```

Это правила публичного результата, а не требование хранить Optional в каждом внутреннем поле. Правила приёма null в аргументах, организация полей и доступ к коллекциям мутабельной модели ещё не согласованы.

## 3. Мутабельные классы и пакеты

Принято: мутабельные и неизменяемые классы размещаются в разных Java-пакетах. Конкретные имена пакетов пока не выбраны.

Предложение заказчика для обсуждения: использовать строителей внутри неизменяемых узлов для построения графа со сложными связями. Способ хранения строителя, момент фиксации связей и запрет последующих изменений ещё не согласованы. Это предложение пока не является утверждённой архитектурой.

## 4. Следующие вопросы

- Жизненный цикл строителей внутри неизменяемых узлов и получение замкнутого неизменяемого графа.
- Общий обход детей при наличии именованных геттеров.
- Способ построения узлов, валидация и представление дополнительных ссылок.
- Именование методов и размещение классов по пакетам.
