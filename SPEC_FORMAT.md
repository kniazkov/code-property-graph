# Спецификация формата утверждений и автоматических проверок

Версия: 0.1  
Дата: 2026-11-24  
Статус: черновик

## 1. Назначение

Документ описывает формат хранения переработанной спецификации языка программирования в виде набора независимо проверяемых утверждений, а также формат вспомогательных файлов и алгоритмы автоматических проверок.

Цели формата:

- представить спецификацию как конечное множество атомарных утверждений;
- обеспечить независимую проверку каждого утверждения;
- отделить нормативные требования от информативных примеров и примечаний;
- обеспечить трассируемость «утверждение → проверка → результат»;
- не хранить в открытом репозитории исходный текст спецификации;
- позволить использовать разные оракулы, не полагаясь только на компилятор.

Документ не является юридической консультацией. Вопросы распространения исходной спецификации и производных произведений должны быть проверены юристом.

## 2. Термины

**Утверждение** — минимальный фрагмент спецификации, который имеет один субъект, одну модальность и может быть проверен независимо.

**Нормативное утверждение** — утверждение, которое налагает требование, запрет или разрешение, либо определяет обязательное поведение.

**Информативное утверждение** — примечание, пример, пояснение или иной элемент, который не является требованием.

**Оракул** — источник ожидаемого результата проверки. Оракулом может быть правило спецификации, таблица, независимая грамматика, независимый вычислитель, формальная модель, метаморфическое отношение, компилятор или человек.

**Проверка** — воспроизводимый эксперимент, который сопоставляет утверждение с наблюдаемым результатом.

**Доверие** — оценка независимости и надёжности проверки. Доверие не равно «проверка прошла»; это свойство оракула.

**Провенанс** — сведения о происхождении утверждения: приватный локатор в исходном документе и отпечаток фрагмента. Провенанс не содержит исходного текста в открытом репозитории.

## 3. Юридическая рамка и провенанс

Смена формата не снимает автоматически авторско-правовую охрану. Переработка, перевод и пересказ могут быть производными произведениями. Поэтому в открытом репозитории хранятся только:

- независимо сформулированные утверждения;
- идентификаторы;
- проверки и тестовые данные;
- таблицы, полученные как факты;
- метаданные провенанса без исходного текста.

Исходные PDF/TXT/HTML и карта «утверждение → исходный абзац» хранятся в закрытом хранилище. В публичном репозитории допускаются только:

- `private_locator` — например, `p.9, 2.13.2/1`;
- `fingerprint` — хэш исходного фрагмента;
- `extracted_at` — дата извлечения;
- `reviewer` — идентификатор проверяющего.

Перед публикацией CI выполняет проверку на дословные совпадения с закрытым корпусом. Порог и алгоритм проверки задаются отдельно и не раскрывают исходный текст.

## 5. Общие правила формата

- Кодировка: UTF-8 без BOM.
- Переносы строк: LF.
- Отступы: два пробела, табы запрещены.
- Основной формат утверждений и проверок: YAML 1.2.
- Схемы: JSON Schema.
- Сгенерированные файлы в `generated/` не редактируются вручную.
- Все идентификаторы уникальны в пределах редакции.
- Идентификаторы не переиспользуются и не перенумеровываются.
- Изменения оформляются как дополнения или пометки `deprecated`, а не удаление.

## 6. Идентификаторы

Базовая схема:

```text
CPP03-<раздел>-<номер>
```

Примеры:

```text
CPP03-2.13.2-001
CPP03-5.1-004
CPP03-A-012
CPP03-DEF-007
```

Правила:

- `CPP03` — редакция языка.
- `<раздел>` — номер клаузы или приложения.
- `<номер>` — порядковый номер внутри раздела, начиная с `001`.
- Для определений используется `DEF`.
- Для грамматических продукций допускается `GRAM`.
- При объединении или разделении утверждений старый ID получает `deprecated: true`, а новый — `supersedes`.
- При переносе утверждения в другой раздел ID сохраняется, а `clause` обновляется.

## 7. Модель утверждения

### 7.1. Обязательные поля

```yaml
schema_version: 1
id: CPP03-2.13.2-001
edition: N1638
clause: "2.13.2"
type: requirement
modality: shall
normative: true
title: "Тип и значение обычного character literal"
statement: >
  Обычный character literal, содержащий ровно один c-char,
  имеет тип char, а его значение равно числовому значению
  кодировки этого c-char в execution character set.
subject: "ordinary character literal with one c-char"
condition: "literal is ordinary and contains exactly one c-char"
requirement: "type is char; value equals execution character set encoding"
exceptions: []
depends_on: []
related: []
provenance:
  private_locator: "p.9, 2.13.2/1"
  fingerprint: "sha256:..."
  extracted_at: "2026-11-24"
verification: []
status: draft
```

### 7.2. Типы утверждений

- `requirement` — требование, запрет или разрешение.
- `definition` — определение термина.
- `grammar` — грамматическая продукция.
- `constraint` — ограничение или диагностическое правило.
- `behavior_undefined` — неопределённое поведение.
- `behavior_implementation_defined` — поведение, определяемое реализацией.
- `behavior_unspecified` — неуказанное поведение.
- `informative_note` — примечание.
- `informative_example` — пример.
- `table_row` — строка таблицы требований.
- `cross_reference` — ссылка или зависимость.

### 7.3. Модальности

- `shall` — обязательное требование.
- `shall_not` — запрет.
- `may` — разрешение.
- `is` — определение или утверждение о типе/значении.
- `is_not` — отрицательное определение.
- `implementation_defined` — реализация обязана определить и документировать.
- `undefined` — требования отсутствуют.
- `unspecified` — реализация не обязана документировать.
- `informative` — информативное утверждение.

### 7.4. Правила атомизации

Одно утверждение должно содержать одно требование. Если предложение содержит несколько независимых требований, оно разделяется.

Пример исходного предложения:

> Обычный character literal с одним c-char имеет тип `char`, а его значение равно кодировке этого c-char.

Атомизация:

```text
CPP03-2.13.2-001: тип обычного character literal с одним c-char — char.
CPP03-2.13.2-002: значение обычного character literal с одним c-char равно кодировке c-char.
```

Если требование зависит от контекста, контекст записывается в `condition`, а не прячется в текст `statement`.

### 7.5. Нормативность

`normative: true` означает, что утверждение входит в покрытие соответствия. `normative: false` означает, что утверждение информативно; его можно проверять на консистентность, но нельзя требовать от реализации.

### 7.6. Статусы

- `draft` — черновик, проверки могут отсутствовать.
- `reviewed` — техническое и юридическое ревью пройдено.
- `verified` — все обязательные проверки проходят.
- `disputed` — есть спор о формулировке или оракуле.
- `deprecated` — утверждение заменено или удалено из новой редакции.
- `waived` — проверка официально отложена с указанием причины.

## 8. Модель проверки

### 8.1. Обязательные поля

```yaml
schema_version: 1
check_id: ast-type
statement_id: CPP03-2.13.2-001
kind: parser_ast
oracle: spec_rule
trust: high
inputs:
  source: "'a'"
expected:
  ast:
    kind: CharacterLiteral
    prefix: none
    cchars: ["a"]
    type: char
negative_control:
  mutate: "type: int"
  expected: fail
evidence:
  - parser_version
  - ast_dump
```

### 8.2. Виды проверок

- `parser_ast` — проверка AST, построенного парсером.
- `parser_diagnostic` — проверка диагностики парсера.
- `compile_pass` — программа должна компилироваться.
- `compile_fail` — программа должна отвергаться.
- `runtime` — программа должна дать ожидаемый результат.
- `table_driven` — проверка по таблице.
- `property` — проверка свойства.
- `metamorphic` — проверка эквивалентности преобразований.
- `round_trip` — проверка `parse → print → parse`.
- `differential` — сравнение с другим оракулом.
- `formal` — проверка формальной моделью.
- `manual` — ручная проверка.

### 8.3. Оракулы

- `spec_rule` — правило, непосредственно выведенное из утверждения.
- `spec_table` — таблица из спецификации.
- `independent_grammar` — грамматика, написанная отдельно от парсера.
- `independent_evaluator` — независимый вычислитель типов/значений.
- `formal_model` — формальная модель.
- `metamorphic_relation` — отношение эквивалентности.
- `compiler` — clang/g++ и другие компиляторы.
- `manual` — человек.

### 8.4. Уровни доверия

- `high` — таблица, инвариант, независимая формальная модель.
- `medium` — независимый парсер, независимый вычислитель, свойство.
- `low` — дифференциальная проверка компилятором, ручная проверка без формального критерия.

Доверие утверждения вычисляется так:

- `high`, если есть хотя бы одна проверка `high` и нет падений;
- `medium`, если нет `high`, но есть `medium` и нет падений;
- `low`, если есть только `low`;
- `none`, если обязательных проверок нет.

### 8.5. Результаты

- `pass` — результат совпал с ожидаемым.
- `fail` — результат не совпал.
- `error` — проверка не смогла выполниться.
- `skipped` — проверка не применима в данном окружении.
- `waived` — проверка официально отложена.
- `disputed` — результат требует ручного разбора.

### 8.6. Доказательства

Для каждой проверки сохраняются:

- версия парсера/инструмента;
- версия компилятора и флаги, если использовался компилятор;
- целевая платформа и кодировка;
- входные данные;
- ожидаемый результат;
- фактический результат;
- код возврата;
- хэш входных данных и тестового файла;
- дата и длительность выполнения.

## 9. Вспомогательные файлы

### 9.1. Схемы

`schema/statement.schema.json`, `schema/check.schema.json`, `schema/test.schema.json` описывают допустимые поля и типы. Схемы версионируются вместе с форматом.

### 9.2. Независимая грамматика

`grammar/com.kniazkov.cpg.ebnf` — грамматика, написанная независимо от парсера. Она используется для генерации тестов и для проверки покрытия продукций. Нельзя генерировать тесты той же грамматикой, из которой сгенерирован парсер.

`grammar/cpp03-negative.ebnf` — правила, описывающие заведомо невалидные конструкции для негативных тестов.

### 9.3. Таблицы

`tables/keywords.yaml`, `tables/alternative-tokens.yaml`, `tables/escape-sequences.yaml`, `tables/execution-charset.yaml` содержат факты, извлечённые из спецификации. Таблицы не содержат длинных цитат.

Пример:

```yaml
schema_version: 1
table: execution-charset
edition: N1638
charset: ascii
entries:
  "a": 97
  "A": 65
  "0": 48
  "\\n": 10
  "\\0": 0
```

### 9.4. Тесты

Тесты хранятся в `tests/` и описываются YAML-манифестами. Тест не содержит ожиданий, выведенных из самого парсера; ожидания берутся из утверждения, таблицы, независимой грамматики или независимого вычислителя.

Пример:

```yaml
schema_version: 1
test_id: char-literal-type
statement_id: CPP03-2.13.2-001
cases:
  - name: ordinary-single
    source: "'a'"
    expected:
      kind: CharacterLiteral
      prefix: none
      cchars: ["a"]
      type: char
  - name: wide-single
    source: "L'a'"
    expected:
      kind: CharacterLiteral
      prefix: wide
      cchars: ["a"]
      type: wchar_t
  - name: multichar
    source: "'ab'"
    expected:
      kind: CharacterLiteral
      prefix: none
      cchars: ["a", "b"]
      type: int
```

### 9.5. Оракулы

`oracles/` содержит независимые реализации правил. Например, `char_literal_eval.py` вычисляет значение character literal по таблице кодировки и правилам escape-последовательностей, не используя парсер.

### 9.6. Инструменты

`tools/validate.py` проверяет схемы и уникальность ID.  
`tools/verify.py` запускает проверки.  
`tools/coverage.py` строит отчёт о покрытии.  
`tools/diff.py` выполняет дифференциальные проверки.  
`tools/license_check.py` ищет дословные совпадения с закрытым корпусом.

### 9.7. Отчёты

`reports/results.json` содержит результаты проверок.  
`reports/coverage.json` содержит покрытие утверждений и продукций.  
`generated/statements.md` — человекочитаемая документация, собранная из утверждений.

## 10. Алгоритмы автоматических проверок

Ниже описаны алгоритмы проверок. Для каждого указаны назначение, входы, шаги, оракул, пример и ограничения.

### 10.1. Генерация по независимой грамматике

**Назначение.** Проверить, что парсер принимает все строки, выводимые из независимой грамматики, и строит ожидаемую структуру.

**Входы.** Независимая грамматика, генератор строк, парсер, правило сопоставления AST.

**Шаги.**

1. Загрузить независимую грамматику.
2. Сгенерировать строку с заданной глубиной вывода.
3. Сохранить вывод грамматики: продукцию, дерево вывода и ожидаемую структуру.
4. Передать строку парсеру.
5. Проверить, что парсер не вернул ошибку.
6. Сопоставить AST с ожидаемой структурой.
7. Повторить для всех продукций и глубин.

**Оракул.** Независимая грамматика и её дерево вывода.

**Пример.** Для продукции `nonzero-digit: one of 1 2 3 4 5 6 7 8 9` генератор создаёт строку `7`. Парсер должен построить узел `nonzero-digit` со значением `7`, а не `integer-literal` с другим разбором.

**Ограничение.** Если генератор и парсер используют одну и ту же грамматику, проверка циклическая. Грамматика должна быть написана отдельно.

### 10.2. Негативная генерация

**Назначение.** Проверить, что парсер отвергает строки, не выводимые из грамматики.

**Входы.** Независимая негативная грамматика или мутатор, парсер, ожидаемая диагностика.

**Шаги.**

1. Взять валидную строку.
2. Применить мутацию, которая нарушает конкретную продукцию.
3. Убедиться, что мутация действительно делает строку невалидной по независимой модели.
4. Передать строку парсеру.
5. Проверить, что парсер вернул ошибку.
6. Проверить категорию и позицию диагностики.
7. Убедиться, что валидная строка без мутации принимается.

**Оракул.** Независимая негативная грамматика или модель мутаций.

**Пример.** Для `integer-literal` заменить `0x` на `0z`. Парсер должен отвергнуть строку как некорректный hexadecimal-literal, а не принять её как identifier.

**Ограничение.** Не все мутации делают строку невалидной; такие случаи нужно отфильтровывать независимой моделью.

### 10.3. Покрытие продукций

**Назначение.** Убедиться, что каждая продукция независимой грамматики проверена хотя бы одним тестом.

**Входы.** Список продукций, тесты, карта `production → tests`.

**Шаги.**

1. Извлечь все продукции из грамматики.
2. Для каждого теста определить, какие продукции он покрывает.
3. Построить отчёт: покрытые, непокрытые, частично покрытые.
4. Для непокрытых продукций сгенерировать тесты.
5. Зафиксировать порог: 100% продукций для нормативных правил.

**Оракул.** Список продукций и карта покрытия.

**Пример.** Продукция `hex-quad` считается покрытой, если есть тест на `\u0041` и тест на `\U00000041`, где `hex-quad` встречается в разборе.

**Ограничение.** Покрытие продукций не гарантирует семантическую корректность.

### 10.4. Покрытие ошибок

**Назначение.** Убедиться, что каждая ожидаемая диагностика достижима и проверена.

**Входы.** Список диагностик из утверждений, тесты, карта `diagnostic → tests`.

**Шаги.**

1. Собрать все утверждения с `kind: constraint` или `parser_diagnostic`.
2. Для каждой диагностики создать минимальный негативный пример.
3. Проверить, что парсер выдаёт диагностику нужной категории.
4. Проверить, что позиция указывает на ожидаемый токен.
5. Проверить, что без нарушения диагностика не выдаётся.

**Оракул.** Утверждение и ожидаемая категория диагностики.

**Пример.** Для нарушения `integer-suffix` после `0x` парсер должен выдать диагностику «некорректный hexadecimal-literal», а не «неизвестный identifier».

**Ограничение.** Нельзя проверять точный текст сообщения; проверяется категория и позиция.

### 10.5. Maximal munch и инварианты токенизации

**Назначение.** Проверить, что лексер выбирает самый длинный допустимый токен и правильно обрабатывает перекрывающиеся последовательности.

**Входы.** Набор строк, таблица токенов, правила фаз перевода.

**Шаги.**

1. Составить строки, где возможны разные разбиения: `a+++++b`, `a+++b`, `>>=`, `>=`, `...`, `##`.
2. Для каждой строки перечислить все допустимые разбиения.
3. Выбрать разбиение по правилу максимального совпадения.
4. Сравнить с токенами парсера.
5. Проверить, что альтернативные токены (`and`, `&&`) дают одинаковую структуру.
6. Проверить digraph/trigraph и экранирование переводов строк.

**Оракул.** Таблица токенов и правила максимального совпадения.

**Пример.** Строка `a+++++b` должна разбираться как `a ++ ++ + b`, а не `a + ++ ++ b` или иначе. Если парсер выбирает другое разбиение, тест падает.

**Ограничение.** Некоторые последовательности зависят от контекста; их нужно вынести в отдельные утверждения.

### 10.6. Round-trip

**Назначение.** Проверить, что AST можно напечатать обратно в текст и снова разобрать без потери структуры.

**Входы.** Парсер, канонический принтер, функция сравнения AST.

**Шаги.**

1. Разобрать исходную строку в AST.
2. Напечатать AST каноническим принтером.
3. Разобрать напечатанную строку снова.
4. Сравнить AST с точностью до нормализации.
5. Повторить для корпуса валидных строк.

**Оракул.** Функция структурной эквивалентности AST.

**Пример.** `'a'` → AST → `'a'` → AST. Оба AST должны быть эквивалентны, включая тип `char` и значение.

**Ограничение.** Round-trip проверяет представимость, а не правильность семантики.

### 10.7. Метаморфические проверки

**Назначение.** Проверить, что преобразования, не меняющие смысл программы, не меняют AST или результат.

**Входы.** Набор преобразований, парсер, функция сравнения.

**Шаги.**

1. Взять валидную программу.
2. Применить преобразование: добавить пробелы, комментарии, переносы строк, заменить `and` на `&&`, заменить digraph на обычный символ.
3. Разобрать исходную и преобразованную программу.
4. Сравнить AST или результат.
5. Для преобразований, которые должны менять смысл, проверить ожидаемое изменение.

**Оракул.** Отношение эквивалентности, заданное утверждением.

**Пример.** `a and b` и `a && b` должны дать одинаковое AST. `'a'` и `'\x61'` на ASCII должны дать одинаковое значение.

**Ограничение.** Не все преобразования законны; список преобразований должен быть явным.

### 10.8. Грамматический фаззинг

**Назначение.** Найти падения, зависания и недетерминизм парсера.

**Входы.** Генератор строк, парсер, таймаут, инварианты.

**Шаги.**

1. Сгенерировать строку из грамматики или мутировать корпус.
2. Запустить парсер с таймаутом.
3. Проверить, что процесс завершился.
4. Проверить, что нет падения и утечек.
5. Проверить, что повторный запуск даёт тот же результат.
6. Сохранить минимальный воспроизводящий пример.

**Оракул.** Инварианты: завершение, отсутствие падения, детерминизм.

**Пример.** Сгенерировать глубоко вложенные скобки и проверить, что парсер не падает по переполнению стека, а выдаёт ошибку или обрабатывает вход.

**Ограничение.** Фаззинг не доказывает корректность; он ищет дефекты.

### 10.9. Мутационный фаззинг

**Назначение.** Проверить, что небольшие изменения валидной программы дают предсказуемое изменение AST или диагностику.

**Входы.** Корпус валидных программ, модель мутаций, парсер, ожидаемые изменения.

**Шаги.**

1. Взять валидную программу.
2. Применить мутацию: заменить оператор, литерал, идентификатор.
3. Определить ожидаемый эффект: ошибка, другой тип, другое значение.
4. Разобрать мутированную программу.
5. Сравнить с ожидаемым эффектом.
6. Сохранить мутанты, которые не были обнаружены.

**Оракул.** Модель мутаций и утверждение.

**Пример.** Заменить `'a'` на `'b'`; тип остаётся `char`, значение меняется на код `'b'`. Заменить `'a'` на `L'a'`; тип меняется на `wchar_t`.

**Ограничение.** Эквивалентные мутанты нужно исключать.

### 10.10. Независимый вычислитель

**Назначение.** Проверить типы и значения, вычисленные парсером, с помощью отдельной реализации правил.

**Входы.** AST, независимый вычислитель, таблицы, утверждения.

**Шаги.**

1. Передать AST независимому вычислителю.
2. Вычислитель применяет правила типов и значений.
3. Сравнить результат с результатом парсера.
4. При расхождении сохранить оба результата и минимальный пример.
5. Проверить негативный контроль: вычислитель должен отличать правильное значение от неправильного.

**Оракул.** Независимый вычислитель и таблицы.

**Пример.** Для `'a'` вычислитель берёт таблицу execution charset и возвращает `97` для ASCII; парсер должен вернуть то же значение.

**Ограничение.** Вычислитель и парсер могут иметь общую ошибку, если написаны по одной модели. Нужна независимая реализация.

### 10.11. Property-based testing

**Назначение.** Проверить свойства, которые должны выполняться для всех входов из заданного класса.

**Входы.** Генераторы, свойства, парсер.

**Шаги.**

1. Сформулировать свойство: например, `'0' + 1 == '1'`.
2. Сгенерировать входы, удовлетворяющие предусловию.
3. Проверить свойство на каждом входе.
4. При нарушении сохранить минимальный контрпример.
5. Повторить с разными seed.

**Оракул.** Свойство, выведенное из утверждения.

**Пример.** Для всех цифр `d` от `0` до `8` должно выполняться `'d' + 1 == 'd+1'`. Для всех обычных character literal с одним c-char тип должен быть `char`.

**Ограничение.** Свойство нужно доказать или обосновать; иначе можно проверять ложное утверждение.

### 10.12. Table-driven проверки

**Назначение.** Проверить поведение по таблицам, извлечённым из спецификации.

**Входы.** Таблица, парсер, правило сопоставления.

**Шаги.**

1. Загрузить таблицу.
2. Для каждой строки таблицы построить вход.
3. Получить результат парсера.
4. Сравнить с ожидаемым значением из таблицы.
5. Проверить, что все строки таблицы покрыты.
6. Проверить негативный контроль: изменить ожидание и убедиться, что тест падает.

**Оракул.** Таблица.

**Пример.** Таблица escape-последовательностей: `\n` → 10, `\t` → 9, `\0` → 0. Парсер должен выдавать эти значения.

**Ограничение.** Таблица должна быть извлечена без ошибок; ошибка в таблице делает проверку ложной.

### 10.13. Проверки таблицы типов и ограничений

**Назначение.** Проверить инварианты таблицы символов, областей видимости и преобразований типов.

**Входы.** AST, таблица символов, модель типов.

**Шаги.**

1. Построить таблицу символов.
2. Проверить, что каждое имя имеет ровно одно объявление в области видимости.
3. Проверить, что ссылки разрешаются в допустимые объявления.
4. Проверить, что преобразования типов соответствуют правилам.
5. Проверить, что запрещённые преобразования отвергаются.

**Оракул.** Независимая модель типов и ограничений.

**Пример.** Для `int x; x = 'a';` преобразование `char` в `int` разрешено; для `int* p; p = 'a';` должно быть отвергнуто.

**Ограничение.** Применимо только к формализуемому подмножеству.

### 10.14. Абстрактная интерпретация

**Назначение.** Проверить постоянные выражения, переполнения, promotions и сужение типов без выполнения программы.

**Входы.** AST, абстрактная семантика, домены значений.

**Шаги.**

1. Построить абстрактное состояние.
2. Вычислить значение выражения в абстрактном домене.
3. Проверить, что результат соответствует утверждению.
4. Проверить, что неопределённые операции дают `undefined`.
5. Сравнить с независимым вычислителем.

**Оракул.** Абстрактная семантика.

**Пример.** Для `2147483647 + 1` в 32-битном `int` результат должен быть `undefined` или `long` в зависимости от правил; абстрактная интерпретация должна это показать.

**Ограничение.** Сложно для всего языка; эффективно для подмножества.

### 10.15. SMT и bounded model checking

**Назначение.** Формально проверить выполнимость ограничений для небольшого подмножества.

**Входы.** Формальная модель, ограничения, решатель SMT.

**Шаги.**

1. Закодировать утверждение и правила в логику.
2. Сформулировать проверяемое свойство.
3. Запустить решатель.
4. Если свойство не выполняется, получить контрпример.
5. Проверить контрпример на парсере.
6. Зафиксировать границы модели.

**Оракул.** Формальная модель и решатель.

**Пример.** Проверить, что для всех `c-char` из заданного множества тип литерала `char`, а значение лежит в диапазоне `char`.

**Ограничение.** Не масштабируется на весь C++; применимо к отдельным правилам.

### 10.16. Дифференциальный интерпретатор

**Назначение.** Сравнить два независимых вычислителя семантики.

**Входы.** Два интерпретатора, корпус программ.

**Шаги.**

1. Выполнить программу в первом интерпретаторе.
2. Выполнить ту же программу во втором.
3. Сравнить результаты, типы и диагностику.
4. При расхождении сохранить минимальный пример.
5. Классифицировать расхождение: баг, неопределённое поведение, разная модель.

**Оракул.** Второй интерпретатор.

**Пример.** Один интерпретатор считает `'a'` как ASCII 97, второй — как EBCDIC; расхождение должно быть объяснено окружением, а не считаться багом.

**Ограничение.** Оба интерпретатора могут ошибаться одинаково.

### 10.17. Дифференциальная проверка двух парсеров

**Назначение.** Сравнить два независимых парсера на одном корпусе.

**Входы.** Два парсера, корпус, функция сравнения AST.

**Шаги.**

1. Разобрать корпус первым парсером.
2. Разобрать корпус вторым.
3. Сравнить accept/reject.
4. Сравнить AST с точностью до нормализации.
5. Классифицировать расхождения.
6. Сохранить минимальные примеры.

**Оракул.** Второй парсер.

**Пример.** Hand-written recursive descent и parser generator должны одинаково разбирать `a+++++b`.

**Ограничение.** Нужны действительно независимые реализации.

### 10.18. Дифференциальная проверка с clang/g++

**Назначение.** Использовать публичные компиляторы как дополнительный оракул.

**Входы.** Парсер, clang/g++, корпус, матрица версий.

**Шаги.**

1. Зафиксировать версии компиляторов и флаги.
2. Скомпилировать корпус.
3. Сравнить accept/reject и диагностику по категориям.
4. Сравнить поведение, если оно определено.
5. Классифицировать расхождения: баг парсера, расширение компилятора, баг компилятора, неопределённое поведение.
6. Не делать компилятор единственным оракулом.

**Оракул.** Компилятор.

**Пример.** Парсер принимает `'a'` как `char`; clang и g++ тоже. Если один компилятор расходится, это повод для разбора, а не автоматический приговор.

**Ограничение.** Компиляторы не эталон; они могут поддерживать расширения и иметь баги.

### 10.19. Дифференциальная проверка по версиям

**Назначение.** Убедиться, что поведение не зависит от версии компилятора или платформы.

**Входы.** Матрица версий, корпус, парсер.

**Шаги.**

1. Запустить проверки на каждой версии.
2. Сравнить результаты.
3. Выделить различия, связанные с реализацией.
4. Обновить таблицы окружения.
5. Зафиксировать поддерживаемые версии.

**Оракул.** Матрица версий и утверждение.

**Пример.** `sizeof(int)` различается на платформах; утверждение о диапазоне integer literal должно быть параметризовано моделью данных.

**Ограничение.** Дорого по времени; используется для ключевых утверждений.

### 10.20. Дифференциальная проверка с conformance suite

**Назначение.** Сравнить парсер с открытым набором тестов соответствия.

**Входы.** Conformance suite, парсер, лицензия suite.

**Шаги.**

1. Проверить совместимость лицензии.
2. Запустить suite.
3. Сопоставить тесты с утверждениями.
4. Сравнить результаты.
5. Зафиксировать расхождения.

**Оракул.** Внешний suite.

**Пример.** Открытый набор тестов на лексику C++03.

**Ограничение.** Лицензия suite должна позволять использование; suite может быть неполным.

### 10.21. Compile-fail тесты

**Назначение.** Проверить, что невалидная программа отвергается с диагностикой нужной категории.

**Входы.** Негативный пример, компилятор или парсер, ожидаемая категория.

**Шаги.**

1. Подготовить минимальный пример.
2. Запустить компилятор/парсер.
3. Проверить, что получена ошибка.
4. Проверить категорию и позицию.
5. Проверить, что без ошибки пример компилируется.
6. Сохранить доказательство.

**Оракул.** Утверждение и ожидаемая категория.

**Пример.** `int asm;` должно быть отвергнуто, потому что `asm` — ключевое слово.

**Ограничение.** Не проверять точный текст сообщения.

### 10.22. Негативный контроль

**Назначение.** Убедиться, что проверка действительно различает правильный и неправильный результат.

**Входы.** Проверка, мутация ожидаемого результата.

**Шаги.**

1. Взять проверку, которая проходит.
2. Изменить ожидаемый результат на заведомо неверный.
3. Запустить проверку.
4. Убедиться, что она падает.
5. Вернуть исходное ожидание.

**Оракул.** Мутация ожидания.

**Пример.** Для `'a' == 97` заменить ожидание на `98`; тест должен упасть. Если он проходит, проверка бесполезна.

**Ограничение.** Мутация должна быть семантически значимой.

### 10.23. Мутационное тестирование

**Назначение.** Проверить, что тесты ловят дефекты в парсере.

**Входы.** Парсер, набор мутантов, тесты.

**Шаги.**

1. Внести мутацию в парсер: изменить правило, условие, границу.
2. Запустить тесты.
3. Если тесты не упали, мутант выжил.
4. Проанализировать выживших.
5. Добавить тесты или признать мутанта эквивалентным.

**Оракул.** Набор тестов и мутанты.

**Пример.** Заменить в парсере тип character literal с `char` на `int`; тест типа должен упасть.

**Ограничение.** Эквивалентные мутанты не обнаруживаются.

### 10.24. Проверка детерминизма

**Назначение.** Убедиться, что повторный запуск даёт тот же результат.

**Входы.** Парсер, корпус, несколько запусков.

**Шаги.**

1. Запустить парсер на корпусе.
2. Повторить запуск.
3. Сравнить AST, диагностику и код возврата.
4. Проверить, что порядок обхода стабилен.
5. Проверить, что нет зависимости от времени, сети и случайности.

**Оракул.** Идемпотентность.

**Пример.** Два запуска на `'a'` должны дать одинаковый AST и значение.

**Ограничение.** Не ловит логические ошибки, только недетерминизм.

### 10.25. Покрытие утверждений

**Назначение.** Убедиться, что у каждого нормативного утверждения есть проверка.

**Входы.** Список утверждений, список проверок.

**Шаги.**

1. Загрузить все утверждения.
2. Для каждого найти проверки по `statement_id`.
3. Построить отчёт: покрытые, непокрытые, waived.
4. Для непокрытых нормативных утверждений — ошибка CI.
5. Для информативных — предупреждение.

**Оракул.** Модель утверждений и проверок.

**Пример.** `CPP03-2.13.2-001` имеет проверки `ast-type` и `value-table`; покрытие — 100%.

**Ограничение.** Наличие проверки не гарантирует её качество; нужна проверка оракулов.

### 10.26. Покрытие проверок

**Назначение.** Убедиться, что каждая проверка привязана к утверждению.

**Входы.** Проверки, утверждения.

**Шаги.**

1. Загрузить все проверки.
2. Проверить наличие `statement_id`.
3. Проверить, что утверждение существует.
4. Найти «сиротские» проверки.
5. Удалить или привязать их.

**Оракул.** Ссылочная целостность.

**Пример.** Проверка `char-literal-diff` без `statement_id` — ошибка.

**Ограничение.** Не проверяет качество проверки.

### 10.27. Разнообразие оракулов

**Назначение.** Убедиться, что утверждение не проверяется только компилятором.

**Входы.** Проверки, оракулы, уровни доверия.

**Шаги.**

1. Для каждого утверждения собрать множество оракулов.
2. Проверить, что есть хотя бы один оракул, отличный от `compiler`.
3. Если нет — пометить `trust: low` и потребовать ручное ревью.
4. Построить отчёт по утверждениям с низким доверием.

**Оракул.** Политика доверия.

**Пример.** Утверждение с единственной проверкой `compiler-diff` получает `trust: low`.

**Ограничение.** Не все утверждения можно проверить без компилятора; для них нужен waiver.

### 10.28. Замыкание зависимостей

**Назначение.** Убедиться, что проверка не требует необъявленных утверждений или ресурсов.

**Входы.** Граф `depends_on`, проверки, ресурсы.

**Шаги.**

1. Построить граф зависимостей утверждений.
2. Для каждой проверки найти используемые утверждения и файлы.
3. Проверить, что все зависимости объявлены.
4. Проверить отсутствие циклов.
5. Проверить, что порядок выполнения не влияет на результат.

**Оракул.** Граф зависимостей.

**Пример.** Проверка значения `'a'` зависит от таблицы `execution-charset`; таблица должна быть объявлена.

**Ограничение.** Не проверяет семантику зависимостей.

### 10.29. Регрессионное сопоставление

**Назначение.** Убедиться, что изменение утверждения запускает ровно нужный набор проверок.

**Входы.** Diff утверждений, карта `statement → checks`, CI.

**Шаги.**

1. Сравнить старую и новую версии утверждений.
2. Определить изменённые ID.
3. Найти проверки, привязанные к ним.
4. Запустить эти проверки и зависимости.
5. Проверить, что не затронуты несвязанные проверки.
6. Сохранить отчёт.

**Оракул.** Карта покрытия и diff.

**Пример.** Изменение `CPP03-2.13.2-001` запускает `ast-type`, `value-table`, `metamorphic`, но не проверки integer literal.

**Ограничение.** Требует стабильных ID и корректной карты.

## 13. Пример независимого оракула

```python
def eval_char_literal(literal, charset):
    prefix, body = split_prefix(literal)
    if prefix == "L":
        raise NotApplicable("wide literal is a different statement")
    chars = parse_cchars(body)
    if len(chars) != 1:
        raise NotApplicable("multichar literal is a different statement")
    return charset[chars[0]]
```

Оракул не вызывает парсер. Он использует таблицу кодировки и правила escape-последовательностей.

## 14. CI-конвейер

1. Проверить YAML по схемам.
2. Проверить уникальность ID.
3. Проверить ссылочную целостность `depends_on` и `related`.
4. Проверить, что у каждого нормативного утверждения есть проверка.
5. Проверить разнообразие оракулов.
6. Запустить проверки.
7. Собрать `reports/results.json`.
8. Собрать `reports/coverage.json`.
9. Проверить дословные совпадения с закрытым корпусом.
10. Сгенерировать `generated/statements.md` и `generated/statements.db`.
11. Опубликовать отчёт.

Падение CI обязательно при:

- невалидной схеме;
- дубликате ID;
- нормативном утверждении без проверки;
- падении обязательной проверки;
- проверке без `statement_id`;
- дословном совпадении с закрытым корпусом.

Предупреждение CI допускается при:

- информативном утверждении без проверки;
- утверждении с `trust: low`;
- waived-проверке;
- отсутствии опциональной дифференциальной проверки.

## 15. Критерий satisfactory-парсера

Парсер считается удовлетворительным, если:

- каждое нормативное утверждение имеет хотя бы одну проверку;
- у каждого нормативного утверждения есть хотя бы одна проверка с оракулом, отличным от компилятора, либо официальный waiver;
- все обязательные проверки проходят;
- все проверки детерминированы и воспроизводимы;
- покрытие утверждений и продукций зафиксировано в отчёте;
- нет «сиротских» проверок;
- нет дословных совпадений с закрытым корпусом;
- результаты проверок сохранены с доказательствами.

## 16. Пилот

Для первой итерации предлагается:

- одна клауза, например `2.13.2`;
- 30–50 утверждений;
- одна независимая грамматика;
- три таблицы: ключевые слова, escape-последовательности, execution charset;
- 10–15 проверок;
- один независимый вычислитель;
- CI с покрытием и негативным контролем.

После пилота нужно ответить на вопросы:

- где ломается атомизация;
- сколько утверждений реально в клаузе;
- какие проверки дают ложные срабатывания;
- какие утверждения невозможно проверить без компилятора;
- сколько времени занимает ревью.
