# План реализации C++03 в Code Property Graph

## Как читать план. Зелёные и красные узлы

**Зелёный узел** описывает конструкцию программы через понятия, общие для нескольких языков. Например, узел «добавить элемент в конец динамического массива» указывает, какой контейнер изменяется и какое значение в него добавляется. Проход анализа может использовать эти сведения независимо от того, как операция записывается в исходном языке.

**Красный узел** описывает конструкцию в терминах конкретного языка. Например, вызов выбранной перегрузки `std::vector<int>::push_back` хранит сведения о вызываемом методе C++. Красный узел допустим и в полностью разобранной программе. Цвет обозначает зависимость от языка. В одном дереве могут соседствовать узлы обоих видов.

**Озеленение** — отдельный проход, который распознаёт языковую конструкцию или сочетание узлов и строит для неё эквивалентное представление из общих узлов. Например, после разрешения имён проход может представить переменную типа `std::vector<int>` как динамический массив целых, а вызов `v.push_back(x)` — как добавление значения `x` в конец `v`. Основанием служат тип контейнера и выбранная операция. Одного совпадения имени `push_back` недостаточно. Если подходящего преобразования нет, конструкция сохраняется в исходной форме. Исходный снимок графа остаётся доступен.


Рабочая версия. Цель — прочитать проект C++03, построить неизменяемый граф, разрешить сущности языка и стандартной библиотеки, выполнить анализ и сгенерировать C++03. Галочка означает, что результат доступен через штатный API и проверен. Этапы описывают работу небольшими изменениями. Конструкцию можно провести через несколько этапов раньше остальных, если выполнены её зависимости.

- [ ] Поставлять профиль размеров типов по умолчанию: `int` — 32 бита, `long` — 64 бита. Описать всю таблицу профиля с единицами измерения. Для каждой единицы трансляции позволить явно задавать профиль через параметры или файл настроек (например, JSON).
- [ ] Применять эффективный профиль при определении диапазонов, вычислении констант, `sizeof` и озеленении типов. Учитывать число битов в байте целевой платформы. Согласовать с профилем знаковость `char`, тип `wchar_t`, кодировки и предопределённые макросы. Выдавать диагностику для несовместимых настроек.
- [ ] Задать в профиле по умолчанию выравнивание типов и правила размещения полей; разрешить их явное переопределение. Документировать единицы, выравнивание самого агрегата и правила хвостового заполнения. Различать отсутствие переопределения (наследуется значение профиля) и отсутствие известного правила в эффективном профиле.
- [ ] Сворачивать корректное выражение `sizeof(S)` только при наличии всех данных для данного типа. Иначе сохранить выражение и представить его значение как неизвестное. Отдельно диагностировать недопустимое применение `sizeof`, например к неполному классу.
- [ ] Если численная граница массива зависит от неизвестного параметра профиля, хранить у типа массива выражение границы со ссылками на его операнды. Для `char buf[sizeof(S) + 1];` проверить через API и JSON операцию сложения, ссылку на тип `S` и литерал `1`. Генератор должен воспроизвести эквивалентную границу. При повторном анализе с профилем, где размер `S` равен 8 байтам, получить длину 9; исходный снимок сохраняет символическую границу.
- [ ] Проверить `struct S { char c; int i; };` при восьмибитном байте и четырёхбайтовом `int`: в профиле с выравниванием поля и структуры на 4 байта и округлением размера до этого выравнивания ожидать 8 байт; при плотном размещении с выравниванием на 1 байт — 5. При неизвестном правиле размещения оставить `sizeof(S)` без свёртки.
- [ ] Проверить один исходник с профилем по умолчанию и с переопределением `long` в 32 бита. При восьмибитном байте `sizeof(long)` должен дать 8 и 4 соответственно. В обоих профилях перегрузки `f(int)` и `f(long)` остаются различимыми, включая случай одинаковой ширины.
- [ ] При озеленении целого типа дать анализу общие свойства (знаковость и ширину в битах), сохранить связь с исходным типом C++ и у вызова — с выбранной перегрузкой. Одинаковые ширина и знаковость не делают `int` и `long` взаимозаменяемыми при генерации C++.
- [ ] Сквозной тест для профиля с 32-битными `int` и `long`: определить `f(int)` и `f(long)` с разными результатами, вызвать `f(1)` и `f(1L)`. Проверить обе цели после озеленения, наличие суффикса `L` при обратной генерации и выбор тех же перегрузок после повторного разбора.
- [ ] Проверить два .cpp с одним config.h и разными -DWIDE. Обе версии typedef должны существовать в одном Project с одинаковым исходным диапазоном и разной привязкой в каждой единице.
- [ ] Проверить изоляцию макросов соседних единиц, стабильность графа при повторном запуске и диагностику конфликтующих настроек.

## 3. Происхождение макросов и обратная генерация

- [ ] Сохранить событие раскрытия со ссылками на вызов, действовавшее определение, фактические аргументы и родительское раскрытие. Для # и ## хранить участвующие фрагменты.

- [ ] Сохранить границы замещения на уровне токенов. Макрос может породить несколько инструкций, часть выражения или вообще ни одного узла. Проверить эти случаи отдельно от макроса, соответствующего целому поддереву.
- [ ] При выводе неизменённого раскрытия восстанавливать исходный вызов, если при повторном препроцессировании он даст тот же результат. Для изменённого участка выводить изменённый код и сохранять происхождение в графе.

- [ ] Инвентаризировать разделы библиотеки по заголовкам и семействам: языковая поддержка, диагностика, утилиты и память, строки, локали, контейнеры, итераторы, алгоритмы, численные средства, ввод-вывод и средства из C. Отмечать отдельно разрешение объявления и наличие модели поведения.
- [ ] Первым провести std::vector<int> через весь конвейер. Разрешить тип и push_back, сохранить исходное написание. На green представить динамический массив int и добавление в конец. Отразить чтение аргумента и изменение контейнера.
- [ ] Проверить typedef для vector, квалифицированное имя и using. Метод push_back пользовательского типа должен остаться пользовательским вызовом. Для vector<bool> отдельно проверить прокси-ссылку до применения общих правил.
- [ ] Добавлять отдельными группами доступ к элементам, размер, пустоту и итерацию. Для каждой операции фиксировать наблюдаемые эффекты, предусловия и условия безопасной замены. Детали перераспределения памяти не входят в модель динамического массива.
- [ ] Для разрешённой операции без зелёного эквивалента сохранить C++-вызов и цель. При неизвестных эффектах анализ обязан учитывать возможное изменение доступных данных.
- [ ] Проверить каталог без системной STL. Для контрольных E2E компилировать сгенерированную программу настоящим компилятором и его библиотекой.

## 9. Потоки, диагностика, генерация и приёмка

- [ ] Расширять CFG вместе с инструкциями. Включить короткое замыкание, ветвление ?:, switch, переходы, нормальные и исключительные выходы, неявные вызовы деструкторов. Не придумывать порядок вычисления там, где язык его оставляет открытым.
- [ ] Представить в CFG неявный вызов деструктора со ссылками на объект и выбранный деструктор. Включать его на каждом пути выхода из области после успешного создания объекта, в том числе при возврате и раскрутке стека. Генератор C++ сохраняет исходную автоматическую длительность хранения и не вставляет явный вызов деструктора.
- [ ] E2E: для `Guard a; Guard b; work();` проверить порядок разрушения `b, a` при обычном выходе и при исключении из `work()`, перехваченном вызывающей функцией. Если конструктор `b` бросил исключение, среди этих двух объектов разрушается только `a`. Сверить пути CFG с журналом вызовов сгенерированной программы, включая число разрушений.
- [ ] Для внешней функции без доступного тела и без ограничивающей спецификации исключений строить обычное продолжение и возможный исключительный выход. Провести исключительный путь через разрушение уже созданных локальных объектов к подходящему обработчику либо к исключительному выходу вызывающей функции.
- [ ] Парный тест CFG: поместить `Guard g; work();` внутрь `try` с `catch (...)`. Для объявления `void work();` проверить путь от вызова через разрушение `g` к обработчику. Для `void work() throw();` такого пути от вызова нет. На обычном выходе в обоих случаях `g` разрушается один раз.
- [ ] Расширять DFG для адресов, ссылок, полей, элементов массива, параметров и возвратов. Проверить запись через указатель и чтение через другой указатель на тот же объект. При неполной информации использовать консервативный результат.
- [ ] Обновить UnreadWrites на исключительных путях, вызовах и записи через псевдонимы. Проверить отсутствие ложного предупреждения, когда значение может быть прочитано.
- [ ] Генерировать корректный C++03 для каждого принятого вида узла. Проверять объявления до использования, квалификацию, приоритет, сохранение заголовков и границ единиц трансляции. Для C++-специфичных конструкций явно обозначить границу межъязыковой генерации.
- [ ] Сопоставлять диагностику с файлом, диапазоном, единицей трансляции и цепочкой макросов. Проверить детерминированность JSON и отсутствие устаревших ссылок после edit/build и повторного анализа.
- [ ] На каждую главу стандарта собрать положительные, отрицательные и пограничные случаи. Отдельно учитывать неопределённое, неуточнённое и зависящее от реализации поведение. Ответ компилятора использовать как дополнительную проверку.
- [ ] Итоговый E2E: многофайловая программа с пользовательским заголовком, макросами, шаблоном, vector, виртуальным вызовом и исключением. Проверить связи в JSON, происхождение раскрытия, эффекты контейнера, генерацию, сборку и вывод.
- [ ] Перед объявлением поддержки пройти матрицу по каждому правилу и обязательному заголовку, перечислить оставшиеся пробелы и ограничения профиля в RU/EN. Результат отдельного демонстрационного примера закрывает только соответствующий сценарий.
