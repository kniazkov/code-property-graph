# План реализации C++03 в Code Property Graph

[Журнал вопросов и решений](CPP03-DECISIONS.ru.md). Обновлять журнал и этот чеклист не реже одного раза за каждые три вопроса.

## Как читать план. Зелёные и красные узлы

**Зелёный узел** описывает конструкцию программы через понятия, общие для нескольких языков. Например, узел «добавить элемент в конец динамического массива» указывает, какой контейнер изменяется и какое значение в него добавляется. Проход анализа может использовать эти сведения независимо от того, как операция записывается в исходном языке.

**Красный узел** описывает конструкцию в терминах конкретного языка. Например, вызов выбранной перегрузки `std::vector<int>::push_back` хранит сведения о вызываемом методе C++. Красный узел допустим и в полностью разобранной программе. Цвет обозначает зависимость от языка. В одном дереве могут соседствовать узлы обоих видов.

**Озеленение** — отдельный проход, который распознаёт языковую конструкцию или сочетание узлов и строит для неё эквивалентное представление из общих узлов. Например, после разрешения имён проход может представить переменную типа `std::vector<int>` как динамический массив целых, а вызов `v.push_back(x)` — как добавление значения `x` в конец `v`. Основанием служат тип контейнера и выбранная операция. Одного совпадения имени `push_back` недостаточно. Если подходящего преобразования нет, конструкция сохраняется в исходной форме. Исходный снимок графа остаётся доступен.


Рабочая версия. Цель — прочитать проект C++03, построить неизменяемый граф, разрешить сущности языка и стандартной библиотеки, выполнить анализ и сгенерировать C++03. Галочка означает, что результат доступен через штатный API и проверен. Этапы описывают работу небольшими изменениями. Конструкцию можно провести через несколько этапов раньше остальных, если выполнены её зависимости.

### Корпус сквозных тестов и ручной запуск

- [ ] Расширять корпус вместе с матрицей покрытия. Для каждой группы правил добавлять минимальные положительные и отрицательные примеры и сценарии взаимодействия с уже реализованными конструкциями. Для диагностического сценария документировать ожидаемую ошибку.
- [ ] Расширить существующий CliSandbox загрузкой каталога с сохранением вложенных путей. В CI на каждом PR и основной ветке запускать весь корпус через mvn verify с упакованным JAR. Сбой любого сценария завершает проверку ошибкой. Проверять число обнаруженных сценариев по перечню корпуса, чтобы случайное исключение теста не дало зелёную сборку.
- [ ] На Linux для каждого исполняемого сценария C++03 собирать исходную и сгенерированную программы как GCC (`g++`), так и Clang (`clang++`) с флагами `-std=c++03 -pedantic-errors`. Для каждой сборки проверить код выхода и ожидаемый вывод. В сценариях редактирования задать отдельные ожидания до и после изменения. Обе проверки обязательны на PR и в основной ветке; отсутствие компилятора или пропуск сценария считается ошибкой CI. Указывать версию компилятора и команду при сбое.
- [ ] Дать возможность повторить один сценарий локально через Failsafe и отдельно запустить CPG на его исходниках. Для исполняемых примеров с определённым поведением сравнивать результаты исходной и сгенерированной программ; для графа и диагностики проверять ожидаемые узлы, связи и позиции.

- [ ] Прочитать пример через CLI. В JSON проверить два чтения одного аргумента; в SVG показать, как от умножения перейти к вызову в .cpp и оператору в .h. Дать команды воспроизведения и указать ожидаемые фрагменты графа.
- [ ] Через API редактирования заменить правый операнд только первого раскрытия. Сгенерировать C++ и проверить, что изменился этот участок, а общий заголовок и второй вызов макроса сохранились. Собрать обе единицы вместе и запустить программу. Подобрать различные значения операндов и проверить заранее рассчитанные результаты до и после правки.
- [ ] Считать веху завершённой, когда сценарий проходит в полном CI и воспроизводится вручную из того же каталога по опубликованным командам.

## 1. Входной проект, единицы трансляции и профиль

- [ ] Добавить редакцию C++ в параметры парсера Java API и предоставить тот же выбор в CLI, например `--from cpp --cpp-standard c++03`. На этом этапе C++03 — единственная поддерживаемая редакция и значение по умолчанию. Проверить, что прежний вызов API без версии и CLI с `--from cpp` без `--cpp-standard` дают тот же граф, что и явный выбор C++03 для того же исходника. Передавать выбранную редакцию препроцессору и парсеру. Проверить одинаковый граф при явном выборе C++03 обоими способами и понятную ошибку для явно запрошенной неподдерживаемой редакции.
- [ ] Оставить чтение папки простым входом. Добавить в API описание сборки с перечнем единиц трансляции, рабочей папкой, упорядоченными путями заголовков и начальными определениями/отменами макросов для каждой единицы.
- [ ] Обязательно поддержать импорт `compile_commands.json` через CLI и Java API в ту же модель единиц трансляции. Прочитать `directory`, `file` и аргументы из `arguments` либо `command`. Разбирать командную строку без запуска компилятора или оболочки. Относительные пути разрешать от рабочего каталога записи.
- [ ] Определять редакцию для каждой записи базы в порядке приоритета: явный выбор в API или CLI, затем `-std` данной команды компиляции, затем C++03 по умолчанию. Различать явно выбранный C++03 и отсутствие выбора. При неподдерживаемой эффективной редакции сообщать имя файла и редакцию.
- [ ] E2E: в одной базе задать для `a.cpp` редакцию C++03, а для `b.cpp` — C++11. Оба исходника используют только конструкции C++03. Без явного выбора ожидать ошибку с указанием `b.cpp` и C++11. С явным выбором C++03 через CLI и API ожидать успешный разбор обоих файлов. Затем добавить в `b.cpp` лямбду и проверить, что при том же переопределении разбор сообщает об ошибке C++03.
- [ ] Сохранить порядок путей поиска и операций `-D`/`-U`, поддержать слитную и раздельную запись аргументов. Выдавать диагностику с именем файла для неподдержанных ключей, влияющих на разбор.
- [ ] Сквозной тест CLI: импортировать базу из другого рабочего каталога, передать путь с пробелом и разные определения для двух файлов. Сравнить типы и ссылки в JSON с результатом явного задания тех же параметров через API.
- [ ] Сохранять в одном `Project` отдельную единицу трансляции для каждого варианта сборки одного `.cpp`. Дать анализу возможность перечислить варианты по пути и выбрать конкретный вариант. Одного пути файла недостаточно для идентификации единицы.
- [ ] E2E: импортировать две записи для `engine.cpp` с `-DSERVER` и `-DCLIENT`. Проверить наличие обеих единиц и выбор каждой через API. В каждой версии вызов должен указывать на объявление из активной ветви; CFG и DFG одной версии не должны содержать рёбер в альтернативную версию.
- [ ] Дать возможность явно задать состав каждой сборки как набор выбранных единиц трансляции. При поиске определения из другой единицы учитывать состав выбранной сборки. Если состав неизвестен и подходят несколько определений, вернуть все возможные цели и обозначить неоднозначность.
- [ ] E2E: серверная и клиентская версии main.cpp вызывают run() из своих версий engine.cpp. При явном составе проверить обе пары целей, при неизвестном составе — множество из двух возможных определений. Отличать этот случай от нарушения правила одного определения внутри одной известной сборки.
- [ ] Отделить физический файл, конкретное включение и единицу трансляции. Повторное чтение файла допускает общий исходный текст. Результат раскрытия зависит от контекста в точке включения.
- [ ] Поставлять профиль размеров типов по умолчанию: `int` — 32 бита, `long` — 64 бита. Описать всю таблицу профиля с единицами измерения. Для каждой единицы трансляции позволить явно задавать профиль через параметры или файл настроек (например, JSON).
- [ ] Применять эффективный профиль при определении диапазонов, вычислении констант, `sizeof` и озеленении типов. Учитывать число битов в байте целевой платформы. Согласовать с профилем знаковость `char`, тип `wchar_t`, кодировки и предопределённые макросы. Выдавать диагностику для несовместимых настроек.
- [ ] Задать в профиле по умолчанию выравнивание типов и правила размещения полей; разрешить их явное переопределение. Документировать единицы, выравнивание самого агрегата и правила хвостового заполнения. Различать отсутствие переопределения (наследуется значение профиля) и отсутствие известного правила в эффективном профиле.
- [ ] Сворачивать корректное выражение `sizeof(S)` только при наличии всех данных для данного типа. Иначе сохранить выражение и представить его значение как неизвестное. Отдельно диагностировать недопустимое применение `sizeof`, например к неполному классу.
- [ ] Если численная граница массива зависит от неизвестного параметра профиля, хранить у типа массива выражение границы со ссылками на его операнды. Для `char buf[sizeof(S) + 1];` проверить через API и JSON операцию сложения, ссылку на тип `S` и литерал `1`. Генератор должен воспроизвести эквивалентную границу. При повторном анализе с профилем, где размер `S` равен 8 байтам, получить длину 9; исходный снимок сохраняет символическую границу.
- [ ] Проверить `struct S { char c; int i; };` при восьмибитном байте и четырёхбайтовом `int`: в профиле с выравниванием поля и структуры на 4 байта и округлением размера до этого выравнивания ожидать 8 байт; при плотном размещении с выравниванием на 1 байт — 5. При неизвестном правиле размещения оставить `sizeof(S)` без свёртки.
- [ ] Проверить один исходник с профилем по умолчанию и с переопределением `long` в 32 бита. При восьмибитном байте `sizeof(long)` должен дать 8 и 4 соответственно. В обоих профилях перегрузки `f(int)` и `f(long)` остаются различимыми, включая случай одинаковой ширины.
- [ ] При озеленении целого типа дать анализу общие свойства (знаковость и ширину в битах), сохранить связь с исходным типом C++ и у вызова — с выбранной перегрузкой. Одинаковые ширина и знаковость не делают `int` и `long` взаимозаменяемыми при генерации C++.
- [ ] Сквозной тест для профиля с 32-битными `int` и `long`: определить `f(int)` и `f(long)` с разными результатами, вызвать `f(1)` и `f(1L)`. Проверить обе цели после озеленения, наличие суффикса `L` при обратной генерации и выбор тех же перегрузок после повторного разбора.
- [ ] Проверить два .cpp с одним config.h и разными -DWIDE. Обе версии typedef должны существовать в одном Project с одинаковым исходным диапазоном и разной привязкой в каждой единице.
- [ ] Проверить изоляцию макросов соседних единиц, стабильность графа при повторном запуске и диагностику конфликтующих настроек.

## 2. Перевод исходного текста в токены и препроцессор

- [ ] Реализовать фазы в порядке C++03. Проверить преобразование триграфов до склейки строк, затем разбиение на preprocessing tokens и замену комментариев пробелом. Сохранять отображение в физические координаты.
- [ ] До замены комментариев пробелами в потоке препроцессора сохранить в графе исходного файла текст и координаты `//` и `/* … */`. Проверить сохранение комментариев при обычной генерации.
- [ ] Хранить комментарий один раз у файла. От поясняемой конструкции проводить `HAS_COMMENT`. Проверить комментарий после последнего объявления строки, несколько строк `//` непосредственно перед объявлением в исходном порядке и комментарий перед аргументом после запятой. Пустая строка отделяет предшествующий комментарий от конструкции. При неоднозначности сохранить комментарий только у файла.
- [ ] Разобрать внутри Doxygen-комментария `@brief`, `@param`, `@tparam` и `@return`, включая написание с обратной косой чертой. Сохранить полный исходный текст и связь с документируемой конструкцией. Связать записи `param` и `tparam` с соответствующими объявлениями параметров функции и шаблона. Предоставить описания через API.
- [ ] E2E: документировать шаблонную функцию с параметром и возвращаемым значением. Проверить обе формы префикса, порядок описаний, точные цели ссылок, сохранность неизвестной команды и всего комментария при обратной генерации. После вызова утилиты удаления комментариев проверить отсутствие оставшихся ссылок на удалённую документацию.
- [ ] Для `@param size` у функции с единственным параметром `count` сохранить запись без цели и выдать предупреждение на диапазоне имени `size`. Проверить успешное построение графа и сохранение исходного комментария при генерации.
- [ ] E2E: объявить `process(int count)` с `@param count` в заголовке и определить `process(int n)` в исходнике. Связать запись с `count` в документируемом объявлении; сопоставить параметры согласованных объявлений одной функции по позиции. Проверить переход от `n` к документации. В двух независимых правках проверить, что переименование `count` обновляет только связанное имя в теге, а переименование `n` сохраняет `@param count`. В обоих случаях свободный текст описания воспроизводится дословно.
- [ ] В запросе всей документации функции вернуть отдельные комментарии объявления и определения с их координатами, включая оба `@brief`. При повторном включении одного заголовка вернуть его комментарий один раз по физическому файлу и диапазону. Через API проверить привязку `@param` отдельно для каждого контекста включения, в том числе при разных сигнатурах под `#ifdef`.
- [ ] Добавить в пакет утилит библиотечную операцию Java API, которая по явному вызову возвращает новый `Project` без комментариев, включая текст неактивных ветвей. Штатный конвейер её не вызывает; отдельной команды CLI нет. Использовать лексические границы комментариев, сохранить разделение токенов и значимые переводы строк.
- [ ] Проверить исходный и очищенный снимки, `int/**/value;`, строку `"/* это текст */"` и обе ветви `#ifdef` с комментариями. После генерации очищенного снимка повторно разобрать и собрать обе конфигурации; в исходном снимке комментарии остаются доступными.
- [ ] Различать идентификаторы, универсальные имена символов, preprocessing numbers, литералы, операторы, альтернативные токены, имена заголовков. Проверить границы токенов и ошибки незакрытого литерала.

## 9. Потоки, диагностика, генерация и приёмка

- [ ] Расширять CFG вместе с инструкциями. Включить короткое замыкание, ветвление ?:, switch, переходы, нормальные и исключительные выходы, неявные вызовы деструкторов. Не придумывать порядок вычисления там, где язык его оставляет открытым.
- [ ] Представить в CFG неявный вызов деструктора со ссылками на объект и выбранный деструктор. Включать его на каждом пути выхода из области после успешного создания объекта, в том числе при возврате и раскрутке стека. Генератор C++ сохраняет исходную автоматическую длительность хранения и не вставляет явный вызов деструктора.
- [ ] E2E: для `Guard a; Guard b; work();` проверить порядок разрушения `b, a` при обычном выходе и при исключении из `work()`, перехваченном вызывающей функцией. Если конструктор `b` бросил исключение, среди этих двух объектов разрушается только `a`. Сверить пути CFG с журналом вызовов сгенерированной программы, включая число разрушений.
- [ ] Для внешней функции без доступного тела и без ограничивающей спецификации исключений строить обычное продолжение и возможный исключительный выход. Провести исключительный путь через разрушение уже созданных локальных объектов к подходящему обработчику либо к исключительному выходу вызывающей функции.
- [ ] Парный тест CFG: поместить `Guard g; work();` внутрь `try` с `catch (...)`. Для объявления `void work();` проверить путь от вызова через разрушение `g` к обработчику. Для `void work() throw();` такого пути от вызова нет. На обычном выходе в обоих случаях `g` разрушается один раз.
- [ ] Расширять DFG для адресов, ссылок, полей, элементов массива, параметров и возвратов. Проверить запись через указатель и чтение через другой указатель на тот же объект. При неполной информации использовать консервативный результат.
- [ ] Для внешнего вызова без доступного тела представить возможную запись через неконстантную ссылку как эффект конкретного вызова. На пути обычного возврата добавить этот источник к прежним достигающим записям объекта. Сам факт передачи ссылки не доказывает перезапись.
- [ ] Проверить `int x = 1; update(x); use(x);` с объявлениями `void update(int&);` и `void use(int);`. Через API и экспорт JSON проверить у чтения аргумента `use` оба возможных источника: инициализацию `x` и эффект вызова `update`. На инициализации не должно быть предупреждения `unread-write`.
- [ ] При доступном теле строить межпроцедурные связи с учётом места вызова: сопоставлять параметры с фактическими объектами, переносить эффекты записи и возвращаемое значение к соответствующему вызову. Для `void update(int& x) { x = 7; }` последующее чтение аргумента после нормального возврата должно иметь источником присваивание в теле; для условной записи сохранить и предшествующий источник.
- [ ] Удалять прежний источник только при доказанной записи в конкретный объект на всех соответствующих путях. Разделять обычные и исключительные выходы; объединять возможные эффекты нескольких целей виртуального вызова. Для рекурсии вычислять устойчивые сводки эффектов, для недоступных целей применять консервативное правило внешнего вызова. Проверить два вызова одной функции с разными объектами, передачу одного объекта по двум ссылкам и взаимную рекурсию.
